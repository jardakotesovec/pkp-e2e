## Summary

Since the fix for disabled accounts (`3407fc5bc0`), the app no longer
reads the "Keep me logged in" cookie at all. Someone who signs in with
"Keep me logged in" ticked (the default) is signed out as soon as their
session ends: after `session_lifetime` days idle (7 by default, where
`remember_me_lifetime` promises 30), or when the browser closes on an
install with `session_expire_on_close = On`. Until yesterday `main`
and the 3.5 branch signed them back in from the cookie. The same
change is why a second browser is now signed out when the account's
email address is changed (U03 S4, red on CI in all three apps): that
sign-out is intended (`invalidateOtherSessions()`), and only the
cookie used to hide it.

## Impact

- **Lost**: nothing stored; a person signs in again sooner than the
  login page and the configuration promise. Unsaved work in an open
  form is lost if the session ends under it, as it would without
  "Keep me logged in".
- **Who**: everyone who ticks "Keep me logged in", on every install; most
  felt by sites that set `session_expire_on_close = On` or a short
  `session_lifetime` and rely on `remember_me_lifetime` (pkp/pkp-lib#12547)
  to keep people signed in.
- **Way round**: none on screen; a site can raise `session_lifetime`.

Low: nothing is lost and signing in again gets the task done; the
"Keep me logged in" box and `remember_me_lifetime` simply do nothing. It
would be medium if a released version had kept people signed in this
way: no 3.5.0 release carries the July fallback (`3_5_0-3` to
`3_5_0-5` read the session alone), so on a release this is how it
already behaves, and the regression is against `main` and the 3.5
branch since 2026-07-21.

## Steps to reproduce

Preconditions:
- The default dataset, OJS `main` (the same on OMP and OPS, and on
  `stable-3_5_0`).
- In `config.inc.php`, under `[security]`, set
  `session_expire_on_close = On`.

1. Open the journal's Login page, sign in as `dbarnes` with "Keep me
   logged in" left ticked.
2. Close the browser completely and open it again (the session cookie
   goes; the `remember_web_…` cookie, valid 30 days, stays).
3. Open `http://<host>/index.php/publicknowledge/submissions`.

**Expected**: the submissions dashboard, signed in as `dbarnes`, as on
`main` before `3407fc5bc0` and on `stable-3_5_0` before `edc3d36c74`.

**Observed**: the Login page
(`…/publicknowledge/login?source=%2Findex.php%2Fpublicknowledge%2Fsubmissions`);
the same for the profile (`…/user/profile`). The browser sends the
`remember_web_…` cookie with that first request, and the answer removes
it: afterwards the browser holds a new session cookie and no
`remember_web_…` cookie. No line in the server log.

The second effect, the one U03 S4 meets: sign in as the same user in
two browsers (both with "Keep me logged in"), save a new email address
under "Edit Profile" › "Contact" in the first, then press "Identity"
in the second: a browser alert reads "##user.authorization.userRequired##"
and the tab stays empty; a full page load goes to the Login page.
Before the change the second browser stayed signed in.

## Cause

`3407fc5bc0` changed `PKPRequest::getUser()` back from

```php
// Fall back on Laravel authorization.
$user = Auth::user();
```

to

```php
if (Validation::isLoggedIn()) {
    $user = Repo::user()->get($this->getSessionGuard()->getUserId(), true);
}
```

`Auth::user()` was the only call that reached Laravel's
`SessionGuard::user()` with no user in the session, and so its
`recaller()` branch, which signs a person in from the `remember_web_…`
cookie through `PKPUserProvider::retrieveByToken()`. Now
`getUser()` and `Validation::isLoggedIn()` read only the session's
`userId`, and the remaining `Auth::user()` calls sit behind
`isLoggedIn()` or in sign-in and sign-out, so the cookie is still set
at sign-in (`Auth::login($user, $remember)`) but never read. The
`Auth::user()` line itself came on 2026-07-21 with `a6d68f9547`
(pkp/pkp-lib#12790, also for #12780); the October commit returns
`getUser()` to its pre-July form. The issue's own cases (a disabled
account signing in, a signed-in account disabled, "Login As" a
disabled account and back) hold after the change.

## Proposed fix

A proposal, tried; the team decides. Ask Laravel's guard for the user
as the session starts, so that its own "Keep me logged in" restore runs
before the session is first saved, and have that restore write the
session data a sign-in writes. Leave the browser's cookie alone except
where the guard sets or removes it, and store the token "Sign out"
cycles. Three files in pkp-lib, the same lines on `main` and
`stable-3_5_0`
([fix.diff](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-12780/fix.diff)
for `main`,
[fix-stable-3_5_0.diff](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-12780/fix-stable-3_5_0.diff)
for 3.5, whose `PKPAuthenticateSession::logout()` lacks `main`'s audit
entry; both applied at the app root):

- `PKPAuthenticateSession::handle()`, the session middleware that
  `Dispatcher::initSession()` runs before routing, first calls
  `$this->guard()->user()`. With no user in the session and the cookie
  in the request, Laravel's `SessionGuard::user()` restores the user
  from it (`userFromRecaller()` → `PKPUserProvider::retrieveByToken()`,
  whose `Repo::user()->get()` leaves disabled accounts out by default),
  moves the session to a new id and fires the login event; the parent
  middleware then checks the cookie's password hash. An override of
  `PKPSessionGuard::userFromRecaller()` writes the restored user into
  the session as a sign-in does (`setUserDataToSession()`: `userId`,
  `username`, `email`), shares the object with `getUser()`, and removes
  a cookie that brings no one in. API requests are left out, since
  their responses (`APIHandler`, `->send()`) never carry the session
  cookies: there the override only marks the recall as done, so the
  restore inside the session save does not run either.
- `PKPSessionGuard::updateSessionCookieToResponse()` stops clearing the
  remember cookie on every session update: the cookie changes only when
  the guard queues one (a sign-in with the box ticked sets it, "Sign
  out" removes it). A new `PKPSessionGuard::logoutOtherDevices()` sends
  the cookie Laravel's parent queues with the new password hash, which
  PKP never sent: changing one's own password then keeps this browser
  remembered (`ChangePasswordForm`, `LoginChangePasswordForm`,
  `ResetPasswordForm`, `UserDetailsForm` for one's own account).
- `PKPAuthenticateSession::logout()`, the middleware's own sign-out
  (the session's password hash no longer matches, because the password
  was changed in another browser; or, with `session_check_ip`, the
  address changed), calls `Auth::logoutCurrentDevice()`, as Laravel's
  `AuthenticateSession` does, instead of `Auth::logout()`, and sends the
  removed cookie. It ends this browser's session and remembered sign-in,
  and leaves the token of the person's other browsers alone.
- `PKPUserProvider::updateRememberToken()` stores the token it is given,
  as Laravel's `DatabaseUserProvider` does, instead of returning early
  because the guard has already set it on the user.

```php
// PKPAuthenticateSession::handle(), before parent::handle()
$this->guard()->user();

// PKPSessionGuard
protected function userFromRecaller($recaller)
{
    if ($this->recallAttempted) {
        return null;
    }
    if (Application::get()->getRequest()->getRouter() instanceof APIRouter) {
        $this->recallAttempted = true;
        return null;
    }
    $user = parent::userFromRecaller($recaller);
    if ($user) {
        $this->setUserDataToSession($user);
        Registry::set('user', $user);
    } elseif ($recaller->valid()) {
        $this->getCookieJar()->queue($this->getCookieJar()->forget($this->getRecallerName()));
        $this->updateSessionCookieToResponse();
    }
    return $user;
}
```

Why there. Who a request belongs to is the session's `userId`:
`getUser()`, `Validation::isLoggedIn()`, the public menus, the Login
page and "Login As" all read it, and a sign-in writes it behind the
disabled-account check `3407fc5bc0` was for. The session middleware
runs before any of those reads and before the session is first saved,
so a restore there is seen by every page and kept. Since `3407fc5bc0`
nothing asks the guard before that save, so Laravel's restore runs
inside it and is lost (the A8 report's Cause); the July version asked
it from `getUser()`, which left `userId` empty, the half-signed-in
state of U01 A8 (the public pages offer "Login", "Login As" fails on
the server). The override is the A8 report's own fix, and this is the
early call it said it needed. `getUser()` stays as `3407fc5bc0` left it,
so the disabled-account fix holds and the call cycle of the first try
below cannot form. Both pieces follow Laravel's own flow
(`SessionGuard::user()` → `userFromRecaller()` → `updateSession()`,
then `AuthenticateSession`'s hash check), so nothing of it is written
twice.

Every instance. `updateSessionCookieToResponse()` cleared the remember
cookie on every session update, not only on a restore (Observed: the
first page after the session ends removes it). The email-change save
under "Edit Profile" (`BaseProfileForm`) and "Login As" and back
(`signInAs()`, `signOutAs()`) each dropped "Keep me logged in" in that
browser as well. Leaving the cookie to the guard covers all of them, and
keeps the window fixed from the sign-in, as `remember_me_lifetime`
describes, instead of restarting it at every return. The same holds for
the cookie Laravel queues on a password change, which PKP never sent
(the `logoutOtherDevices()` override). The other `Auth::user()` callers
(`Validation::login()`, `logout()`, `isAuthorized()`,
`PKPPageRouter::getHomeUrl()`) run with a signed-in session and are
unchanged. Left out: a refused sign-in of a disabled account still
leaves Laravel's login key in the session (`Auth::attempt()` runs before
the disabled check), so the session row carries that user's id; nothing
signs anyone in from it.

What it touches, with the team's calls marked:
- A request that carries the cookie with no user in the session costs
  one user lookup. A restore is not a sign-in (maintainer's call,
  2026-10-14): it fires Laravel's login event (with `remember` true)
  but writes no `AUTH_LOGIN` audit entry and leaves the last-login date
  alone, so an outstanding password-reset link keeps working (U01 Rule
  8; `Validation::generatePasswordResetHash()` reads the date).
- API calls made after the session ended stay refused until the next
  page load signs the person in; a restore there could not keep its
  session. Without the patch each such call also wrote a session row
  for the person that no browser holds; with it, none.
- Team's call: the email change ends the other browsers' sessions but
  not their "Keep me logged in", so they are signed back in, as before
  `3407fc5bc0` (U03 S4 expects that). Removing their cookies would mean
  cycling the token there.
- "Sign out" now changes the token (as in Laravel), so it ends "Keep me
  logged in" in every browser. A changed password ends it in every other
  browser, each at its next request, through the middleware's sign-out.
  Without the `logoutCurrentDevice()` change that sign-out cycled the
  token once it was stored, and so also ended the remembered sign-in of
  the browser that had just changed the password (walked: a second
  browser's dashboard polls `/api/v1/_submissions/viewsCount`).
- With `session_check_ip = On` (the default), an IP change ends the
  session and the remembered sign-in in that browser only, and the
  removed cookie cannot sign it straight back in from the new address
  (read in the code, not walked: the walks all come from one address).
- Signing out while "Login As" someone cycles that person's token, not
  the manager's (`Auth::user()` is the impersonated user there).
- Disabling an account does not cycle its token: re-enabled, a cookie
  that was never refused in between works again.
- No stored data to repair. 3.5 takes the same lines (its own diff, for
  the context); 3.4 and 3.3 have no such cookie.

Alternatives: the `getUser()` fallback on `Auth::user()` (the July
version and this section's earlier direction) comes too late for the
session save and `isLoggedIn()`, brings A8 back, and loops while
`retrieveById()` calls `getUser()`. A revert of `3407fc5bc0` loses the
disabled-account fix it was for. The first two parts alone (the early
call and the override, ten lines) fix the regression and A8 and were
tried as such: with them, the cookie carries a person over one ended
session only, the other browsers of a password change are signed out
but so is the one that changed it, API calls restore into session rows
no browser holds, and a copy of the cookie taken before "Sign out"
signs the person in afterwards, since the cycled token is never stored.
That last one makes the remaining parts part of the fix rather than
follow-ups. A separate sign-in method in the guard, beside Laravel's
restore, was tried before the override; it worked the same and
repeated the hash check the parent middleware already makes.

Tried on `main` (OJS, OMP, OPS) and on `stable-3_5_0` (OJS), each before
and after the diff, on freshly reset fleets. Before it, the walks show
the Observed on all four. With it, the Steps end as Expected: once the
session cookie is gone, the profile and the dashboard open signed in,
twice in a row, with the cookie's expiry unchanged. The second browser
of an email change keeps the Identity form (U03 S4's case). The
neighbour checks held on all four:
- with the box unticked, the person is signed out;
- a disabled account's sign-in is refused and stays out, a signed-in
  account disabled is signed out, and "Login As" a disabled account and
  back works as before;
- a copy of the cookie taken before "Sign out", a cookie after a
  password change made elsewhere, and the cookie of an account disabled
  since all get the Login page, and the cookie is removed;
- an API call with the cookie alone is refused and writes no session
  row, and the next page signs the person in;
- the browser that saves an email change or changes its password stays
  remembered, while the second browser of that password change gets the
  Login page.

The U01 A8 walk ends as its Expected on the three apps: Users & Roles
opens signed in past the idle limit, "Login As" David Buskins opens his
dashboard, the public header names the user, and the Site
Administrator's "Login As" is still refused. The spec files U01, U03,
U06 and U08 pass on the three apps with the diff (OJS 41, OMP 41, OPS 42
tests), U03 S4 included. Evidence gives the commands.

Guard: the kept walks drive both directions (`remember-me.js`,
`disabled.js`, `fix-edges.js`); U03 S4 turns green; U01's Planned items
for A14 and A8 become tests once the fix lands.

Medium: about 55 lines in three shared files, in the authentication
path, where signed out too soon and a disabled account let in must be
tested together.
