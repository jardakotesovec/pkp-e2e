# "Keep me logged in" no longer keeps anyone signed in once their session ends

- **Severity** low
- **Effort** medium
- **Kind** regression
- **Affects**

Update 2026-10-08: two corrections from a second walk (OJS `main` and
`stable-3_5_0`, the default dataset). The browser does not keep sending
the "Keep me logged in" cookie: the first page opened after the session
ends removes it (Observed). And with the cookie read as before the
change, being signed back in removed the cookie as well, so it carried
a person over one ended session, not over every one in its 30 days
(Proposed fix). `pkp/pkp-lib#12780` was reopened on 2026-10-07.

## Summary

Since the fix for disabled accounts (`3407fc5bc0`), the app no longer
reads the "Keep me logged in" cookie at all. Someone who signs in with
"Keep me logged in" ticked (the default) is signed out as soon as their
session ends: after `session_lifetime` days idle (7 by default, where
`remember_me_lifetime` promises 30), or when the browser closes on an
install with `session_expire_on_close = On`. Until yesterday `main`
and the 3.5 branch signed them back in from the cookie. The same
change is why a second browser is now signed out when the account's
email address is changed (U03 S4, red on CI in all three apps): that
sign-out is intended (`invalidateOtherSessions()`), and only the
cookie used to hide it.

## Impact

- **Lost**: nothing stored; a person signs in again sooner than the
  login page and the configuration promise. Unsaved work in an open
  form is lost if the session ends under it, as it would without
  "Keep me logged in".
- **Who**: everyone who ticks "Keep me logged in", on every install; most
  felt by sites that set `session_expire_on_close = On` or a short
  `session_lifetime` and rely on `remember_me_lifetime` (pkp/pkp-lib#12547)
  to keep people signed in.
- **Way round**: none on screen; a site can raise `session_lifetime`.

Low: nothing is lost and signing in again gets the task done; the
"Keep me logged in" box and `remember_me_lifetime` simply do nothing. It
would be medium if a released version had kept people signed in this
way: no 3.5.0 release carries the July fallback (`3_5_0-3` to
`3_5_0-5` read the session alone), so on a release this is how it
already behaves, and the regression is against `main` and the 3.5
branch since 2026-07-21.

## Steps to reproduce

Preconditions:
- The default dataset, OJS `main` (the same on OMP and OPS, and on
  `stable-3_5_0`).
- In `config.inc.php`, under `[security]`, set
  `session_expire_on_close = On`.

1. Open the journal's Login page, sign in as `dbarnes` with "Keep me
   logged in" left ticked.
2. Close the browser completely and open it again (the session cookie
   goes; the `remember_web_…` cookie, valid 30 days, stays).
3. Open `http://<host>/index.php/publicknowledge/submissions`.

**Expected**: the submissions dashboard, signed in as `dbarnes`, as on
`main` before `3407fc5bc0` and on `stable-3_5_0` before `edc3d36c74`.

**Observed**: the Login page
(`…/publicknowledge/login?source=%2Findex.php%2Fpublicknowledge%2Fsubmissions`);
the same for the profile (`…/user/profile`). The browser sends the
`remember_web_…` cookie with that first request, and the answer removes
it: afterwards the browser holds a new session cookie and no
`remember_web_…` cookie. No line in the server log.

The second effect, the one U03 S4 meets: sign in as the same user in
two browsers (both with "Keep me logged in"), save a new email address
under "Edit Profile" › "Contact" in the first, then press "Identity"
in the second: a browser alert reads "##user.authorization.userRequired##"
and the tab stays empty; a full page load goes to the Login page.
Before the change the second browser stayed signed in.

## Cause

`3407fc5bc0` changed `PKPRequest::getUser()` back from

```php
// Fall back on Laravel authorization.
$user = Auth::user();
```

to

```php
if (Validation::isLoggedIn()) {
    $user = Repo::user()->get($this->getSessionGuard()->getUserId(), true);
}
```

`Auth::user()` was the only call that reached Laravel's
`SessionGuard::user()` with no user in the session, and so its
`recaller()` branch, which signs a person in from the `remember_web_…`
cookie through `PKPUserProvider::retrieveByToken()`. Now
`getUser()` and `Validation::isLoggedIn()` read only the session's
`userId`, and the remaining `Auth::user()` calls sit behind
`isLoggedIn()` or in sign-in and sign-out, so the cookie is still set
at sign-in (`Auth::login($user, $remember)`) but never read. The
`Auth::user()` line itself came on 2026-07-21 with `a6d68f9547`
(pkp/pkp-lib#12790, also for #12780); the October commit returns
`getUser()` to its pre-July form. The issue's own cases (a disabled
account signing in, a signed-in account disabled, "Login As" a
disabled account and back) hold after the change.

## Proposed fix

A direction, not a tried patch: read the "Keep me logged in" cookie again
when the session holds no user, and refuse a disabled account on that
path as the sign-in does. In `PKPRequest::getUser()`, after the
`isLoggedIn()` branch, let the guard restore the user from the cookie
(`Auth::user()`, or the guard's recaller alone), and in
`PKPUserProvider::retrieveByToken()` return `null` for a user whose
`getDisabled()` is true. `retrieveById()` must then stop calling
`getUser()`, or the two call each other. The restored user must also
land in the session's own user id (`PKPSessionGuard`), so that every
page agrees: until yesterday the cookie restored the user for
`getUser()` alone, which is the half-signed-in state of U01 A8 (public
pages and the Login page treat the person as signed out, "Login As"
answers a blank page).

Two tries on `stable-3_5_0` OJS (the same files as `main`), both taken
out again:
- `getUser()` falling back on `Auth::user()` alone: every request of
  the signed-in browser ran into the 120-second limit ("Maximum
  execution time … Facade.php"), since `retrieveById()` now calls
  `getUser()`.
- The same plus `retrieveById()` back to `Repo::user()->get((int) $id,
  true)`: "Keep me logged in" works again (both steps above pass; without
  "Keep me logged in" the person is still signed out), but a disabled
  account's sign-in, refused with "Your account has been disabled.
  Please contact the administrator for more information.", leaves that
  account signed in on the next page. So the disabled check on the
  cookie and sign-in paths is part of the fix, not optional.

A third part, latent today: "Sign out" never changes the remember
token. Laravel's `SessionGuard::cycleRememberToken()` sets the new token
on the user object and then calls `PKPUserProvider::updateRememberToken()`,
which returns early because the object's token already equals it
(line 103 on `main` and `stable-3_5_0`), so nothing is stored; the sign-in
never rotates it either. Seen 2026-10-07 on OJS `main` and 3.5 (dataset
fleet, `dbarnes`): `users.remember_token` unchanged after "Sign out", and
a second sign-in set a byte-identical cookie. Harmless while the cookie
is not read; once a fix reads it again, a copied cookie would outlive
"Sign out" until the password changes, so the fix should store the
cycled token (compare against the stored value, not the object's). No
3.5.0 release read the cookie, so no release is exposed.

A fourth part, for the same fix: the cookie did not last its 30 days
before the change either. With the three files as they were before
`edc3d36c74` (3.5 OJS, 2026-10-08), the first page after the session
ended opened signed in, and the browser was left with a new session
cookie and no `remember_web_…` cookie: the next ended session meant
the Login page. Today's code removes the cookie on that first page
too, without signing anyone in. A fix that should honour
`remember_me_lifetime` has to set the cookie again when it restores
the person (or stop removing it), and the guard below should drop the
session twice.

Guard: an e2e or integration test that signs in with "Keep me logged in",
drops the session and expects to stay signed in; and one that expects
a disabled account to stay signed out after its refused sign-in (the
kept `disabled.js` drives both).

Medium: a few lines in two shared files, but in the authentication
path, where both directions (signed out too soon, a disabled account
let in) must be tested together, and the July and October versions
already went one way each.
