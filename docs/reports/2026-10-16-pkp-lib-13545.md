## Summary

Since `pkp/pkp-lib#13543`, an article version's "Body Text" page has an
"Export" menu. "Export to HTML" saves the text as an "HTML" galley, and
"Preview: PDF" › "Create PDF" saves it as a "PDF" galley. A later export
of the same version is meant to add a revision to that galley, not a
second galley.

1. Two or more exports of the same version that reach the server at the
   same moment (two editors, or one request sent twice) each add a
   galley. Four simultaneous HTML exports left three "HTML" galleys; four
   PDF exports left two "PDF" galleys. Readers of a published version
   then see the label more than once, and later exports revise only one
   of the copies. Deleting the extras on "Galleys" puts it right.
2. The HTML export run outside a web request (a command-line tool or a
   queued job, which has no journal in its request) stops with an error
   and stores nothing. The PDF export works there. No screen reaches this
   today.

## Finding 1 — Simultaneous exports of one version each make a galley

- **Severity** low
- **Effort** small
- **Kind** defect
- **Affects**
  - main: OJS
  - ore, 3.5, 3.4, 3.3: none (code)

### Impact

- **Lost**: nothing is lost. A version gets a second or third "HTML" or
  "PDF" galley. Once published, readers see the label twice; later
  exports revise only one copy, so the others keep the older text.
  Nobody is told.
- **Who**: editors and Layout Editors who export the same version at
  the same time, or whose export request is sent twice (a double press,
  a retry).
- **Way round**: delete the extra galleys on "Galleys".

Low: it needs simultaneous requests, the extra galleys are visible on
"Galleys", and one deletion each clears them. Silent duplicates on many
published articles would raise it.

### Steps to reproduce

Preconditions:

- The default dataset, OJS `main`.
- The site served by more than one PHP worker, as php-fpm serves a
  production site. With PHP's built-in server, start it with
  `PHP_CLI_SERVER_WORKERS=4`; a single worker answers one request at a
  time and hides the fault.
- `api_key_secret` set in `config.inc.php`, and `dbarnes`'s API key from
  Profile › "API Key".

No screen sends two exports at the same moment reliably, so the steps
send the requests the "Export" menu sends.

1. Send four "Export to HTML" requests for "Yam diseases and its
   management in Nigeria" (submission 15, publication 16, in
   Production, no galleys) at the same moment:

   ```sh
   KEY='<dbarnes API key>'
   BASE='http://localhost/index.php/publicknowledge/api/v1/submissions'
   for i in 1 2 3 4; do
     curl -s -w ' %{http_code}\n' -X POST "$BASE/15/publications/16/bodyText" \
       -H "Authorization: Bearer $KEY" -H 'Content-Type: text/html; charset=UTF-8' \
       --data "<p>Export $i</p>" &
   done; wait
   ```

2. Send four "Create PDF" requests for "Genetic transformation of forest
   trees" (submission 5, publication 6, in Production, no galleys) the
   same way, with any PDF file:

   ```sh
   for i in 1 2 3 4; do
     curl -s -w ' %{http_code}\n' -X POST "$BASE/5/publications/6/bodyText/pdf" \
       -H "Authorization: Bearer $KEY" -H 'Content-Type: application/pdf' \
       --data-binary @article.pdf &
   done; wait
   ```

3. Sign in as `dbarnes` and open each submission's "Publication" ›
   "Galleys".

**Expected**: one "HTML" galley on "Yam diseases…" and one "PDF" galley
on "Genetic transformation…", each "Generated from text editor"; the
later exports are revisions of it, and every answer names the same
galley.

**Observed**: all eight requests answer 201, with these galley ids:

```
HTML  201 {"id":6}  201 {"id":4}  201 {"id":5}  201 {"id":4}
PDF   201 {"id":8}  201 {"id":7}  201 {"id":7}  201 {"id":7}
```

"Yam diseases…" has three "HTML" galleys (4, 5, 6), each with its own
file; "Genetic transformation…" has two "PDF" galleys (7, 8). The count
varies from run to run: two or three galleys of four exports, in each
of eight runs since 2026-10-23.

Control: the same exports sent one after another leave one galley, and
each later export adds a revision to it.

### Cause

`PKP\bodyText\Repository::createGalleyFile()`
(`classes/bodyText/Repository.php`) looks for the version's generated
galley (same label, same locale, `generatedFrom` "editor") inside a
database transaction, and adds a galley and a submission file when it
finds none. Nothing makes a second export wait for the first: each
transaction looks before any has added its galley, finds none, and adds
one.

The feature's first commits started that transaction with a row lock on
the publication, commented "Serialize concurrent exports so they cannot
create duplicate galleys". `85e618b07f` ("Use revision count instead of
the label in the schema") removed it, and the merge carries the file
without it.

Reach:

- the HTML and the PDF export, which share `createGalleyFile()`
  (both driven);
- on a new version, the export that gives the copied galley a file of
  its own: by the code, simultaneous exports there each add a new
  submission file and only the last is attached to the galley, the
  others left unused (not driven).

### Proposed fix

Put the lock back as the first statement in the transaction
([`lock-fix.diff`](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13545/lock-fix.diff)):

```php
$galleyId = DB::transaction(function () use (/* … */) {
    // Serialize concurrent exports so they cannot create duplicate galleys.
    DB::table('publications')->where('publication_id', $publicationId)->lockForUpdate()->first();
```

The second export then waits until the first has committed, finds its
galley and adds a revision. Tried during the review, twice on each of
two rounds and each time on a fresh dataset, on code that differs from
the merged file only in the optional user: four simultaneous HTML
exports and four PDF exports each left one galley, and the later
answers named it.

- **Alternatives**: a unique index on the generated galley's columns
  would need a schema change and an upgrade migration for a rule the
  lock already enforces; checking for the galley again after adding it
  narrows the window without closing it.
- **What goes with it**: nothing to repair beyond deleting duplicate
  galleys an install may already hold. A unit test cannot race two
  requests; the e2e guard is U48's Planned export scenario.

Small: two lines in one method, following the round-2 code.

## Finding 2 — The HTML export fails when the request has no journal

- **Severity** low
- **Effort** small
- **Kind** defect
- **Affects**
  - main: OJS
  - ore, 3.5, 3.4, 3.3: none (code)

### Impact

- **Lost**: the HTML galley a command-line tool or a queued job meant to
  make; nothing is stored, and the caller gets a `TypeError`.
- **Who**: no one today: only the REST API calls the export, and an API
  request always carries the journal. A plugin, a command-line tool or a
  job that exports the Body Text would meet it on every HTML export.
- **Way round**: none for such a caller; the PDF export works.

Low: a latent defect that no user can reach today.

### Steps to reproduce

None through the screens: no screen or API request reaches the export
without a journal in the request. A command-line tool, a scheduled task
or a queued job calling `Repo::bodyText()->createHtmlFile()` reaches it,
the case the merged commit `6035a6fed8` ("Make user nullable in case of
command line usage") prepared the export for.

**Expected**: from a command-line tool, with or without a signed-in
user, `createHtmlFile()` stores an "HTML" galley (and a revision of it
the second time), as `createPdfGalley()` does.

**Observed**: every `createHtmlFile()` call stops, with the admin
signed in and with no user, and no file is stored:

```
TypeError: PKP\submissionFile\maps\Schema::__construct(): Argument #4 ($context) must be of type PKP\context\Context, null given
  classes/core/MapContainer.php:37
  classes/submissionFile/Repository.php:105
  classes/bodyText/Repository.php:407
```

The same calls of `createPdfGalley()` store a "PDF" galley and, the
second time, a revision of it, with or without a user.

### Cause

`createGalleyFile()` resolves the journal for a request without one
(from the submission's `contextId`) and uses it for the genres and the
file's name. `prepareHtmlImages()`, which the HTML export calls first,
does not get that journal: it builds the submission-file map with
`Repo::submissionFile()->getSchemaMap($submission, [])`
(`classes/bodyText/Repository.php:407`, from `d830a2a01b`). The map
container fills the map's `Context` argument from the request, which is
null outside a web request, and the map's constructor takes only a
`Context`.

Reach:

- the HTML export, every call, with or without figures in the text
  (driven without figures);
- `Repository::map()` (line 47) builds the same map, but only the Body
  Text API reads it, always with a journal (code);
- the PDF export builds no map (driven).

### Proposed fix

Pass the journal `createGalleyFile()` already resolved into
`prepareHtmlImages()`, and build the map with it
([`context-fix.diff`](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13545/context-fix.diff)):

```php
$schemaMap = app('maps')->withExtensions(Repo::submissionFile()->schemaMap, [
    'submission' => $submission,
    'genres' => [],
    'context' => $context,
]);
```

Tried during the review, on code byte for byte the merged file's: the
command-line calls stored an "HTML" galley and a revision of it with the
admin signed in, and an "HTML" galley with no user; the HTML export from
the "Body Text" page, a figure included, and the refusal of another
submission's image were unchanged.

- **Alternatives**: an optional `Context` on
  `SubmissionFile\Repository::getSchemaMap()` would cover every caller,
  but changes a shared method's signature for one caller that has the
  journal at hand.
- **What goes with it**: a unit test calling `createHtmlFile()` with no
  context in the request.

Small: one parameter and the map's arguments, in one file.
