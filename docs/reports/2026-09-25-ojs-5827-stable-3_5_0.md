# stable-3_5_0: a title holding a bare "<" (as in "p<0.05") is cut off at the "<" in the article's JATS XML

Regression. OJS `stable-3_5_0` at `a3dc3b54ff` (lib/pkp `479b38a09c`);
introduced by pkp/ojs#5827 (`4a76983529`, merged 2026-09-24:
`plugins/generic/jatsTemplate` `14f51fa667..26c6ca0aa2`, for
pkp/pkp-lib#12414). `main` does not show it: the same title comes through
whole at ojs `d9b567efec` (driven on both). OMP and OPS: not affected,
the plugin ships in OJS alone. Tracked in `docs/tracking/ci-triage.md`
"Open regressions". Temporary: delete once acted on.

## Summary

On 3.5, an article's default JATS XML (the "JATS XML" page under
Publication, and `GET …/publications/{id}/jats`) now builds its titles
through the HTML-to-JATS conversion ported from `main`. A title, subtitle
or translated title stored with a bare "<" in front of a character, as
statistics titles often have ("Effects at p<0.05 in small trials"), comes
out cut off at the "<": "Effects at p". Before the update the JATS carried
the whole title. The workflow and the article page still show the full
title.

## Impact

Journals that write titles through the REST API (an integration, a
migration script) with a comparison sign in them: "p<0.05", "n<30",
"a<b". The editor's own "Title & Abstract" box stores the sign as
`&lt;` and is not affected. What they lose is the rest of the title in
every consumer of the default JATS XML (the "JATS XML" page and a JATS
file made from it); nothing warns, because the result is well-formed.
The OAI-PMH `jats` record is not affected (it builds its titles itself).
Workaround: store the sign as `&lt;`. Minor: a narrow path (API-written
titles with a bare "<"), output only, but silent loss of title text.

## Steps to reproduce

Preconditions: a fresh 3.5 install (`stable-3_5_0`) with its default
languages and an `api_key_secret` set in `config.inc.php`; one journal;
one submission at any stage; a Journal Manager account.

1. Sign in as the Journal Manager, open the user menu › "Edit Profile" ›
   "API Key", and press "Generate"; copy the key.
2. From any HTTP client, send
   `PUT /index.php/{journal}/api/v1/submissions/{id}/publications/{publicationId}`
   with the header `Authorization: Bearer {key}` and the body
   `{"title": {"en": "Effects at p<0.05 in small trials"}, "subtitle": {"en": "Cohorts of n<30 patients"}}`.
   It answers 200 and returns the title as sent.
3. Open the submission's workflow › "Publication" › "JATS XML" (or
   `GET …/publications/{publicationId}/jats` with the same key) and read
   the `<title-group>`.

Expected (the behavior before the update, and `main`'s today):

```xml
<article-title xml:lang="en">Effects at p&lt;0.05 in small trials</article-title>
<subtitle xml:lang="en">Cohorts of n&lt;30 patients</subtitle>
```

Observed:

```xml
<article-title xml:lang="en">Effects at p</article-title>
<subtitle xml:lang="en">Cohorts of n</subtitle>
```

A translated title is cut the same way (`<trans-title>Effets à p</trans-title>`
for "Effets à p<0,05 dans de petits essais"). The workflow's header reads
"Effects at p<0.05 in small trials: Cohorts of n<30 patients". Control:
the same PUT on `main` gives the Expected output.

## Cause

`plugins/generic/jatsTemplate/classes/JatsHelper.php` on
`stable-3_5_0`, `htmlToJatsElement()`: the first step is
`strip_tags($html, $allowedTags)`, which reads "<0.05 in small trials" as
the start of an unterminated tag and drops everything after it; the
plain-text fallback strips the same way. `main`'s helper runs
`PKPString::stripUnsafeHtml($html)` first (`JatsHelper.php:90` on
`main`), and HTMLPurifier turns the stray "<" into `&lt;`, which
`strip_tags()` leaves alone; the backport left that step out. The removed
3.5 path (`Article::mapHtmlTagsForTitle()` and `createElement()`) never
stripped tags, so the sign reached the XML as text.

## Proposed fix

A proposal; the team decides.

1. Port `main`'s first step too: `$html = PKPString::stripUnsafeHtml($html);`
   at the top of `JatsHelper::htmlToJatsElement()` on `stable-3_5_0`
   (3.5's `PKPString` has the method). One line; it also brings 3.5's
   output closer to `main`'s for any other stray markup.
2. The titles' other issue on this branch (tag names written as text,
   "The <i>species</i> element", turned into markup) is `main`'s pkp/ojs#5813
   mechanism and is fixed with it; it is carried in that report, not here.
