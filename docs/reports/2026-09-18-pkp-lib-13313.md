Temporary report (RUNBOOK "What goes where"): delete once the team has
acted on it. Spec entry: `docs/specs/U06-user-invitations.md`, register
A9 (❓, reviewed by @beaug 2026-09-18). Found 2026-09-18 by the upstream-sync claim check of the
changed slice (S18a) on OJS `7c8d69af3e` (lib/pkp `14473fe784`), OMP
`c6a132892` and OPS `4bb66b1469` (both lib/pkp `1bcd4dd55f`); driven twice
on each app, then once more on freshly reset databases the same day
(`.reports/sync/s18-13313-fresh/result-{ojs,omp,ops}.json`), the same on
all three apps every time.

**Ruling, @beaug 2026-09-18 (the sync's thread):** "Remove Role" and the
masthead select are to stay active for a disabled user; that half is
intended. The removal email's language did not take the disabled state
into account; that may be intended and may be patched in the future. What
stays open is the email's wording alone (U06 A9, narrowed the same day).

This is not a regression. It is a gap between the fix and the intention
the issue states, and the issue is still open, so it is cheap to close
with it.

## The change and its intention

pkp/pkp-lib#13313 ("Edit User Page, disabled user causing error when
trying to edit in users & roles"), commit `2ecbd331ee` ("Disable user edit
page load fix", 2026-09-15; the 3.5 twin is `d3079f201e`, PR #13330):
`PKPUserController::get()` reads the user with `get($userId, true)`, so
`GET users/{id}` answers for a disabled user, and
`UserRoleAssignmentInviteResource` adds `disabled` to the payload, which
the details step answers with the disabled-user warning.

The issue's expected result: "Should not throw an error. I would also
assume that this user is disabled so all fields are disabled meaning they
can't be edited."

The first half is met on OJS, OMP and OPS: Users & Roles › Edit on a
disabled user's row no longer pops "The requested resource was not found."
over an empty wizard (spec U06 register A6, retired today). It opens "STEP
1 - Enter details and invite for roles" with the user's details and roles
under "The user is currently disabled." / "The user was disabled. You
cannot assign them a role while they are disabled. Please enable the user
first to invite them to a role.", with "Add Another Role" and "Save And
Continue" inactive.

## Finding: "Remove Role" and the masthead select still act on the disabled user, who is then emailed that their account "is still active"

Steps, on a fresh install of OJS, OMP or OPS at the tips above:

1. Sign in as a Journal Manager (Press Manager, Preprint Server Manager).
2. Settings › Users & Roles. Pick a user who holds two roles in the
   journal (the drive used Author and Reader). Open the row's menu ›
   "Disable User" › "OK".
3. Open the same row's menu › "Edit".
4. In the roles table, press "Remove Role" on the Reader row. The dialog
   "Remove Role" asks "Are you sure you want to remove this role? The user
   will lose access and permissions associated with it." Press "Remove
   Role".
5. On the Author row, change the masthead select to the other value. The
   dialog "Confirm masthead visibility change" says "This will update
   whether this user appears on the journal masthead for the selected
   role. The user will be notified of this change." Press "Confirm".

Expected, by the issue's sentence: every field on a disabled user's screen
is inactive, so steps 4 and 5 offer nothing to press; and a disabled
account is not written to about its roles.

Observed, all three apps:

- Step 4: `PUT users/{id}/endRole/{userGroupId}` answers 200; the Reader
  row shows End Date today and "User Removed From Role". The disabled
  user's mailbox then holds "You have been removed from a role", whose
  body says "Your account with {journal} is still active and any other
  roles you previously held are still active."
- Step 5 on OJS: `PUT users/{id}/masthead/{userGroupId}` answers 200 and
  the disabled user is emailed "Your journal masthead visibility has been
  updated". On OMP and OPS the same press answers 500 with the raw error
  "Email template USER_ROLE_MASTHEAD_UPDATE not found. The migration
  script I11800_AddUserRoleMastheadUpdateEmail needs to be run." (the
  existing U06 register entry OMP1, not this change).
- Controls: disabling a user, opening Edit and meeting a disabled user on
  the invitation wizard's search step email nobody (a second disabled
  user and two enabled users: 0 messages each).

Cause, in the developer layer (ui-library): the payload's `disabled` flag
gates the banner (`UserInvitationDetailsFormStep.vue`), the new-role rows
and "Add Another Role" (`UserInvitationUserGroupsTable.vue`) and the
continue button (`isSubmitting` in `UserInvitationPageStore.js`); the same
table's current-role rows render their masthead `FieldSelect` and "Remove
Role" without reading it. The server side (`endRole`, `masthead`) does not
look at the user's disabled state either.

Kept script: `shared/playwright/checks/sync/pkp-lib-13313/s18a.js`
(`PROBE_FEATURE=sync PROBE_AGENT=<agent> node bin/probe.js all <script>`;
it seeds a scratch context, disables two scratch users on screen and
records every screen; facts in `result-<app>.json` › `editPress`,
`mailAtEnd`). Snapshots of the first drives: `.reports/sync/ccS18a/`
(`edit-4-remove-role-dialog-*`, `edit-5-after-remove-confirmed-*`,
`edit-5b-masthead-confirmed-*`).
