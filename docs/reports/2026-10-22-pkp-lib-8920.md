# Edits to a published article no longer reach ORCID, and imported articles stay out of search

- **Severity** medium
- **Effort** small
- **Kind** regression
- **Affects**
  - main: OJS, OPS (both halves); OMP (the import only: a press sends no works to ORCID)
  - 3.5: none (walked on OJS; OMP and OPS by code, the same listeners and jobs)
  - ore: OJS (code; pkp-lib `ore` carries `b44cf27793`, and no listener hears either event)
  - 3.4: none (code; a published version cannot be edited, and `BatchMetadataChangedListener` indexes an import)
  - 3.3: none (code; the import indexes each article itself)

## Summary

An editor who corrects the title or abstract of an article that is
already published ("Title & Abstract", "Save") sees the change on the
article page, but the journal no longer sends it to the ORCID records
of the article's authors: their ORCID record keeps the old title, while
publishing the article sent it there.

An article, book or preprint imported as published with the Native XML
plugin goes live, but the site's search never finds it. It appears in
search only after an administrator rebuilds the search index from the
command line.

Nothing tells anyone in either case. Unpublishing and publishing the
item again sends it to ORCID and indexes it. The edit also leaves the
search index stale (U15 A3); the same fix closes it.

## Impact

- **Lost**: an up-to-date work on each verified contributor's ORCID
  record after a correction; and search for every item imported as
  published. Neither is announced.
- **Who**: editors of journals and preprint servers on ORCID's Member
  API who correct a published item one of whose contributors has
  verified their ORCID iD; managers and administrators who import
  published content (a back catalogue, a migration) on any of the three
  apps.
- **Way round**: unpublish and publish again (or publish a new
  version), item by item; for imports, an administrator runs
  `php tools/rebuildSearchIndex.php`, which needs server access. Until
  then each correction and each import adds to what is stale.

Medium: no content is lost and both halves have a way round, but ORCID
records and the search stay wrong without a word to anyone. A journal
that imports its whole back catalogue and finds none of it in search
would raise it.

## Steps to reproduce

Preconditions: the default dataset, OJS `main` (OPS the same with a
preprint; OMP for the import only). An ORCID Member Sandbox client
("Client ID" and "Client Secret") that accepts the install's address as
a redirect, and an ORCID sandbox account for the contributor.

Editing a published article:

1. Sign in as `rvaca`. Settings › Users & Roles › "ORCID": tick "Enable
   ORCID functionality", set "ORCID API" to "Member Sandbox", enter the
   "Client ID" and "Client Secret", "Save".
2. Open submission 17, "Antimicrobial, heavy metal resistance and
   plasmid profile of coliforms isolated from nosocomial infections in a
   hospital in Isfahan, Iran", › "Contributors". Edit Vajiheh
   Karbasizaed and press "Request verification".
3. As the contributor, open the link in the email that arrives, sign in
   to the ORCID sandbox and authorize. The journal's page reads "Your
   ORCID iD has been verified and successfully associated with the
   submission." and "The submission has been added to your ORCID
   record."
4. On sandbox.orcid.org, the contributor's record lists the article
   under "Works" with its title.
5. Back as `rvaca`, submission 17 › "Title & Abstract". The page shows
   "Warning: This version has been published. Editing it may impact the
   published content." Change "Title" to "Coliforms in an Isfahan
   hospital", "Save".
6. Wait a minute for the install's background jobs, then reload the
   contributor's ORCID record.

**Expected**: the work on the ORCID record reads "Coliforms in an
Isfahan hospital", as on 3.5, which sends the work again after the
save and updates it in place.

**Observed**: the work keeps "Antimicrobial, heavy metal resistance and
plasmid profile of coliforms isolated from nosocomial infections in a
hospital in Isfahan, Iran". The save sends nothing to ORCID. Publishing
does send: the same contributor's work goes out when the article, or a
new version of it, is published.

Importing a published article:

1. As `rvaca`, Tools › "Import/Export" › "Native XML Plugin" › "Export
   Articles": tick submission 17, "Export Articles", and keep the file.
2. In the file, change the text of `<title locale="en">` to "Velmorak
   coliforms", so the copy can be told apart.
3. "Import" tab: upload the file, "Import". "Import Results" reads "The
   import completed successfully. The following items were imported:"
   and the article.
4. Signed out, the journal's "Search": search for "Velmorak".

**Expected**: "Found one item." with "Velmorak coliforms" (on 3.5 once
the import's background job has run).

**Observed**: "No Results", while the imported article's own page
opens. After an administrator runs `php tools/rebuildSearchIndex.php`,
the same search finds it.

## Cause

On 3.5 a publication edit and a Native XML import each fire an event
that a listener turns into a queued search-index job:

- `PKPSubmissionController::editPublication()` (lib/pkp
  `api/v1/submissions/PKPSubmissionController.php:1322`) fires
  `MetadataChanged`; `MetadataChangedListener::handle()`
  (`classes/observers/listeners/MetadataChangedListener.php:43`)
  dispatches `MetadataChangedJob`, which calls the search index's
  `submissionMetadataChanged()`, `submissionFilesChanged()` and
  `submissionChangesFinished()`.
- `NativeXmlSubmissionFilter::process()`
  (`plugins/importexport/native/filter/NativeXmlSubmissionFilter.php:204`,
  under "// Index imported content") fires `BatchMetadataChanged`;
  `BatchMetadataChangedListener::handle()` (line 43) dispatches
  `BatchMetadataChangedJob`, which does the same per imported
  submission.
- `pkp/pkp-lib#10744` ("If any metadata is changed with the submission,
  a redeposit should be attempted, e.g. on the hook
  `ArticleSearchIndex::articleMetadataChanged`") put the ORCID send at
  the end of `submissionMetadataChanged()`: OJS
  `classes/search/ArticleSearchIndex.php:81-83` (for a published
  publication) and OPS `classes/search/PreprintSearchIndex.php:80-83`
  call `(new SendSubmissionToOrcid($publication, $context))->execute()`,
  which queues a `DepositOrcidSubmission` per verified contributor; the
  deposit updates the existing work through its stored put-code.

`b44cf27793` replaced that search framework with Laravel Scout ("Remove
dead job/listener code"): it deleted both listeners and both jobs, and
the app commits deleted `ArticleSearchIndex`, `PreprintSearchIndex` and
`MonographSearchIndex`. The events stayed. `main` still fires
`MetadataChanged` in `editPublication()` (line 1457) and
`BatchMetadataChanged` in `NativeXmlSubmissionFilter::process()`
(line 204), and nothing listens: `git grep "MetadataChanged::class"` is
empty in pkp-lib, OJS, OMP and OPS, whose listeners are discovered from
`classes/observers/listeners` (`EventServiceProvider.php:86-87`).

What `main` kept listens to publishing only:
`UpdateSubmissionInSearchIndex` (`PublicationPublished`,
`PublicationUnpublished`; lines 30-52) and the `SendSubmissionToOrcid`
listener (`PublicationPublished`, published or scheduled; lines 30-50).
An import writes the publication with its stored status and never goes
through `Repo::publication()->publish()`, so neither runs. The rewrite
was for the search engine; its PRs do not mention ORCID, and the
ORCID send went with the class it lived in.

Reach:

- A galley file's metadata save (`PKPManageFileApiHandler::saveMetadata()`,
  line 250) fires `MetadataChanged` and is not re-indexed either (code).
- The scheduled-publish task (`PublishSubmissions.php:55`) and OJS's
  issue publish (`IssueGridHandler.php:634`) fire `MetadataChanged`
  after `publish()`, whose `PublicationPublished` covers them (code).
- The edit's search half is U15 A3 (all three apps on `main`).
- OMP sends no works (`SendSubmissionToOrcid::canDepositSubmission()`
  returns false), so only its import half applies.

## Proposed fix

A listener in pkp-lib on both events that, like the two
`PublicationPublished` listeners, updates the search index and, for a
published current publication, runs the same ORCID send. Not tried:
its ORCID half can only be checked against ORCID's sandbox, which the
test installs do not reach.

```php
// lib/pkp/classes/observers/listeners/UpdateSubmissionOnMetadataChange.php
class UpdateSubmissionOnMetadataChange
{
    public function subscribe(Dispatcher $events): void
    {
        $events->listen(MetadataChanged::class, fn (MetadataChanged $e) => $this->update(collect([$e->submission])));
        $events->listen(BatchMetadataChanged::class, fn (BatchMetadataChanged $e) => $this->update(
            Repo::submission()->getCollector()
                ->filterByContextIds([Application::SITE_CONTEXT_ID_ALL])
                ->filterBySubmissionIds($e->submissionIds)
                ->getMany()
        ));
    }

    protected function update(Collection $submissions): void
    {
        app(\Laravel\Scout\EngineManager::class)->engine()->update($submissions);
        foreach ($submissions as $submission) {
            $publication = $submission->getCurrentPublication();
            if ((int) $publication?->getData('status') !== PKPPublication::STATUS_PUBLISHED) {
                continue;
            }
            $context = Application::getContextDAO()->getById($submission->getData('contextId'));
            if (OrcidManager::isEnabled($context)) {
                (new \APP\orcid\actions\SendSubmissionToOrcid($publication, $context))->execute();
            }
        }
    }
}
```

It lives where the events are fired and the other two listeners live,
so every caller is covered: the edit, the galley file's metadata save
and the import. The ORCID send runs inside the request, as the publish
listener's does; the work is built there and only the deposit is
queued. 3.5 built it inside a queued job, which fails under the
command-line worker
([2026-10-21-pkp-lib-10744-stable-3_5_0.md](https://github.com/jardakotesovec/pkp-e2e/blob/main/docs/reports/2026-10-21-pkp-lib-10744-stable-3_5_0.md)).

**Alternatives**:

- Restore `MetadataChangedListener` and its job: the search-index
  classes it called are gone, and building the work in a queued job is
  what fails on 3.5.
- Publish imported items through `Repo::publication()->publish()`: it
  would run every publish listener (`NotifyAuthorOnPublication` among
  them) for content that was published elsewhere.
- Add the two events to `UpdateSubmissionInSearchIndex` and the ORCID
  send to `SendSubmissionToOrcid`: equivalent, in two files.

**What goes with it**: an imported contributor carries no ORCID
token (the export holds none), so for an import the send finds no one
and queues nothing. The issue publish and the scheduled-publish task
fire both events, so they index twice (the rows are deleted and
rebuilt) and send twice; `DepositOrcidSubmission` is unique per author
while queued, so the second send folds into the first. Items imported
or edited on an install of `main` or `ore` stay stale until they are
edited again or the index is rebuilt; an upgrade note pointing to
`tools/rebuildSearchIndex.php` covers the search. Test: a listener test
that fires each event for a published submission with a verified
contributor and asserts the search job and one `DepositOrcidSubmission`
are queued, plus an e2e scenario for U15 A3.

Small: one listener class in pkp-lib modelled on the two that exist,
and its test.
