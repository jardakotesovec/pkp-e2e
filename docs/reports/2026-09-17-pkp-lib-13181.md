## The change and its intention

pkp/pkp-lib#13181 ("Invitation accept/decline URLs name the wrong journal
when the invitation is sent from a queued job"), commits `4d9ec3cbd0`
("Respect Invitation's context rather than request's") and `aeac6f75cf`
("Fix redirect to profile/contact after needed login"). Accept and decline
links, the decline page's form address and the redirect targets are now
built from the invitation's own journal (`Invitation::getContextPath()`,
`index` when the invitation has none) instead of the journal of the
request that happens to be running. For role invitations and reviewer
access links that is the fix the issue asks for, and it holds: role
invitation links on a two-language journal, the accept wizard, the decline
page and the reviewer's one-click link were all driven and work
(`.reports/sync/rr10/suspicions.md`, S1 and S5a). The old blank 500 on the
"reject" link of a site-level email change (spec U03, register A3) is gone
on OJS.

The two findings below are side effects on the **email-change**
invitation, which is always created without a journal
(`classes/user/form/BaseProfileForm.php:76-78`:
`$invite->initialize($user->getId())`, no context id), so after the change
it always counts as a site-level invitation, wherever it was requested.

The "before" side of both findings was driven the same day on OPS, whose
lib/pkp pointer (`360badeef5`) still carries the pre-change code
(`.reports/sync/s17-13181-ops-before/check-13181-emailchange-ops.json`,
the same kept script): a two-server account's links read
`{A}/invitation/accept?…` and `{A}/invitation/decline?…` and both land on
`{A}/user/profile#contact` inside server A; a one-server account's
"reject" link reads `{J}/invitation/decline?…`, the form posts to
`{J}/invitation/confirmDecline?…` and the request is discarded.

## Finding 1 — an account with roles in two journals is taken out of the journal

Weight: minor. The flow completes; the user ends up on the site-level
profile instead of the journal they were working in.

Steps, on a fresh install with two journals A and B (the site's default
two languages, English and French):

1. Create a user with the Author role in journal A and in journal B.
2. Sign in as that user at journal A's Login page.
3. Open the user menu › "Edit Profile" › "Contact" (address
   `index.php/A/user/profile#contact`). Replace "Email address" with a new
   address and press "Save".
4. Open the message "Confirm account contact email change request" sent
   to the old address and, in the same browser, open its "confirm" link.
5. Repeat step 3 with another address, and this time open the "reject"
   link and press "Confirm Decline Invitation".

Expected (before the change): both links read
`index.php/A/invitation/accept?…` / `…/decline?…` and both land on
`index.php/A/user/profile#contact`, inside journal A, with "Your changes
have been saved.".

Observed: the links read `index.php/index/invitation/accept?id=…&key=…`
and `index.php/index/invitation/decline?id=…&key=…`. "confirm" answers
302 → `index/en/invitation/accept` → 302 `index/en/user/profile/contact`
→ 200 `index.php/index/en/user/profile#contact`: the page title is
"Profile | Open Journal Systems" with the site's header ("Journals", "Open
Journal Systems"), not journal A's. The Contact tab shows the new address
and "Your changes have been saved.". "reject" and "Confirm Decline
Invitation" land on the same site-level page with the old address kept.

Control in the same run: an account with a role in one journal only lands
on `index.php/{journal}/user/profile#contact` on "confirm", "reject" and a
signed-out "confirm" followed by sign-in, because
`pages/user/ProfileHandler.php:71-73` forwards a one-journal account from
the site-level profile to its journal (the forward `aeac6f75cf` repaired).
An account with two journals is not forwarded.

Cause: `InvitationHandler::getActionUrl()` and
`ChangeProfileEmailInviteRedirectController` now take the path from
`$invitation->getContextPath()`, and the email-change invitation never
receives the journal it was requested in. Passing the request's context id
to `initialize()` in `BaseProfileForm::execute()`, or falling back to the
request's context when the invitation has none, would restore the landing.

## Finding 2 — a "reject" link mailed before the upgrade answers a blank error page

Weight: low, transitional. It concerns email-change requests that are
still pending when a site moves to the new code (the links live for the
invitation's expiry period), on a site where the journal and the site
differ in the number of languages (the default install: a two-language
site, a journal created with one language).

Steps, on the same install with a journal J that has one language:

1. As a user with a role in J only, request an email change (Finding 1,
   step 3, at `index.php/J/user/profile#contact`).
2. Take the "reject" link from the message. The new code mails
   `index.php/index/invitation/decline?id=…&key=…`; the code before the
   change mailed `index.php/J/invitation/decline?id=…&key=…` for the same
   request (spec U03, code map, MAIL-003). Open the second form, which is
   what a message sent before the upgrade contains (the OPS control above
   mails exactly this shape). The OJS fleet cannot mail a pre-change link,
   so the address was rewritten by hand: `index` replaced by `J`, id and
   key untouched.
3. The "Decline Invitation" page opens (200). Press "Confirm Decline
   Invitation".

Expected (before the change): the form posts to
`index.php/J/invitation/confirmDecline?…`, the request is discarded and
the browser lands on Profile › Contact with "Your changes have been
saved.".

Observed: the form's address reads
`index.php/index/invitation/confirmDecline?id=…&key=…` (the site's path,
no language segment, because the language list still comes from the
journal being served). The chain is `POST 302
/index.php/index/invitation/confirmDecline?…` → `GET 500
/index.php/index/en/invitation/confirmDecline?…`: a blank page, no title,
no text. The server log has "PHP Fatal error: Uncaught
Symfony\Component\HttpKernel\Exception\MethodNotAllowedHttpException in
lib/pkp/pages/invitation/InvitationHandler.php:70". Profile › Contact
afterwards still shows the pending notice; the request was not discarded.

Control in the same run: the link as the new code mails it
(`index/invitation/decline?…`) declines normally and lands on J's Contact
tab.

Cause: `InvitationActionRedirectController::declineHandle()` builds the
form address with `$this->invitation->getContextPath()` (`index`) while
the dispatcher decides about the language segment from the served journal
(one language, so none). The two-language site then answers the POST with
a redirect that inserts `/en/`, the browser follows with a GET, and
`InvitationHandler::confirmDecline()` refuses anything but a POST. The
mirror case (a two-language journal on a one-language site) was read, not
driven. The pre-change "confirm" link holds no POST in its chain and was
not driven.
