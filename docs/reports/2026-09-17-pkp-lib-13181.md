# Email-change links take a user with roles in two journals out of their journal, and a "reject" link mailed before the upgrade ends on a blank error page

Regression. OJS at `7c8d69af3e` (lib/pkp `14473fe784`), OMP at
`c6a132892` and OPS at `4bb66b1469` (lib/pkp `1bcd4dd55f`); introduced by
pkp/pkp-lib#13181 (`4d9ec3cbd0` and `aeac6f75cf`, 2026-09-16).
stable-3_5_0: shows both findings too, at OJS `63c7e555cc` (lib/pkp
`9ce915e07e`, backports `ac6b031624` and `78d439c8b8`). Tracked in
`docs/tracking/ci-triage.md` "Open regressions". Temporary: delete once
acted on.

Found 2026-09-17 on OJS; OMP and OPS received the change on 2026-09-18
and show the same. One report for both lines.

## Summary

When a user replaces their email address under Profile › Contact, the
app mails the old address a message with a "confirm" and a "reject" link.
Since pkp-lib#13181 both links point at the site instead of the journal
the user was in. A user with roles in two journals therefore lands on the
site-level Profile page after either link (Finding 1). And a "reject"
link mailed before the upgrade, which still names the journal, now ends
on a blank error page and the change request stays pending (Finding 2).
The fix the issue asked for, invitation links naming the right journal,
works: role invitations and reviewer access links were driven and hold.

## Finding 1 — an account with roles in two journals is taken out of the journal

### Impact

Anyone with roles in two or more journals of a site (reviewers and
editors who serve several journals are the usual case) who changes their
email address. The change itself goes through, but "confirm" and "reject"
both leave them on the site's Profile page, with the site's header and
none of the journal's navigation, and they have to find their way back.
A user with a role in one journal only is not affected. Minor: nothing is
lost, one wrong landing per email change.

### Steps to reproduce

Preconditions: a fresh install with its default two languages (English,
French) and two journals A and B; a user with the Author role in both.

1. Sign in as that user on journal A's Login page.
2. Open the user menu › "Edit Profile" › "Contact"
   (`index.php/A/user/profile#contact`). Replace "Email address" with a
   new address and press "Save".
3. Open the message "Confirm account contact email change request" sent
   to the old address and, in the same browser, open its "confirm" link.
4. Repeat step 2 with another address. This time open the message's
   "reject" link and press "Confirm Decline Invitation".

Expected (the behavior before the change): both links read
`index.php/A/invitation/accept?…` and `…/A/invitation/decline?…`, and
both land on `index.php/A/user/profile#contact` inside journal A with
"Your changes have been saved.".

Observed, on OJS, OMP and OPS: the links read
`index.php/index/invitation/accept?id=…&key=…` and
`index.php/index/invitation/decline?id=…&key=…`. "confirm" ends on
`index.php/index/en/user/profile#contact`, page title "Profile | Open
Journal Systems", with the site's header ("Journals", "Open Journal
Systems") instead of journal A's; the Contact tab shows the new address
and "Your changes have been saved.". "reject" followed by "Confirm
Decline Invitation" lands on the same site-level page with the old
address kept. The redirect chain of "confirm":

```
302 index/en/invitation/accept
302 index/en/user/profile/contact
200 index.php/index/en/user/profile#contact
```

Control: a user with a role in one journal only lands on that journal's
Contact tab on "confirm", on "reject" and on a signed-out "confirm"
followed by sign-in, because the site-level profile page forwards a
one-journal account to its journal. A two-journal account is not
forwarded.

### Cause

The email-change invitation is created without a journal
(`classes/user/form/BaseProfileForm.php:76-78`:
`$invite->initialize($user->getId())`, no context id). After the change,
`InvitationHandler::getActionUrl()` and
`ChangeProfileEmailInviteRedirectController` build the links and the
redirect from `$invitation->getContextPath()`, which answers `index` for
an invitation with no context, wherever it was requested. Before the
change they used the journal of the request.

### Proposed fix

A proposal; the team decides.

1. Give the email-change invitation the journal it was requested in:
   pass the request's context id to `initialize()` in
   `BaseProfileForm::execute()`. One line; the invitation then carries the
   journal like a role invitation does, and the links and landings follow.
   A change requested from the site-level profile stays site-level.
2. Or, in `getActionUrl()` and the redirect controller, fall back to the
   request's context when the invitation has none. Keeps the stored
   invitation as it is, but the link then depends on where the mail was
   built, which is what #13181 set out to remove.

## Finding 2 — a "reject" link mailed before the upgrade answers a blank error page

### Impact

Users whose email-change request is still pending when the site moves to
the new code, on a site where the journal has fewer languages than the
site (the default install: a two-language site, a one-language journal).
The "reject" link in their message still names the journal. Opening it
shows the "Decline Invitation" page as before, but pressing "Confirm
Decline Invitation" gives a blank page with no title and no text, and the
request stays pending under Profile › Contact. The user cannot reject the
change from that message. Minor and transitional: it concerns links
mailed before the upgrade, which live for the invitation's expiry
period; a link the new code mails declines normally.

### Steps to reproduce

Preconditions: the same install; a journal J created with one language;
a user with a role in J only.

1. Sign in as that user and request an email change under Profile ›
   Contact (`index.php/J/user/profile#contact`).
2. Open the message and copy its "reject" link. The new code mails
   `index.php/index/invitation/decline?id=…&key=…`; in the address
   replace `index` with `J`, keeping `id` and `key`. That is the link a
   message sent before the upgrade contains (the code before the change
   mailed `index.php/J/invitation/decline?…` for the same request).
3. Open the edited link. The "Decline Invitation" page opens. Press
   "Confirm Decline Invitation".

Expected (the behavior before the change): the form posts to
`index.php/J/invitation/confirmDecline?…`, the request is discarded, and
the browser lands on Profile › Contact with "Your changes have been
saved.".

Observed, on OJS, OMP and OPS: the form's address reads
`index.php/index/invitation/confirmDecline?id=…&key=…` (the site's path,
no language segment). Pressing the button gives a blank page:

```
POST 302 /index.php/index/invitation/confirmDecline?…
GET  500 /index.php/index/en/invitation/confirmDecline?…
```

The server log has:

```
PHP Fatal error: Uncaught Symfony\Component\HttpKernel\Exception\MethodNotAllowedHttpException
in lib/pkp/pages/invitation/InvitationHandler.php:70
```

Profile › Contact afterwards still shows the pending notice.

Control: the link as the new code mails it (`index/invitation/decline?…`)
declines normally and lands on J's Contact tab.

### Cause

`InvitationActionRedirectController::declineHandle()` builds the form's
address from `$this->invitation->getContextPath()` (`index`), while the
dispatcher decides whether the address needs a language segment from the
journal being served (J, one language, so none). The site has two
languages, so it answers the POST with a redirect that inserts `/en/`;
the browser follows with a GET, and `InvitationHandler::confirmDecline()`
accepts only POST.

### Proposed fix

A proposal; the team decides.

1. Build the decline form's address from the request that serves the
   page rather than from the invitation, so the form posts back to the
   journal and language the page was opened in. The page is already
   being served there; the invitation's own context only matters for the
   links the mail carries. Small, and it covers the mirror case (a
   two-language journal on a one-language site), which was read but not
   driven.
2. Or, when the invitation's context path differs from the served one,
   redirect the "decline" GET to the invitation's own path first, so the
   form and its POST share one context. Costs one extra redirect on
   every old-shape link.

Finding 1's option 1 does not close this one: a message mailed before the
upgrade has no journal on its invitation either way.
