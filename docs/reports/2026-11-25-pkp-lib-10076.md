## Summary

An assistant assigned to a submission's review stage (a Funding
coordinator, or a journal's own assistant role with the review stage)
opens the review round and finds no declined or cancelled reviewers in
the "Reviewers" table. A round whose reviewers all declined or were
cancelled reads "No Items", and their dashboard row shows no indicator
for those reviewers. The editor on the same round sees every reviewer.
Up to 3.4 the assistant's reviewers grid listed them all.

The assistant still has "Add Reviewer", so they can invite again someone
who just declined, and cannot reinstate a cancelled reviewer or resend
a request to one who declined. Nothing on the page says rows are
missing. The editor's view and the "Activity Log" still show what
happened.

## Impact

- **Lost**: the round's history, on the screen where the assistant
  manages reviewers. Nothing is deleted, and nobody is told that rows
  are hidden.
- **Who**: every assistant-role participant assigned to a review stage,
  on any round with a declined or cancelled reviewer. On those rounds
  their dashboard row reads "All reviews are confirmed and a decision is
  needed." with nothing beneath it.
- **Way round**: an editor reads the table for them, or the assistant
  reads the declines and cancellations in the "Activity Log". Neither
  lets the assistant reinstate or resend.

Medium: assistants who run reviewer invitations are misled about who has
already been asked, silently, and lose the reinstate and resend actions
3.4 gave them. There is a way round, and nothing is lost. It would be
high if journals commonly gave assistants the review stage by default;
the default role set gives it only to the Funding coordinator.

## Cause

The "Reviewers" table on the workflow page and the activity cell of the
dashboard both list `submission.reviewAssignments`, which the submission
map builds in `PKP\submission\maps\Schema::getPropertyReviewAssignments()`
(`classes/submission/maps/Schema.php:630`). That method skips a declined
or cancelled assignment unless `canSeeAllReviewAssignments()` returns
true. That check (`Schema.php:747`) only accepts `ROLE_ID_MANAGER`,
`ROLE_ID_SUB_EDITOR` and `ROLE_ID_SITE_ADMIN` among the user's roles at
the assignment's stage. An assistant assigned to the review stage holds
`ROLE_ID_ASSISTANT` there, so their list drops those rows.

Before `pkp/pkp-lib#10076`, the same method dropped declined and
cancelled assignments for everyone (an `@todo` "for now, only show
reviews that haven't been declined or cancelled"). That filter did no
harm while the reviewers table was the legacy grid
(`PKPReviewerGridHandler::loadData()`, every assignment of the round,
assistants authorized for every operation but creating and enrolling
reviewers). It started to show when `pkp/pkp-lib#7495` made the Vue
workflow page the default (October 2024), and when `pkp/pkp-lib#10766`
removed the old page (March 2025). `pkp/pkp-lib#10076` restored the rows,
as its issue asked, "for editors" only, and its role list is what keeps
assistants out today.

Reach:

- The workflow page's "Reviewers" table (`ReviewerManager`), OJS and
  OMP (walked); OMP's internal review stage too (code, the same check by
  stage).
- The dashboard's review activity cell (walked; spec U23 A7).
- OPS has no review stage.
- The legacy grid operations still authorize assistants for "Reinstate
  Reviewer", "Resend Review Request" and the others (code), so the
  actions work once the rows are listed (walked with the fix: the rows
  came with "More Actions").

## Proposed fix

Add the assistant role to the stage-scoped check, so an assistant
assigned to the assignment's stage sees what the reviewers grid showed
them up to 3.4
([fix.diff](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-10076/fix.diff)):

```diff
-        // only managers, sub-editors, or site admins at THIS stage can see
-        // the declined/cancelled assignments for that stage
-        if (array_intersect($roles, [Role::ROLE_ID_MANAGER, Role::ROLE_ID_SUB_EDITOR, Role::ROLE_ID_SITE_ADMIN])) {
+        // managers, sub-editors, site admins and assistants at THIS stage can see
+        // the declined/cancelled assignments for that stage, as in the reviewers grid before
+        if (array_intersect($roles, [Role::ROLE_ID_MANAGER, Role::ROLE_ID_SUB_EDITOR, Role::ROLE_ID_SITE_ADMIN, Role::ROLE_ID_ASSISTANT])) {
```

The check keeps what `pkp/pkp-lib#10076` built: it stays per stage, so
an assistant assigned only to copyediting gets nothing new, and authors
and reviewers never hold one of these roles at the stage. The assistant
already sees the reviewers' names on the active rows, so the declined
and cancelled rows expose nothing new. Tried on `main`, OJS and OMP:
the Funding coordinator then sees both rows with "More Actions", their
dashboard row carries the two indicators, and the author's view is
unchanged.

**Alternatives**

- Drop the role check and show every assignment to whoever receives the
  list: it would reach authors, whose list goes through the same map.
- A product decision that assistants should not see them: it would
  then also need the legacy grid operations to refuse assistants, and a
  line on the page saying rows are hidden.

**What goes with it**

- A unit test of `canSeeAllReviewAssignments()` per role, in pkp-lib.
- The same one-line change on `stable-3_5_0`, where the method is the
  same (`Schema.php:742` there).
- No stored data to repair.

Small: one role in one shared check, and a unit test.
