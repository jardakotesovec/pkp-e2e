predefined-message list left blank is now sent, as the stage's

## Finding 1 — No "Discussion (…)" template to fall back on: the message fails on the server

- **Severity** medium
- **Effort** small
- **Kind** intention gap
- **Crash** server
- **Affects**
  - main: OJS, OMP, OPS (walked on OJS; OMP and OPS by code, shared code)

### Impact

- **Lost**: the typed message. The window stays open with it and says
  nothing; on "Assign" the person is assigned anyway, so the editor may
  believe the message went out.
- **Who**: an editor or manager on a stage whose "Discussion (…)"
  template a manager deleted under Settings › Workflow › "Tasks and
  Discussions" (that screen allows it). A fresh install has the template
  on every stage, a press's Internal Review included once omp#2487 merges.
- **Way round**: choose another predefined message and replace its text,
  or open the discussion from the stage's discussions panel.

Medium: a task fails with a server error, in a state that is rarely met
(a deleted default), and there is a way round on screen. It would be
high if a stage could lose its template without a manager deleting it.

### Steps to reproduce

Preconditions:
- A fresh OJS install with a journal, its Journal Manager, a Section
  editor and an author.
- A submission in the Submission stage.

1. Sign in as the Journal Manager and open Settings › Workflow › "Tasks
   and Discussions".
2. In "Submission Stage", open the row menu of "Discussion (Submission)"
   and choose "Delete", then "OK".
3. Open the submission's Submission stage.
4. In "Participants", open the author's row menu and choose "Notify".
5. Leave "Choose a predefined message to use, or fill out the form
   below." on its blank entry, type "Please check the files." in
   "Message" and press "Notify".
6. Press "Assign", choose the Section editor, leave the list blank, type
   a message and press "OK".

**Expected**: the message is sent, as it is on a stage that still has
its "Discussion (…)", or the window says why it cannot be.

**Observed**: both windows stay open as filled with no notice; no email,
no discussion. The Section editor is assigned all the same (the row
shows after a reload). Both requests answer 500:

```
PHP Fatal error:  Uncaught Error: Call to a member function promote() on null in lib/pkp/controllers/grid/users/stageParticipant/form/PKPStageParticipantNotifyForm.php:194
```

Control: on a journal with "Discussion (Submission)" in place, the same
steps send the message as "Discussion (Submission)".

### Cause

`PKPStageParticipantNotifyForm::sendMessage()` replaces a blank or
refused template with
`Template::withKeys(Repo::editorialTask()->getDiscussionTemplateKeys(), $contextId)->withStageId($this->_stageId)->withType(EditorialTaskType::DISCUSSION->value)->first()`
and calls `$template->promote($submission)` without checking that one
was found. A deleted default leaves the stage with nothing.

### Proposed fix

A proposal; the team decides.
1. Guard the null: when no template is found, refuse with a form error
   ("Choose a predefined message…") instead of the 500, so the editor
   knows nothing was sent. A few lines in `sendMessage()` (or in the
   form's validation, before the assignment is saved).
2. Or send without a template: the mailable from the typed message, the
   discussion titled with a localized generic string. More code, since
   `TemplateVariables` is built from the template.

Small: one guard in one method, with a test that deletes the default
and sends.

## Finding 3 — On a press upgraded from 3.5, Internal Review's "Discussion (Review)" fills "Message" with a sentence about emails

- **Severity** low
- **Effort** small
- **Kind** intention gap
- **Affects**
  - main: OMP, presses that existed before the upgrade from 3.5 (driven through the migration)

### Impact

- **Lost**: nothing; the sender sees "This email is sent when a
  discussion is created or replied to in the review stage." in "Message"
  and types over it. Sent unchanged, the recipient reads that sentence.
- **Who**: editors and managers of every press upgraded from 3.5, on
  the Internal Review stage's "Assign", "Notify" and "Add" windows when
  they choose "Discussion (Review)"; the template's text under Settings
  shows the same sentence.
- **Way round**: a manager edits the template's text once under
  Settings › Workflow › "Tasks and Discussions".

Low: wording that misleads while the message still goes out as typed.

### Steps to reproduce

Preconditions:
- An OMP 3.5 install with a press, upgraded to `main` with pkp/omp#2487
  merged (the evidence drove the migration on the test install instead).
- A submission sent to "Internal Review".

1. Sign in as the Press Manager and open the submission's "Internal
   Review" stage.
2. In "Participants", open the author's row menu and choose "Notify".
3. Choose "Discussion (Review)" in "Choose a predefined message to use,
   or fill out the form below.".

**Expected**: "Message" reads "Please enter your message.", as on a new
press and on every other stage's "Discussion (…)".

**Observed**: "Message" reads "This email is sent when a discussion is
created or replied to in the review stage." (French: "Ce courriel est
envoyé lorsqu'une discussion ou un message sont ajoutés à l'étape de
l'évaluation.").

### Cause

`APP\migration\upgrade\v3_6_0\I12593_DiscussionInternalReviewTemplate::up()`
writes the template's `description` from
`__('mailable.discussionReview.description')`, the mailable's admin
description. The registry row omp#2487 adds for new presses uses
`emails.discussion.body` ("Please enter your message."), and
`I12593_EmailToTaskTemplates` gave the other stages the 3.5 email text,
which is the same. The Participants panel and the "Add" window fill
"Message" from `description`.

### Proposed fix

In the migration, take `__('emails.discussion.body', [], $locale)` for
`description`, as the registry row does. A one-word change in one file;
the template is only written by this migration, so no stored data needs
repair before the release.

Small: one line, checked by running the upgrade from a 3.5 dump.
