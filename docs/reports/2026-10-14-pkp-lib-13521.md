## 1. An API key made in the unattended browser passes the gate (round 1; ruled out by the team 2026-10-20: API-token requests are not re-authenticated by design)

**Who**: installations with `password_timeout` set, and someone at the
administrator's browser after the confirmation period, as in #928.

**Steps** (default dataset, `[security] password_timeout = 1`,
`api_key_secret` set; OJS, OMP, OPS):

1. Sign in as `admin`, open Administration › Site Settings, answer
   "Confirm Access" with `admin`.
2. Leave the browser untouched for two minutes.
3. In the same tab, from Site Settings, the Security "Save": refused
   ("Your access to Administration has expired…").
4. User menu › "Edit Profile" › "API Key", "Create API Key". It opens
   and makes the key without asking for the password.
5. With that key and no browser cookie (a script, or `curl -H
   "Authorization: Bearer <key>"`): `POST index/api/v1/contexts`
   (a scratch journal), `DELETE index/api/v1/contexts/<its id>`,
   `GET index/api/v1/site`, `GET index/api/v1/jobs/failed/all`.

**Expected**: once the period has run out, nobody at that browser
changes Administration without the password.

**Observed**: step 5 answers 200 to all four: the journal is created and
deleted. The same requests with the tab's cookie, with or without
`?apiToken=<key>`, stay refused (403).

**Cause**: `ReauthenticationRequiredPolicy::effect()` permits an API
request whose session has no user (`isAuthenticatedViaApiToken()`)
before it checks the period. A request with the key and no cookie is
exactly that. The key itself is made by `APIProfileForm`, which the gate
does not cover (Profile is outside Administration). The detection is
sound: a request that carries the administrator's cookie never reaches
the exemption.

**Proposed fix** (not tried; #928 left the token question to the team):
keep the exemption for keys made inside a confirmed period, by making
"Create API Key" ask for Confirm Access while the gate is on. One way is
for `APIProfileForm::execute()`, or the profile handler's API key
operation, to refuse a site administrator whose
`isElevatedSessionActive()` is false. Dropping the exemption instead
would need `isElevatedSessionActive()` to stop reading the session's
user, because without the exemption every administrator key call is
refused even with the gate off (`Validation::isSiteAdmin()` reads the
session).

## 2. Site Navigation Menu items and the site Plugin Gallery stay ungated (round 1; fixed in round 2)

**Steps** (as in 1, steps 1–2, then from the open Site Settings tab):

- Navigation Menus (the items grid): an item's "Remove" (the request
  `index/$$$call$$$/grid/navigation-menus/navigation-menu-items-grid/delete-navigation-menu-item`).
  The menus grid above it (`navigation-menus-grid`), for comparison.
- Plugins › Plugin Gallery: a plugin's "Install"
  (`grid/plugins/plugin-gallery-grid/install-plugin`).

**Observed**: the menus grid answers the "expired" message, as the PR
intends. The items grid's "Remove" deletes the site's menu item
(the dataset's item 7 is gone after re-confirming), in all three apps;
"Add Item" and its save also go through. The Gallery's "Install" passes
authorization and stops only on the gallery feed, which the VM cannot
reach (500 at `PluginGalleryDAO.php:129`, the same inside the period).
No plugin was installed.

**Cause**: `NavigationMenuItemsGridHandler::authorize()` and
`PluginGalleryGridHandler::authorize()` add no
`ReauthenticationRequiredPolicy`. `NavigationMenusGridHandler` and
`AdminPluginGridHandler` now do.

**Proposed fix** (not tried): the PR's own pattern. In
`NavigationMenuItemsGridHandler::authorize()`, add the policy when the
context is the site, as `NavigationMenusGridHandler` now does. In
`PluginGalleryGridHandler::authorize()`, add it when there is no context
(Administration's Plugins tab). Its `installPlugin` and `upgradePlugin`
are Site Administrator operations wherever they are called.

**What goes with it** (team's call): a journal's Website › Plugins
offers the same Site Administrator operations (`upload-plugin`,
`upgrade-plugin`, `delete-plugin` in the journal's plugin grid, and the
journal's Plugin Gallery install), outside Administration and so outside
the gate by #928's scope. Those requests answer the administrator past
the period at the base and at the head alike.

## 3. A manager refused at the newly gated handlers reads "Your access to Administration has expired" (round 1; fixed in round 2)

**Who**: a Journal Manager (any signed-in user who is not the Site
Administrator), on every installation: the gate does not have to be on.
No screen of theirs sends these requests, so they meet it only by
typing or following one of the addresses; they are refused before and
after the PRs, and only the wording changes. Low.

**Steps** (the default dataset, OJS `main`; OMP and OPS the same, with
their own journal path; the gate off, as installed, and again with
`[security] password_timeout = 1`):

1. Sign in as `rvaca` (Journal manager, password `rvacarvaca`).
2. Type into the browser's address bar, one after the other:
   - `/index.php/index/api/v1/announcements`
   - `/index.php/index/api/v1/highlights`
   - `/index.php/index/api/v1/site`
   - `/index.php/index/$$$call$$$/grid/navigation-menus/navigation-menus-grid/fetch-grid`
   - `/index.php/index/$$$call$$$/grid/admin/context/context-grid/fetch-grid`
   - `/index.php/index/$$$call$$$/grid/admin/plugins/admin-plugin-grid/fetch-grid`
   - `/index.php/index/$$$call$$$/grid/admin/languages/admin-language-grid/fetch-grid`
3. Control: `/index.php/index/api/v1/contexts`.

**Expected** (the base, gate on or off): each is refused for the role.
The three API addresses answer 401 with "The current role does not
have access to this operation." (`user.authorization.roleBasedAccessDenied`),
and the four grids answer `"status":false` with the same sentence.

**Observed** (the head, gate on or off): each is still refused, but the
three API addresses answer 403 with "Your access to Administration has
expired. Reload the page and confirm your password to continue."
(`user.confirmAccess.required`), and the four grids show the same
sentence. A Journal Manager has no Administration access to expire, and
no password would let them in. The control reads the same at both
sides (401, "You are not authorized to access the requested resource.",
from `CanAccessSettingsPolicy`, which refuses first).

**Cause**: `ReauthenticationRequiredPolicy` is added before the role
policies (`PKPAnnouncementController` and `HighlightsController` at the
site level, `PKPSiteController`, `NavigationMenusGridHandler` at the
site level, `ContextGridHandler`, `AdminPluginGridHandler`,
`AdminLanguageGridHandler`), and `PKPSessionGuard::isElevatedSessionActive()`
returns false for anyone who is not a Site Administrator, even with the
gate off. So for a manager the policy's refusal comes first, with its
message and, on the API, its 403.

**Proposed fix** (not tried): the policy refuses a user who is not a
Site Administrator without the message or the call-on-deny advice
(`return AuthorizationPolicy::AUTHORIZATION_DENY;` before
`setAdvice()` when `Validation::isSiteAdmin()` is false), so the role
policy's refusal is the one shown, as at the base.

## 4. The site's Navigation Menus API adds and renames site menus past the period (round 2)

**Who**: installations with `password_timeout` set, and someone at the
administrator's browser with Site Settings left open past the
confirmation period, as in #928. Nothing beyond the site's menus is
reached: their titles, their areas and which items they hold.

**Steps** (the default dataset, `[security] password_timeout = 1`;
OJS, OMP, OPS. The default dataset hosts one journal, press or server,
so the site's "Navigation" tab is hidden; the steps read the site's
menus at the menus grid's address instead):

1. Sign in as `admin`. Open Administration › "Site Settings" and answer
   "Confirm Access" with `admin`.
2. Leave the browser untouched for two minutes.
3. From the same page, send the requests the menu window sends on
   "Save" (the window itself does not open at the site level today,
   U08 A4). In the browser console on that page:
   - "Add Menu":
     `fetch('/index.php/index/api/v1/navigationMenus', {method: 'POST', headers: {'Content-Type': 'application/json', 'X-Csrf-Token': pkp.currentUser.csrfToken}, body: JSON.stringify({title: 'r2 Menu', areaName: ''})})`
   - a menu's "Edit" of the site's "User Navigation Menu" (id 1): the
     same with `'/index.php/index/api/v1/navigationMenus/1'`,
     `method: 'PUT'` and `{title: 'r2 Renamed'}`
4. For comparison, from the same page: the menus grid
   (`/index.php/index/$$$call$$$/grid/navigation-menus/navigation-menus-grid/fetch-grid`).
5. Open Site Settings again and answer "Confirm Access". Then open the
   menus grid's address from step 4 in the browser. It answers JSON
   that holds the site's menu titles.

**Expected**: both requests in step 3 are refused with "Your access to
Administration has expired…", as the grid in step 4 is. The site's
menus in step 5 are as before.

**Observed**: at the round-2 head the grid in step 4 is refused as
expected. But step 3 answers 201 and 200, and step 5 lists "r2 Menu"
and "r2 Renamed". Steps 3 and 5 read the same at the base, in all three
apps. At the base the grid in step 4 goes through too, since nothing
is gated there.

**Cause**: `PKPNavigationMenuController::authorize()` adds no
`ReauthenticationRequiredPolicy`. The controller serves the site too
(`$context?->getId() ?? PKPApplication::SITE_CONTEXT_ID` in `add()`,
`edit()` and the reads), and the site-level grid's "Add Menu" and row
"Edit" open `NavigationMenuManagerFormModal` with that API's site
address (`NavigationMenusGridHandler::initialize()`,
`NavigationMenusGridRow`). The PR gates the grid but not the API behind
its window. At the site level the window's first request,
`GET navigationMenus/items`, answers 500 today
(`PKPNavigationMenuService::getAllMenuItems()` takes an `int` and is
given the site's `null`), which is why no window opens (U08 A4). Once
that is fixed, the screen's own "Save" reaches this route.

**Proposed fix** (tried): the PR's own pattern, in
`api/v1/navigationMenus/PKPNavigationMenuController.php`, after
`$this->addPolicy($rolePolicy);`:

```php
if (!$request->getContext()) {
    // Admin requires reauthentication for site-wide actions
    $this->addPolicy(new ReauthenticationRequiredPolicy($request));
}
```

(with `use PKP\security\authorization\ReauthenticationRequiredPolicy;`).
With it applied on the round-2 head, step 3 and the window's
`GET items` answer 403 with "Your access to Administration has
expired…" in OJS, OMP and OPS, and the site's menus stay unchanged. A
`POST` sent after re-confirming answers 201. Read in the code, not
driven: a journal's own Navigation tab is untouched, because the gate
is added only without a context; and a Journal Manager meets the role
refusal first, because the gate comes after the role policies, as in
finding 3's fix.
