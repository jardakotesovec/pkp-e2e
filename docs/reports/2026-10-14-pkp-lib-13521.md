## Summary

pkp-e2e#928 reports that once the Site Administrator's confirmation
period has run out, an Administration page left open still saves Site
Settings, creates and removes journals, manages Languages and Plugins,
and retries or deletes failed jobs, without the password. The PRs fix
every one of these. With the PRs, on PKP's default dataset in OJS, OMP
and OPS, #928's steps end differently. The Security "Save" answers "Your access
to Administration has expired. Reload the page and confirm your password
to continue." and the value stays. "Remove" is refused with the same
text, and the journal stays listed. "Create Journal" opens no dialog. The same 13 requests
that Administration's pages send (Site Settings, its theme, Hosted
Journals, Languages, Plugins, the jobs lists and "Retry all", site
Navigation Menus, site announcements, highlights and announcement types)
all go through at the base after the period, and are all refused at the
head. Inside a confirmed period they all go through, and with the gate
off they go through without any prompt. A Journal Manager's own
settings save as before.

Three things the PRs leave:

1. Someone at the unattended browser can still change Administration
   without the password, by making an API key on their own profile page
   and sending the request with that key. The PRs let every API-key
   request through the gate, and making a key does not ask for the
   password.
2. Two grids on Administration pages are still ungated: the site's
   Navigation Menu items (Site Settings › Navigation Menus, the second
   grid) and the site's Plugin Gallery (install and upgrade). The PRs
   gate the grids beside them.
3. A Journal Manager who sends one of the newly gated site-level
   requests is now refused with "Your access to Administration has
   expired…", gate on or off. No screen of theirs sends one; the
   refusal itself is unchanged.

From the tests' side the PRs are safe to merge for what they change:
nothing that worked before breaks. Findings 1 and 2 are what still
separates them from #928's intention. The suites at the PR heads are red
only on OMP U68 S5, which OMP's own `main` shows too (Evidence).

## 1. An API key made in the unattended browser passes the gate

**Who**: installations with `password_timeout` set, and someone at the
administrator's browser after the confirmation period, as in #928.

**Steps** (default dataset, `[security] password_timeout = 1`,
`api_key_secret` set; OJS, OMP, OPS):

1. Sign in as `admin`, open Administration › Site Settings, answer
   "Confirm Access" with `admin`.
2. Leave the browser untouched for two minutes.
3. In the same tab, from Site Settings, the Security "Save": refused
   ("Your access to Administration has expired…").
4. User menu › "Edit Profile" › "API Key", "Create API Key". It opens
   and makes the key without asking for the password.
5. With that key and no browser cookie (a script, or `curl -H
   "Authorization: Bearer <key>"`): `POST index/api/v1/contexts`
   (a scratch journal), `DELETE index/api/v1/contexts/<its id>`,
   `GET index/api/v1/site`, `GET index/api/v1/jobs/failed/all`.

**Expected**: once the period has run out, nobody at that browser
changes Administration without the password.

**Observed**: step 5 answers 200 to all four: the journal is created and
deleted. The same requests with the tab's cookie, with or without
`?apiToken=<key>`, stay refused (403).

**Cause**: `ReauthenticationRequiredPolicy::effect()` permits an API
request whose session has no user (`isAuthenticatedViaApiToken()`)
before it checks the period. A request with the key and no cookie is
exactly that. The key itself is made by `APIProfileForm`, which the gate
does not cover (Profile is outside Administration). The detection is
sound: a request that carries the administrator's cookie never reaches
the exemption.

**Proposed fix** (not tried; #928 left the token question to the team):
keep the exemption for keys made inside a confirmed period, by making
"Create API Key" ask for Confirm Access while the gate is on. One way is
for `APIProfileForm::execute()`, or the profile handler's API key
operation, to refuse a site administrator whose
`isElevatedSessionActive()` is false. Dropping the exemption instead
would need `isElevatedSessionActive()` to stop reading the session's
user, because without the exemption every administrator key call is
refused even with the gate off (`Validation::isSiteAdmin()` reads the
session).

## 2. Site Navigation Menu items and the site Plugin Gallery stay ungated

**Steps** (as in 1, steps 1–2, then from the open Site Settings tab):

- Navigation Menus (the items grid): an item's "Remove" (the request
  `index/$$$call$$$/grid/navigation-menus/navigation-menu-items-grid/delete-navigation-menu-item`).
  The menus grid above it (`navigation-menus-grid`), for comparison.
- Plugins › Plugin Gallery: a plugin's "Install"
  (`grid/plugins/plugin-gallery-grid/install-plugin`).

**Observed**: the menus grid answers the "expired" message, as the PR
intends. The items grid's "Remove" deletes the site's menu item
(the dataset's item 7 is gone after re-confirming), in all three apps;
"Add Item" and its save also go through. The Gallery's "Install" passes
authorization and stops only on the gallery feed, which the VM cannot
reach (500 at `PluginGalleryDAO.php:129`, the same inside the period).
No plugin was installed.

**Cause**: `NavigationMenuItemsGridHandler::authorize()` and
`PluginGalleryGridHandler::authorize()` add no
`ReauthenticationRequiredPolicy`. `NavigationMenusGridHandler` and
`AdminPluginGridHandler` now do.

**Proposed fix** (not tried): the PR's own pattern. In
`NavigationMenuItemsGridHandler::authorize()`, add the policy when the
context is the site, as `NavigationMenusGridHandler` now does. In
`PluginGalleryGridHandler::authorize()`, add it when there is no context
(Administration's Plugins tab). Its `installPlugin` and `upgradePlugin`
are Site Administrator operations wherever they are called.

**What goes with it** (team's call): a journal's Website › Plugins
offers the same Site Administrator operations (`upload-plugin`,
`upgrade-plugin`, `delete-plugin` in the journal's plugin grid, and the
journal's Plugin Gallery install), outside Administration and so outside
the gate by #928's scope. Those requests answer the administrator past
the period at the base and at the head alike.

## 3. A manager refused at the newly gated handlers reads "Your access to Administration has expired"

The journal manager `manager.maya` (campaign seed), from her journal's
settings page, sends `GET index/api/v1/announcements`, `…/highlights`,
`…/site`, or the site Navigation Menus, Hosted Journals, Plugins or
Languages grid. The gate can be on or off. She is refused, as at the
base, but with "Your access to Administration has expired. Reload the
page and confirm your password to continue." (403 on the API) instead
of the role refusal. No screen of hers sends these requests. The cause:
the policy runs before the role check and refuses everyone but a Site
Administrator, so its message comes first. A possible fix (not tried):
the policy returns its plain refusal, without the message or the
call-on-deny advice, when the user is not a Site Administrator. Low.

## Other observations (no change asked)

- The `HasRoles` change (`$context?->getId()`) also makes the site
  Highlights save work for an administrator inside the period (`POST
  index/api/v1/highlights` 200 and the list shows it, in all three
  apps). That is U11 A5's crash (pkp-e2e issue report
  `docs/issues/U11-A5-site-highlights-cannot-be-saved.md`), its
  "`$context?->getId()` alone" alternative, read through the API only
  (the Site Settings › Highlights screen was not walked). U11 A5 needs
  re-checking at the merge.
- Hosted Journals' "Edit" dialog and the settings wizard opened after
  "Create Journal" save to `<journal>/api/v1/contexts/<id>`, under the
  journal's path, which the PRs leave ungated (managers share it), as
  #928 proposed.
- A refused "Remove" leaves its "Confirm" dialog open until it is
  closed, as #928 foresaw.
- The PRs add no unit test; #928 suggested one for the policy's answer
  to an API and a grid request.
