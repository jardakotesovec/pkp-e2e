# An upgrade from 3.3 can replace a journal's DOI prefix with an old leftover value, silently

- **Severity** low
- **Effort** small
- **Kind** intention gap
- **Affects**
  - main: OJS, OMP, OPS (once `pkp/pkp-lib#13481` is merged; today the upgrade stops there with an error)
  - 3.5: OJS, OMP, OPS
  - 3.4: none (code; `insert()` is unchanged there, so the upgrade stops with the error)
  - 3.3: none (code; the step belongs to the upgrade to 3.4)
- **Introduced** `pkp/pkp-lib#12082` for `pkp/pkp-lib#11663` · [3604626745](https://github.com/pkp/pkp-lib/commit/3604626745f08043094b910df1c24d5d1d0ed2aa) · 2025-11-28 · Erik Hanson (ewhanson); its port to `main` is `pkp/pkp-lib#13481`, head [7ea38251bd](https://github.com/pkp/pkp-lib/commit/7ea38251bdb9cba920456c4d3140f2f801abaed3), open
- **Upstream** none found for the wrong prefix (2026-10-09); `pkp/pkp-lib#11663` (open) is the stopped upgrade that the change above fixes
- **Tracked in** ci-triage companion row `i11663-main` · Temporary: delete once acted on
- **Checked** 2026-10-09 (the commits in Evidence)
- **Model** claude-opus-5-5

## Summary

A journal, press or preprint server upgraded from 3.3 can come out
with a DOI prefix that is not the one set in its DOI plugin. It happens
when the journal's settings table already holds an old "doiPrefix"
entry with another value: the upgrade keeps that entry and drops the
plugin's prefix. The upgrade reports success, Settings › Distribution ›
"DOIs" shows the old prefix, and every DOI assigned from then on is
made with it. DOIs assigned before the upgrade are not changed.

Before the fix for `pkp/pkp-lib#11663`, such an install could not
upgrade at all: the upgrade stopped on the entry with a database error.
The fix lets it through by keeping whatever the entry holds. That is
right when the entry equals the plugin's prefix, and wrong when it
differs.

What writes such an entry is not known, so neither is how many installs
hold one with a different value. The proposal is one changed call in
the open `main` PR, and the same on 3.5, so that the plugin's prefix
wins.

## Impact

- **Lost**: the DOI prefix the journal used on 3.3, replaced without
  a message. Whether a registration agency accepts a deposit under the
  leftover prefix was not checked.
- **Who**: the manager of a journal, press or server upgraded from 3.3
  to 3.5.0-2 or later, or to `main` once the PR is merged. An install
  already on 3.4 or later has passed this step and is not touched. The
  install of `pkp/pkp-lib#11663` held a leftover entry; whether its
  value differed from the plugin's is not known.
- **Way round**: type the right prefix into "DOI Prefix" under Settings ›
  Distribution › "DOIs" and save; the DOIs assigned before the upgrade
  still show it. A DOI assigned with the wrong prefix is corrected by
  hand on the "DOIs" page.

Low, because no install is known to hold a leftover entry that differs
from its plugin's prefix. It is medium as soon as one is found: new
DOIs then get a wrong prefix and nothing says so.

## Steps to reproduce

On a development install of `main` with `pkp/pkp-lib#13481` checked out
in `lib/pkp` (or of `stable-3_5_0`), OJS shown:

1. Load the 3.3 default dataset, database and files (pkp/datasets
   `ojs/stable-3_3_0`; `tools/load.sh stable-3_3_0`).
2. Delete the dataset's usage event log,
   `usageStats/usageEventLogs/usage_events_*.log` in the files
   directory. Otherwise the upgrade stops at its pre-flight check
   ("There are unprocessed log files from more than 1 day ago").
3. Give the journal the settings a 3.3 manager saves under Settings ›
   Website › "Plugins" › "Public Identifier Plugins" › "DOI" ›
   "Settings" ("Articles" ticked, "DOI Prefix" `10.1234`, "Use default
   patterns."), and the leftover entry, which no 3.3 screen writes:

   ```sql
   INSERT INTO plugin_settings (plugin_name, context_id, setting_name, setting_value, setting_type) VALUES
     ('doipubidplugin', 1, 'enabled', '1', 'bool'),
     ('doipubidplugin', 1, 'enableIssueDoi', '0', 'bool'),
     ('doipubidplugin', 1, 'enablePublicationDoi', '1', 'bool'),
     ('doipubidplugin', 1, 'enableRepresentationDoi', '0', 'bool'),
     ('doipubidplugin', 1, 'doiPrefix', '10.1234', 'string'),
     ('doipubidplugin', 1, 'doiSuffix', 'default', 'string'),
     ('doipubidplugin', 1, 'doiIssueSuffixPattern', '', 'string'),
     ('doipubidplugin', 1, 'doiPublicationSuffixPattern', '', 'string'),
     ('doipubidplugin', 1, 'doiRepresentationSuffixPattern', '', 'string');
   INSERT INTO journal_settings (journal_id, locale, setting_name, setting_value, setting_type)
     VALUES (1, '', 'doiPrefix', '10.9999', 'string');
   ```

4. Run `php tools/upgrade.php upgrade`.
5. Sign in as `dbarnes`, open Settings › Distribution › "DOIs" and read
   "DOI Prefix" on the "Setup" tab.
6. Open "DOIs" in the side menu, tick the first article, choose
   "Bulk Actions" › "Assign DOIs" and confirm with "Assign DOIs".

**Expected**: "DOI Prefix" shows `10.1234`, the prefix the journal
used on 3.3, and the new DOI starts with it.

**Observed**: the upgrade ends with "Successfully upgraded to version
3.6.0.0". "DOI Prefix" shows `10.9999`, and the article's new DOI is
`10.9999/mkjjae34` (the part after the slash is made anew each time).

With `10.1234` as the leftover value, or without the second `INSERT`,
"DOI Prefix" shows `10.1234`. On `main` without the PR the upgrade
stops whenever the second `INSERT` was run, with either value, as
`pkp/pkp-lib#11663` reports:

```
ERROR: Upgrade failed: DB: SQLSTATE[23505]: Unique violation: 7 ERROR:  duplicate key value violates unique constraint "journal_settings_unique"
```

A press takes `press_settings` and `press_id` in the second `INSERT`; a
3.3 preprint server takes it as printed, since OPS 3.3 still keeps its
servers in the `journal` tables. Their plugin rows differ in the kinds:
the script in Evidence writes each app's.

## Cause

`PKPI7014_DoiMigration::_migrateDoiSettingsToContext()`
(`lib/pkp/classes/migration/upgrade/v3_4_0/PKPI7014_DoiMigration.php`)
moves the DOI plugin's settings from `plugin_settings` to the context's
settings table: it writes them in one statement (line 208) and then
deletes the plugin's rows (line 241). `pkp/pkp-lib#12082` turned that
statement from `insert()` into `insertOrIgnore()`, and
`pkp/pkp-lib#13481` does the same on `main`.

`insertOrIgnore()` skips every row whose context, locale and setting
name are already in the table (`on conflict do nothing` on PostgreSQL,
`insert ignore` on MySQL). The row that was there stays. The plugin's
value is deleted with the plugin's rows, and it was the only prefix 3.3
read (`DOIPubIdPlugin::getSetting($contextId, 'doiPrefix')`).

The reach:

- The same holds for every name in that statement: where the table
  already has a row of that name, that row's value stays and the
  migrated one is dropped. The names are `enableDois`,
  `doiCreationTime`, `enabledDoiTypes`, `doiPrefix`, `doiSuffixType`
  and the suffix patterns; only `doiPrefix` was run, the others are
  read in the code. Of these, 3.3 has no setting named `enableDois`,
  `doiCreationTime`, `enabledDoiTypes` or `doiSuffixType`.
- A second write to the same table follows (line 238), still a plain
  `insert()`: `enableDois`, `doiCreationTime` and `useDefaultDoiSuffix`
  for each context without an `enableDois` row. A leftover row of one
  of those names would still stop the upgrade there. 3.3 has no setting
  of these names either, and neither PR touches the line; it is left
  alone here too.
- On MySQL and MariaDB `insert ignore` also skips a row that fails for
  another reason than the duplicate, with a warning instead of an error
  (read in Laravel's grammar, not run).

## Proposed fix

Let the migrated value win, with the `upsert()` the same class already
uses for the suffix patterns (`_transferDefaultPatterns()`, line 300):

```diff
-        DB::table($this->getContextSettingsTable())->insertOrIgnore($insertData);
+        DB::table($this->getContextSettingsTable())->upsert($insertData, [$this->getContextIdColumn(), 'locale', 'setting_name'], ['setting_value']);
```

The upgrade still passes on the duplicate, which is what
`pkp/pkp-lib#11663` asked for, and the journal keeps the prefix it
used. For `doiCreationTime` the migrated value is the constant the
method sets (`copyEditCreationTime`, line 117), not a plugin setting.

Tried on OJS, OMP and OPS on top of the PR, on PostgreSQL
([fix.diff](../../shared/playwright/checks/sync/pkp-lib-13481/fix.diff)):
with the steps above "DOI Prefix" shows `10.1234` and the new DOI
starts with it; with `10.1234` as the leftover value, or without the
leftover, the DOI settings come out the same as without the fix. Not
tried on MySQL or MariaDB, where line 300 already runs the same call.

- **Alternatives**: keep `insertOrIgnore()`, which is right only when
  the two values are equal. Or delete the context's rows of these names
  before the insert, which gives the same result in two statements.
- **What goes with it**:
  - The same line on `stable-3_5_0`, where the change is released
    since 3.5.0-2.
  - No repair of installs already upgraded: the plugin's value is gone
    from them, so a migration has nothing to restore.
  - The reporter of `pkp/pkp-lib#11663` can say whether this happens
    in the field, with one query on the 3.3 database:

    ```sql
    SELECT js.journal_id, js.setting_value AS leftover, ps.setting_value AS plugin
    FROM journal_settings js
    JOIN plugin_settings ps ON ps.context_id = js.journal_id
      AND ps.plugin_name = 'doipubidplugin' AND ps.setting_name = 'doiPrefix'
    WHERE js.setting_name = 'doiPrefix' AND js.setting_value <> ps.setting_value;
    ```
  - No test reaches it: pkp's upgrade jobs load datasets without a
    leftover entry.

Small: one line, in the pattern the class already uses, and no data
repair.

## Evidence

- The kept script takes the Steps on PKP's 3.3 default dataset, three
  cases per app (no leftover, the same value, another value), and
  records the upgrade's last line, the DOI settings, the "DOI Prefix"
  box and the DOI that "Assign DOIs" gives:
  `shared/playwright/checks/sync/pkp-lib-13481/upgrade-from-3_3.js`
  (its header has the two commands; `PKP_E2E_LINE=stable-3_5_0` in
  front for 3.5).
- The plugin rows in step 3 are what `LazyLoadPlugin::setEnabled()`
  and `DOISettingsForm::execute()` store on `stable-3_3_0`: every
  field of the form's `_getFormFields()`, an unticked box as `0`. They
  were read in the code; no 3.3 install was run.
- The script also writes a DOI on the first published submission
  before the upgrade (`pub-id::doi`, `10.1234/existing.1`). It reads
  the same after the upgrade in every case: the Summary's "not
  changed".
- Commits. `main`: pkp-lib `2ac457888e` (the PR's base) and
  `7ea38251bd` (the PR's head), in ojs `46e1d9981a`, omp `625e7bf704`,
  ops `dd92d52d0e` (the heads of `pkp/ojs#5917`, `pkp/omp#2500`,
  `pkp/ops#1441`). 3.5: ojs `4342473090` with pkp-lib `771474347e`,
  omp `9c5e24246c` and ops `38b61882d3` with pkp-lib `cf3f984335`;
  these are behind the branch tips, and `git diff` to the tips shows
  no change under `classes/migration` or `dbscripts`.
- 3.4 and 3.3, read in the code: `stable-3_4_0` still calls `insert()`
  (`git show origin/stable-3_4_0:classes/migration/upgrade/v3_4_0/PKPI7014_DoiMigration.php`);
  the migration runs only on an upgrade from before 3.4
  (`dbscripts/xml/upgrade.xml`).
- PostgreSQL only; MySQL and MariaDB not checked. The `insert ignore`
  sentence is read from `MySqlGrammar::compileInsertOrIgnore()`.
- Unverified: where a leftover "doiPrefix" entry comes from. 3.3
  neither reads nor writes one (`git grep doiPrefix` on the
  `stable-3_3_0` branches of ojs and pkp-lib finds the DOI plugin and
  the export plugins, all through the plugin's settings). OJS 2.4.0's
  upgrade deleted the journal-level one
  (`dbscripts/xml/upgrade/2.4.0_update.xml` on `ojs-stable-2_4_8`). The
  thread of `pkp/pkp-lib#11663` did not find it either.
