# A site whose core version a plugin update already overwrote keeps it, and its next upgrade skips that release's steps

- **Severity** medium
- **Effort** medium
- **Kind** intention gap
- **Affects**
  - main: none known (code; the fix leaves stored rows as they are, but no gallery release writes a version above `main`'s core)
  - 3.5: none known (code; the same)
  - 3.4: OJS (walked), OPS (code; the gallery offers Dataverse 3.4.6.2 to OPS 3.4 too)
  - 3.3: none known (code; walked the 3.3.0-23 upgrade of such a site, which has no step it would skip)
- **Introduced** not traced; the core write through a plugin's descriptor is present on every line since at least 3.3 (`Installer::updateVersion()`). The fix PRs `pkp/pkp-lib#13610`–`#13613` stop new cases and leave existing ones as they are
- **Upstream** `pkp/pkp-lib#13608` (open; fix in PRs `pkp/pkp-lib#13610`, `#13611`, `#13612`, `#13613` and `pkp/plugin-gallery#564`, none covering sites already affected)
- **Tracked in** ci-triage "Open regressions" row (pkp-lib#13608) · Temporary: delete once acted on
- **Checked** 2026-10-23, the PR heads and bases (the commits in Evidence)
- **Model** claude-opus-5-5

## Summary

The PRs for `pkp/pkp-lib#13608` work. A plugin install or upgrade no
longer records the plugin's descriptor version as the core version, on
`main`, 3.5, 3.4 and 3.3. Nothing else changes: the plugin's own version
rows, its migrations and the core installer's own version write all
behave as before. No regression was found.

They don't repair sites that have already been hit. An OJS 3.4.0-10
site that updated Dataverse to 3.4.6.2 records core version 3.4.6.2.
When it upgrades to the next 3.4 release (3.4.0-11), the upgrade
compares every step's version range with 3.4.6.2 instead of 3.4.0.10.
It skips `I12140_MissingDecisionConstantsUpdate`, the 3.4.0-11 step
scoped to sites at 3.4.0.10 or older, prints "Successfully upgraded to
version 3.4.0.11", and leaves 3.4.6.2 as the current core version. The
next 3.4 release's own steps, scoped up to 3.4.0.11, will be skipped in
the same way. The site's pages keep announcing "Open Journal Systems
3.4.6.2".

## Impact

- **Lost**: the release's upgrade steps meant for the site's real
  version (in 3.4.0-11, the decision constants repair of
  `pkp/pkp-lib#12140`), and a true version record. The upgrade reports
  success either way.
- **Who**: OJS and OPS 3.4 sites that installed or updated Dataverse to
  3.4.6.2 from the gallery between 2026-09-14 and the gallery change.
  The issue counts several of them in a web search. No other gallery
  release triggers the defect (all 593 releases checked).
- **Way round**: none on screen. An administrator who knows about it
  can fix the `versions` table by hand before upgrading.

Medium: a rarely met state, but the upgrade is silently incomplete. It
would be higher if a later release put a schema or data step there that
the site cannot do without.

## Steps to reproduce

Preconditions: an OJS 3.4 install whose current core version is 3.4.0.10
(a 3.4.0-10 site), at the `stable-3_4_0` code.

1. As the Site Administrator, Settings › Website › Plugins: upgrade a
   plugin whose `upgrade.xml` reads `<install version="3.4.6.2">`
   (Dataverse 3.4.6.2 from the gallery, or any plugin package with such
   a file). The upgrade succeeds.
2. Administration › System Information, or the `versions` table: the
   current core version is 3.4.6.2.
3. Run `php tools/upgrade.php upgrade` with the 3.4.0-11 code.
4. The log lists `I9813…` and `I9822…` but not
   `I12140_MissingDecisionConstantsUpdate`, then "Successfully upgraded
   to version 3.4.0.11". The current core version is still 3.4.6.2.

Without step 1, step 3 runs `I12140…` and the current core version
becomes 3.4.0.11.

## Cause

`Installer::preInstall()` reads the current core version from the
`versions` table. `parseInstallNodes()` then keeps an `<upgrade
minversion maxversion>` block only when that version falls inside its
range, and `updateVersion()` writes the new version only when it is
newer. A recorded 3.4.6.2 is above every 3.4 range and above every 3.4
release, so blocks capped at 3.4.0.x are skipped and nothing is written.
The PRs add `!$this->isPlugin` to `updateVersion()`, which stops the
write, but nothing removes a row an earlier plugin upgrade wrote.

## Proposed fix

Tried on 3.4, at the PR's base (to produce an affected site) and at its
head: `checks/sync/pkp-lib-13608/repair-fix-3_4.diff`. In
`Installer::preInstall()`, for a core upgrade only (`!$this->isPlugin &&
$this->isUpgrade()`), when the recorded core version is newer than the
code's (`VersionCheck::getCurrentCodeVersion()`):

1. delete each core row that is newer than the code and was installed
   within 60 seconds of some `plugins.*` row (a plugin upgrade writes
   both in the same request);
2. mark the newest remaining core row current, and continue the upgrade
   from it.

With the diff, the affected 3.4 site's upgrade logs "drop core version
3.4.6.2 recorded by a plugin upgrade", runs `I12140…`, and ends on
3.4.0.11. An unaffected site's upgrade is unchanged. The time match
keeps the repair away from a site that really ran newer code (a
downgrade, which is unsupported). It belongs in each line's next
release beside the PRs. On `main` and 3.5 it is only a safeguard, since
no gallery release triggers the defect there. Not tried there, and not
tried on MySQL or MariaDB.
