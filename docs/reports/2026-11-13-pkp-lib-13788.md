## Summary

A new command-line tool repairs the author affiliations that the 3.5.0
upgrade migrated wrongly. An administrator runs it once as a dry run,
reads the CSV it writes, then runs it again with `--commit`. It
misjudges two groups of contributors:

1. An organization contributor ("Organization or group", new in 3.6)
   with a ROR ID and no affiliation is listed as "repair", and the
   repair gives it an affiliation that is the organization itself:
   "NSERC" becomes affiliated with "Natural Sciences and Engineering
   Research Council of Canada". The wrong affiliation shows in the
   contributor's form and on the article page, and goes out in DataCite
   deposits.
2. On a site upgraded to 3.5 with 3.5.0-0 or 3.5.0-1, an author whose
   affiliation was entered in two or more languages, matched no ROR
   organization, and had a ROR ID from the old ROR plugin is neither
   repaired nor listed. The CSV has no line for them and no count
   includes them, so the ROR ID the upgrade dropped stays lost and the
   administrator is not told.

Finding 1 needs a site that runs the tool after moving to 3.6 and has
added organizations with a ROR ID by then; the CSV lists them, so an
administrator who reads it closely can exclude them. Finding 2 is a case
the issue names ("upgraded to 3.5 with 3.5.0-5 or earlier", "a ROR ID
entered with the old ROR plugin was ignored"); 3.5.0-0 and 3.5.0-1 were
the current 3.5 releases from June to November 2025.

## Finding 1 — An organization contributor with a ROR ID is "repaired" into its own affiliation

- **Severity** medium
- **Effort** small
- **Kind** intention gap
- **Affects**
  - main: OJS, OMP, OPS (walked on OJS; OMP and OPS code)
  - ore: none (code; no tool)
  - 3.5: none (code; no organization contributors, no ROR ID on a contributor)
  - 3.4: none (code)
  - 3.3: none (code)

### Impact

- **Lost**: a correct public record. The organization gets an
  affiliation that is itself, with its ROR, in its "Edit" form, the
  REST API, the article page's author list and its DataCite record.
  Nothing flags it: its CSV line reads like any other repair.
- **Who**: an administrator on 3.6 who runs the tool, as the issue asks
  of every site upgraded with 3.5.0-5 or earlier, after editors or
  authors have added organization contributors with a "ROR ID" and no
  affiliation. Every such contributor on the site is hit.
- **Way round**: before `--commit`, exclude the lines whose
  `legacy_affiliation` is `{}` with `--exclude=<ids>`. After it, run the
  rollback SQL the tool writes, straight away, or remove the affiliation
  in each organization's "Edit" form.

Medium: a wrong affiliation on public pages and deposits for the
organization contributors of the sites that run the tool on 3.6, with a
way round for an administrator who reads the CSV line by line. It would
be high if sites commonly add organizations with ROR IDs before they
run the tool.

### Steps to reproduce

Preconditions:
- PKP's default test dataset for OJS `main`, with `lib/pkp` at pkp-lib
  `main` (`c09ff30833` or later; OJS `main`'s pointer does not carry
  the tool yet). The dataset's ROR registry copy is complete, as the
  tool requires, and holds NSERC.

1. Sign in as `dbarnes`.
2. Open "Developing efficacy beliefs in the classroom" (submission 7)
   and, under "Publication" in its menu, choose "Contributors".
3. From the OJS root, run `php lib/pkp/tools/repairRorAffiliations.php`
   (the dry run).
4. Press "Add Contributor". Choose "Organization or group", "Organization
   Name" `NSERC`, "Email" `nserc@mailinator.com`, "Country" "Canada",
   "ROR ID" `https://ror.org/01h531d29`, and tick "Author" under
   "Contributor Roles". Leave "Affiliations" empty. Press "Save".
5. Run the dry run again.
6. Run `php lib/pkp/tools/repairRorAffiliations.php --commit`.
7. In "Contributors", press "Edit" on the "NSERC" row and look at
   "Affiliations".

**Expected**: NSERC was added after the upgrade and has none of the
data the upgrade migrated. Step 5 prints what step 3 printed, the CSV
has no line for it, and its "Affiliations" stay empty after step 6.

**Observed**:
- Step 3: `Checked 0 authors with legacy affiliation data.`
- Step 5:

  ```
  Checked 1 authors with legacy affiliation data.
  To repair: 1, excluded: 0, to review manually: 0.
  Report: …/repairRorAffiliations-20261113-122709.csv
  Nothing was changed. Run again with --commit to apply the repair.
  ```

  The CSV's one line is NSERC's (contributor 31):

  ```
  repair,31,8,7,no,{},https://ror.org/01h531d29,[],"[{""ror"":""https://ror.org/01h531d29"",""name"":{}}]"
  ```

- Step 6: `Repaired 1 authors. Metadata already deposited or harvested (e.g. Crossref, DataCite, OAI) for published ones is only corrected after it is redeposited.`
- Step 7: "Affiliations" lists "Natural Sciences and Engineering
  Research Council of Canada" with the ROR link
  `https://ror.org/01h531d29`. The contributor's REST API record
  (`GET …/submissions/7/publications/8/contributors/31`) now holds
  `"affiliations": [{"ror": "https://ror.org/01h531d29", "name": {"en": "Natural Sciences and Engineering Research Council of Canada", "fr_CA": "Conseil de Recherches en Sciences Naturelles et en Génie du Canada"}}]`
  beside `"contributorType": "ORGANIZATION"` and its `rorId`.

### Cause

`tools/repairRorAffiliations.php`, `RepairRorAffiliationsTool::execute()`
(lines 108-114 at `c09ff30833`), collects every author with a non-empty
`affiliation` or `rorId` row in `author_settings`. `classify()` (line
196) takes that `rorId` as the old ROR plugin's (`$plugInRor`). Up to
3.5 the row could only be the plugin's leftover. On `main` it is also a
live property: `schemas/author.json` describes `rorId` as "The ROR ID
for ORGANIZATION contributor type", and the contributor form's "ROR ID"
field (`ContributorForm`, shown only for "Organization or group") saves
it to the same row (`setting_name` `rorId`, empty locale). Nothing in
the row tells the two apart.

For such an organization the tool rebuilds the shape the faulty upgrade
would have left from its legacy `affiliation` rows, of which there are
none: `[['ror' => null, 'name' => []]]` (line 211), which `canonical()`
reduces to `[]`. The organization's current affiliations are `[]` too,
so line 230 takes it as "unchanged since the upgrade" and marks it
`repair`, with the repaired shape `[{ror: <its own ROR>}]` (line 219,
since that ROR is in the registry). `repair()` inserts that row.

Reach:
- Only organizations with no affiliation of their own and a ROR present
  in the registry: with an affiliation, the current shape differs from
  `[]` and the author is skipped (lines 233-238); with a ROR not in the
  registry, the repaired shape is `[]` as well and line 226 skips it.
  Code.
- The row is read wherever `author_affiliations` is: the "Edit" form
  (walked), the REST API (walked), the article page's author list
  (`templates/frontend/objects/article_details.tpl` prints every
  contributor's affiliations; code) and DataCite's creator for an
  organization (`DataciteXmlFilter`, `'affiliations' => $author->getAffiliations()`;
  code). Crossref leaves an organization's affiliations out (code).
- 3.5: its `schemas/author.json` has neither `rorId` nor contributor
  types, so every `rorId` row there is the plugin's (code).

The `rorId` property the tool collides with predates it:
`pkp/pkp-lib#11765` added the form field (2025-11-11) and
`pkp/pkp-lib#12562` the schema entry (2026-04-14).

### Proposed fix

Leave organization contributors out of the authors the tool checks,
where the column exists. They are new in 3.6, so none of them carries
data from the old ROR plugin or the 3.5.0 upgrade. In `execute()`:

```diff
-        $authorIds = DB::table('author_settings')
-            ->whereIn('setting_name', ['affiliation', 'rorId'])
-            ->whereNotNull('setting_value')
+        $authorIds = DB::table('author_settings as aus')
+            ->whereIn('aus.setting_name', ['affiliation', 'rorId'])
+            ->whereNotNull('aus.setting_value')
+            // from 3.6 on, rorId is also an ORGANIZATION contributor's own ROR ID, not data of the old ROR plugin
+            ->when(Schema::hasColumn('authors', 'contributor_type'), fn ($query) => $query
+                ->join('authors as a', 'a.author_id', '=', 'aus.author_id')
+                ->where('a.contributor_type', '<>', 'ORGANIZATION'))
             ->distinct()
-            ->orderBy('author_id')
-            ->pluck('author_id')
+            ->orderBy('aus.author_id')
+            ->pluck('aus.author_id')
             ->all();
```

The `Schema::hasColumn()` guard keeps one file for both branches, which
matters because the issue tells 3.5 sites to download the
`stable-3_5_0` copy; the tool already guards on `Schema::hasTable()`
the same way. The literal `'ORGANIZATION'` avoids a class 3.5 does not
have; a `main`-only copy would write
`ContributorType::ORGANIZATION->getName()`, as
`I857_ContributorRolesTypes` does. Tried with
[`fix.diff`](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13788/fix.diff)
(both findings): the Steps' dry run after the add checks 0 authors and
`--commit` leaves NSERC's "Affiliations" empty, while person
contributors with a plugin ROR on the same install are still repaired
(finding 2's walk); on 3.5 the guard leaves the query as it was.

**Alternatives**:
- A 3.6 upgrade step that renames the plugin's leftover `rorId` rows
  (to a name only the tool reads): it would also end `rorId`'s two
  meanings on `main`, but it is an upgrade migration and a change on
  both branches, for a tool that runs once.
- Skip authors whose `rorId` was written after the upgrade:
  `author_settings` has no date, so the code cannot tell.

**What goes with it**:
- No stored data needs a migration; the tool is new. A site that has
  already run it on 3.6 can use the rollback SQL it wrote, or remove
  the affiliation in each organization's form.
- Left out: a person contributor given a `rorId` through the REST API
  on 3.6 is still read as plugin data. `Author::CONTRIBUTOR_TYPE_FORM_FIELDS`
  keeps `rorId` for persons, but no screen writes it (code).
- Test: the tool has none. The kept check
  [`org-ror.js`](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13788/org-ror.js)
  takes the Steps; a unit test of `classify()` with an organization
  contributor would guard it in pkp-lib.

Small: one query in the tool, tried, no data to repair.

## Finding 2 — Authors of sites upgraded with 3.5.0-0 or 3.5.0-1 keep the lost ROR ID, and the tool does not list them

- **Severity** medium
- **Effort** small
- **Kind** intention gap
- **Affects**
  - main: OJS, OMP, OPS (walked on OJS; OMP and OPS code)
  - ore: none (code; no tool)
  - 3.5: OJS (walked), OMP, OPS (code; their `lib/pkp` pointer does not carry the tool yet)
  - 3.4: none (code)
  - 3.3: none (code)

### Impact

- **Lost**: the author's ROR ID from the old ROR plugin, which the
  upgrade dropped and the tool exists to restore, and the knowledge
  that it is missing. The dry run has no line for the author, no count
  includes them, and the repair leaves them as they are.
- **Who**: sites upgraded to 3.5 with 3.5.0-0 or 3.5.0-1 that used the
  ROR plugin; among their authors, those whose affiliation was entered
  in two or more languages and matches no ROR organization name. Their
  affiliation also stays split into one entry per language.
- **Way round**: none from the tool. An editor can add the ROR in each
  such author's "Affiliations", but nothing says which authors.

Medium: a ROR ID missing from the public record, silently, in a narrow
state (an upgrade in that window, the plugin, affiliations in several
languages). It would be high if many such sites entered their
affiliations in two languages.

**Expected**: all three lost the plugin's ROR in the upgrade, so all
three are listed as `repair` to
`[{"ror":"https://ror.org/01h531d29","name":{}}]`, the shape the fixed

**Observed**, on `main` and on `stable-3_5_0` alike:

```
Checked 3 authors with legacy affiliation data.
To repair: 2, excluded: 0, to review manually: 0.
```

The CSV lists Amina Mansour (2) and Nicolas Riouf (4) as `repair` to
that shape. Alan Mwandenga (1) has no line and is in neither count.

### Cause

`classify()` rebuilds the shape the faulty upgrade left (lines 209-211
at `c09ff30833`), to tell an author nobody has touched since (repair)
from one edited since (review, or skip). For an affiliation that matched
no ROR name it rebuilds one affiliation holding every language,
`[['ror' => null, 'name' => <all languages>]]`. That is what 3.5.0-2 to
3.5.0-5 wrote. 3.5.0-0 and 3.5.0-1 wrote one affiliation per language
instead: their `I7135_CreateNewRorRegistryCacheTables::migrateNonRorAffiliations()`
inserted one `author_affiliations` row per `author_settings` row, until
`pkp/pkp-lib#11675` grouped them by author for 3.5.0-2.

So a multilingual author from those two releases equals neither the
repaired shape (line 226) nor the rebuilt one (line 230), and the tool
takes them as edited since the upgrade. In that branch (lines 233-238)
only a ROR still guessed from a name earns a "review" line; this author
has none (`$matchedRors` is empty), and `continue` drops them.

Reach:
- Multilingual affiliations that matched no ROR name only. A
  single-language one is one row under either release and is repaired
  (walked: Nicolas Riouf); one that matched a ROR name got the same ROR
  rows from every 3.5.0 release (code).
- Authors of those releases with a multilingual affiliation and no
  plugin ROR are dropped the same way, their affiliation left split
  (code). That split is `pkp/pkp-lib#11675`'s fault rather than one the
  issue names; the fix below repairs them too.
- The counts do not show the gap: "Checked" includes such authors, no
  other number does.

### Proposed fix

Recognise both shapes the upgrade could have left. In `classify()`,
when no ROR name matched, build the per-language shape beside the
grouped one, and repair an author whose affiliations equal either:

```diff
-            $buggy = $matchedRors
-                ? array_map(fn ($ror) => ['ror' => $ror, 'name' => []], $matchedRors)
-                : [['ror' => null, 'name' => $affiliationRows->pluck('setting_value', 'locale')->all()]];
+            $legacyNames = $affiliationRows->pluck('setting_value', 'locale')->all();
+            $buggyShapes = $matchedRors
+                ? [array_map(fn ($ror) => ['ror' => $ror, 'name' => []], $matchedRors)]
+                : [
+                    // 3.5.0-2 to 3.5.0-5: one affiliation holding every language
+                    [['ror' => null, 'name' => $legacyNames]],
+                    // 3.5.0-0 and 3.5.0-1: one affiliation per language (pkp/pkp-lib#11675)
+                    array_map(fn ($locale, $name) => ['ror' => null, 'name' => [$locale => $name]], array_keys($legacyNames), $legacyNames),
+                ];
 …
-            $buggy = $this->canonical($buggy);
+            $buggyShapes = array_map(fn (array $shape) => $this->canonical($shape), $buggyShapes);
 …
-            if ($currentCanonical === $buggy) {
+            if (in_array($currentCanonical, $buggyShapes, true)) {
```

It keeps the tool's rule (only affiliations unchanged since the upgrade
are repaired) and widens "unchanged" to the second shape the upgrade
wrote. Tried with the same
[`fix.diff`](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13788/fix.diff):
on `main` and on `stable-3_5_0` the dry run lists all three authors as
`repair` to `[{"ror":"https://ror.org/01h531d29","name":{}}]`, Amina
Mansour's and Nicolas Riouf's lines unchanged.

**Alternatives**:
- List such authors as `review` instead of repairing them: safer if the
  team doubts that per-language rows are untouched, but it hands the
  administrator by hand what the tool can recognise.
- Repair the per-language shape only when the author has a plugin ROR
  (`&& $plugInRor !== null`): keeps the tool to the harms the issue
  names, and leaves the other split affiliations of those releases as
  they are.

**What goes with it**:
- With the fix as written, authors of 3.5.0-0 and 3.5.0-1 with a
  multilingual affiliation and no plugin ROR are listed as `repair`
  too, merged into one affiliation with all names, which is what the
  issue's "same rules as the fixed migration" give them.
- No stored data needs a migration; the tool is the repair.
- Test: the kept check
  [`split-rows.js`](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13788/split-rows.js);
  a unit test of `classify()` with the three shapes would guard it in
  pkp-lib.

Small: a few lines in `classify()`, tried on both branches.
