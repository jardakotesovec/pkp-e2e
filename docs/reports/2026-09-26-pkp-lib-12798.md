# "Move to Review" opens a page titled "Move to Submission" after a review round

Regression. OJS at `3162c105bf`, OMP at `72a01a026` (lib/pkp
`1ad4a14bb2` in both); introduced by pkp/pkp-lib#12959 (`8240fbe6cc`,
2026-09-25, for issue pkp/pkp-lib#12798), with its follow-up
pkp/pkp-lib#13398 (`1ad4a14bb2`). stable-3_5_0: does not (the change is not
on the line). Tracked in ci-triage "Open — known-red tests on `main`", row
pkp-lib#12798 (U32 S7, S9). Temporary: delete once acted on.

## Summary

Since 2026-09-25, an editor who presses "Move to Review" on a submission
in Copyediting that went through review lands on a decision page whose
heading reads "Move to Submission". The breadcrumb above it still says
"Move to Review", and the decision does send the submission back to
review. Separately, the decisions list in the REST API now names a past
"Move to Review" by the submission's current state, so the same recorded
decision can read "Move to Submission" later.

## Impact

Every journal and press editor who sends an accepted submission back from
Copyediting meets the wrong heading, on every such decision; nothing is
lost, since the decision itself goes to the right stage, but the page
contradicts the button that opened it and the destination the editor
chose, at the moment they confirm an email to the authors. A preprint
server has no Copyediting stage and is not affected. The API item affects
clients reading a submission's decision history: a decision's label no
longer describes what was decided. Minor: the wording misleads, the
outcome is right.

## Steps to reproduce

Preconditions:

- A fresh OJS (or OMP) install with its default languages.
- A journal with a Journal Manager, and a submission sent to review with
  "Send for Review" and then accepted with "Accept Submission", so it sits
  in Copyediting.

1. As the Journal Manager, open the submission's workflow; the stage is
   "Copyediting".
2. Press "Move to Review" at the top of the screen.

**Expected** (as before 2026-09-25): the decision page is titled "Move to
Review", like the button and the breadcrumb.

**Observed**: the page heading (h1) reads "Move to Submission"; the
breadcrumb's last item reads "Move to Review"; the description under the
heading reads "Send this submission back from the copyediting stage.";
recording the decision returns the submission to its review round.

A submission accepted without review (U32 A1) now shows "Move to
Submission" as the heading too, which is the issue's intended wording
there; its workflow button still reads "Move to Review" (the button's
label is a fixed ui-library string, `workflowConfigEditorialOJS.js`), so
neither case shows one label from button to page.

The API item, as a client with a Journal Manager's API key: take the
steps above, then record "Move to Review"; `GET
/api/v1/submissions/{id}/decisions` lists that decision as "Move to
Review". Then record "Cancel Review Round" on the round (no reviewer
confirmed yet). `GET …/decisions` again lists the same recorded decision
as "Move to Submission".

## Cause

`BackFromCopyediting::getLabel()` now takes the submission and returns
"Move to Review" when the submission has a review round, "Move to
Submission" otherwise (and when no submission is passed). Every caller
the PR changed passes the submission (the page title, the breadcrumb,
the submission API's available decisions, the decisions API, the email
variable), but `lib/pkp/templates/decision/record.tpl` builds the page
heading from `{$decisionType->getLabel()}` (lines 16 and 20) with no
argument, so the heading always takes the default. The decisions API
(`classes/decision/maps/Schema.php`) computes the label from the
submission as it is now, not as it was when the decision was taken.

## Proposed fix

Give the template the label the handler already computes:
`DecisionHandler` assigns `'decisionLabel' => $this->decisionType->getLabel(submission: $this->submission)`
and `record.tpl` uses `{$decisionLabel|escape}` in both places (or calls
`getLabel(null, $submission)`). For the API, derive the label of a
recorded decision from the decision's own data (the stage it moved to),
or keep the constant label for recorded decisions and use the conditional
one only for decisions still to be taken. The workflow button could read
the same conditional label from `availableEditorialDecisions`, which
already carries it.

## Evidence

- The heading: pkp-e2e U32 S7 ("'Move to Review' after a review round",
  OJS and OMP) and S9 ("after an internal round only", OMP) red on every
  CI run since the pointers moved (pkp/ojs 36205193903, pkp/omp
  36205535810, pkp-e2e 36211491859 and later), green before (pkp-e2e
  36190102252 at `825f730`, 2026-09-25 21:10); reproduced on a reset OMP
  database on 2026-09-26 (`.reports/sync/s26/pw-u32-omp/`, error
  context: `heading "Move to Submission" [level=1]` under the breadcrumb
  item "Move to Review"). Before-side code: `getLabel()` returned
  `__('editor.submission.decision.backFromCopyediting')` ("Move to
  Review") unconditionally.
- The API: `shared/playwright/checks/sync/pkp-lib-12798/decisions-label.js`
  on OJS and OMP, fresh scratch contexts on databases reset that morning
  (`.reports/sync/rr12798/s1-{ojs,omp}.json`): the same decision row
  (OJS id 3, OMP id 10) "Move to Review" before the cancel, "Move to
  Submission" after it.
- Also seen, not a user-facing regression: a third-party `DecisionType`
  subclass written for 3.5 (`getLabel(?string $locale = null)`) no longer
  loads against `main` (a declaration-compatibility fatal), which is the
  expected cost of the signature change; no hook registers decision types.
