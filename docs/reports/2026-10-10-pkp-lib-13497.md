<a id="finding-1"></a>
## Finding 1: two English slips are still in the file

The send wizard's "Cancel" asks "Are you sure want to cancel this
invitation?" (`userInvitation.cancel.message`), and the help under "Given
Name" on a newcomer's "Enter details" step says "it is tha part of a
personal name" (`acceptInvitation.userDetailsForm.givenName.description`).
The first shows on screen, as pkp-e2e#540's walk recorded on both
branches, and the PR head's file still holds it; the second was read in
the file. Both are in
[pkp-e2e#540](https://github.com/jardakotesovec/pkp-e2e/issues/540),
whose other slips are in the applications' own files.

With the diff the question reads "Are you sure you want to cancel this
invitation?" on the three applications.

<a id="finding-2"></a>
## Finding 2: two texts the pages name are in no file

Both invitation pages name the list of steps with
`invitation.wizard.completeSteps` and show `invitation.wizard.errors`
above the review step when the last press is refused. Neither key has a
text in any language, in pkp-lib or the applications, before or after the
PRs. A screen reader hears the first as
"##invitation.wizard.completeSteps##" on every step of both pages (read
in the accessibility tree at the PR head, three applications, both
branches; [pkp-e2e#543](https://github.com/jardakotesovec/pkp-e2e/issues/543)).
The second was not seen on screen: the one refusal that could be produced
on the review step (a username taken by someone else meanwhile) showed no
notice at all.

The diff adds the two texts pkp-e2e#543 proposes ("Complete the following
steps for this role invitation"; the errors text follows
`submission.wizard.errors`). With it the list's code is gone from both
pages on the three applications; the "##common.help##" left in the
manager's page header belongs to another entry (U08 A1). The wording is
the team's.

<a id="finding-3"></a>
## Finding 3: the issue's own fault is left in two translations

The PRs add the missing "$" to `{reviewAssignmentId}` in every
translation. Two other texts have the same fault and are untouched:

```
locale/da/invitation.po  invitation.userRoleAssignment.validation.error.user.emailMustNotExist
    Når en invitation har en tilknyttet e-mail ({email}), må denne e-mail-adresse ikke være i brug af en anden bruger.
locale/tr/invitation.po  invitation.userRoleAssignment.validation.error.userRoles.unexpectedProperties
    {attribute} indeksindeki ögede beklenmedik özellikler bulundu: {properties}.
```

Both are refusals the invitations API answers with, so a Danish or
Turkish reader gets the placeholder instead of the address or the
property names. English and the other translations fill them. With the
diff both render filled ("…e-mail (nova@example.org)…", "3 indeksindeki
… colour.").
