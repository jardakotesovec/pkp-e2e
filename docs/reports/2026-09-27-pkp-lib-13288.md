# "Cancel" in the upload wizard keeps an upload it should throw away when a second file was picked, or when the same file is revised in two tabs

Regression. OJS, OMP and OPS at ojs `72b85f4ba0`, omp `3cd59e9443`, ops
`e2111e3aae` (lib/pkp `26ae6431b5` / `17a1f01fed`); introduced by
pkp/pkp-lib#13288 (merge `f38c4a4a10`, 2026-09-27, for issue #13286).
stable-3_5_0: does not carry the change. Tracked in ci-triage "Open
regressions" and the submission-files spec (U36 A23, A24). Temporary:
delete once acted on.

Update 2026-09-29: pkp/pkp-lib#13411 (head `7263f86190`, driven before
its merge on OJS, OMP and OPS) fixes Finding 1 and the order of Finding 2
written below (the second tab cancelled first). The other order, the
first tab cancelled first, still fails as on `main`: that tab's "Cancel"
does nothing and the file ends as its upload (U36 A24). The same PR
brings a new case, reported in `docs/reports/2026-09-29-pkp-lib-13411.md`.

## Summary

The same fix that makes "Cancel" restore a renamed file (issue #13286,
verified today) breaks two other cancels. When someone uploading a
revision picks a file, then picks a different one on the same step before
pressing "Cancel", the file is left as the first pick instead of going
back to the original. When the same person revises one file in two
browser tabs, the second "Cancel" does nothing and the file keeps an
upload that was cancelled. Both worked before the change.

## Finding 1 — A second pick on step 1, then "Cancel", leaves the first pick in place

### Impact

Anyone offered "Upload" on a file list (editors, assistants, an author
uploading revisions, a galley's "Change File") who picks the wrong file,
picks again, then changes their mind and presses "Cancel". The window
closes as if all went well, but the file now is the abandoned first pick
under its name and uploader, and the Activity Log lists it as an uploaded
revision with a working "Download". The original is still in the file's
history, so a person who notices can upload it again. Nothing tells them
to look. Minor: it needs a re-pick before a cancel, but when it happens
the wrong file silently becomes the current one.

### Steps to reproduce

Preconditions:
- A fresh install; a journal (or press) with an Editor and an Author.
- A submission whose "Submission Files" list holds `article.pdf`,
  uploaded by the Author.

1. As the Editor, open the submission's workflow, "Submission Files",
   "Upload".
2. On "1. Upload File", choose `article.pdf` under "If you are uploading a
   revision of an existing file, please indicate which file.", pick
   `rev-one.pdf` and wait for it to finish uploading.
3. Still on step 1, pick another file, `rev-two.pdf`, and wait for it to
   finish.
4. Press "Cancel".
5. Reload the page and read "Submission Files".

**Expected** (as before the change): the list shows `article.pdf`,
uploaded by the Author.

**Observed**: the window closes and the list shows `rev-one.pdf`,
uploaded by the Editor. Activity Log & Notes keeps "A file revision
"rev-one.pdf" was uploaded for submission 1 by …" with its "Download".
The same happens with a galley's "Change File" (OJS, OPS). A single pick
followed by "Cancel" restores `article.pdf` correctly.

### Cause

`FileUploadWizardHandler::uploadFile()` now stores the replaced file's
state in the session under one key per submission file, and every upload
overwrites it. The second pick therefore stores the first pick
(`rev-one.pdf`) as "the original". `PKPManageFileApiHandler::cancelFileUpload()`
restores the revision just below the cancelled one (`$revisions->get(1)`,
line 118) with the stored state, and it ignores the `originalFile` the
wizard still posts (fileId 1, `article.pdf`), which the old code
restored. The first pick survives because the wizard's own request to
delete it is refused ("The current user is not authorized to access the
specified submission file.": the page script posts `id=` rather than
`submissionFileId=`). That refusal predates this change and used to be
harmless.

### Proposed fix

A proposal: write the session key only when none is set for that file
(`put` becomes "put if absent") and clear it when the wizard finishes,
so the state recorded before the first upload survives a re-pick. The
restore should then go back to that recorded fileId, which after a
re-pick is no longer `$revisions->get(1)`: either restore to the stored
fileId when it is among the file's revisions, or delete the abandoned
pick's revision when a new pick replaces it. Fixing the delete request's
parameter name (`submissionFileId`) would stop abandoned picks from piling
up in any case.

## Finding 2 — The same file revised in two tabs: the second "Cancel" fails silently

Update 2026-09-29: with pkp/pkp-lib#13411 the steps below close both
tabs and restore `article.pdf`. Pressing "Cancel" in tab A first (step 4
before step 3) still answers `{"status":false,…}` and leaves tab A open;
tab B's "Cancel" then closes and the list shows `rev-a.pdf`, with its
line and "Download" in Activity Log & Notes. Before #13288, tab A's
cancel restored `article.pdf` (tab B's then did nothing, the file staying
`article.pdf`). The cause is unchanged: a cancelled upload that is no
longer the file's current one is refused.

### Impact

One person with two tabs on the same submission (common when comparing
files) revises the same file in both and cancels both. The second
"Cancel" does nothing and shows no message; the window stays open. A
second press closes it, and the file is left as the upload cancelled in
the other tab. Minor: two concurrent revisions of one file by one person
are unusual, and the failure at least leaves the window open.

### Steps to reproduce

Preconditions as in Finding 1.

1. Tab A: as the Editor, "Upload", revise `article.pdf` with `rev-a.pdf`;
   stay on step 1 after the upload finishes.
2. Tab B (same browser, same account): open the same workflow,
   "Upload", revise the same file (now listed as `rev-a.pdf`) with
   `rev-b.pdf`; stay on step 1.
3. Press "Cancel" in tab B.
4. Press "Cancel" in tab A.
5. Reload and read "Submission Files".

**Expected** (as before the change): both windows close and the list
shows `article.pdf`.

**Observed**: tab B closes and the list shows `rev-a.pdf`. Tab A's
"Cancel" answers `{"status":false,"content":""}`; nothing is shown and
the window stays open. After the reload the list still shows
`rev-a.pdf`, and Activity Log & Notes lists "A file revision "rev-a.pdf"
was uploaded …" with its "Download".

### Cause

Tab B's upload overwrote the one session key with the `rev-a.pdf` state;
B's cancel restores `rev-a.pdf` and removes the key
(`$request->getSession()->remove(…)`, line 122). Tab A's cancel then
finds no stored state and returns `JSONMessage(false)` (line 131). The old
code restored from the state each wizard posted, so the two tabs did not
share anything.

### Proposed fix

A proposal: key the stored state by the wizard run as well as the file
(a token the wizard receives with its first upload and posts back on
cancel), or fall back to the posted `originalFile` after checking it
against the file's revisions, as the pre-change code did. The page
script could also show the failure instead of leaving the window open
silently.
