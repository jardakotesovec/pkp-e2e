# A site upgraded to 3.6 keeps the tasks table's old "status" column that a fresh install no longer has

- **Severity** low
- **Effort** small
- **Kind** defect
- **Affects**
  - main: OJS, OMP, OPS
  - ore: OJS (code; `ore` carries the same migration, tags `ore-2026-10-13` on)
  - 3.5: none (code; no `edit_tasks` table, the upgrade to 3.6 adds it)
  - 3.4: none (code)
  - 3.3: none (code)
- **Introduced** `pkp/pkp-lib#11699` · [aff80d393e](https://github.com/pkp/pkp-lib/commit/aff80d393e) · 2025-08-21 · Vitaliy (Vitaliy-1)
- **Upstream** none found (2026-11-09)
- **Tracked in** ci-triage "Open regressions" row (pkp-lib#11699) · Temporary: delete once acted on
- **Checked** 2026-11-09, `main`'s tips (the commits in Evidence)
- **Model** claude-opus-5-5

## Summary

The 3.6 upgrade first creates the editorial tasks table with a
`status` column (`I10406_EditorialTasks`), then a later step
(`I11702_ExtendTasks`) means to drop it again, since 3.6 tracks a task
by its start and close dates instead. That step asks Laravel's schema
builder to `removeColumn('status')`, which only takes the column out of
the builder's own list and sends nothing to the database. So every site
upgraded from 3.5 keeps `edit_tasks.status` (a `smallint`, not null,
default 1), while a fresh 3.6 install has no such column. Nothing on
screen changes today; the two kinds of site simply have different
schemas.

## Impact

- **Lost**: nothing a user sees now. The risk is the next change: a
  later migration that adds a `status` column to `edit_tasks`, or a
  schema comparison or tool that expects the install's shape, fails or
  behaves differently on upgraded sites only. Upgraded sites are where
  such a failure is hardest to reproduce.
- **Who**: every journal, press and server upgraded to 3.6 from 3.5
  (and `ore` sites upgraded the same way).
- **Way round**: an administrator can drop the column by hand.

Low: no behaviour differs today, and the fix is one word.

## Steps to reproduce

1. Install OJS (or OMP, OPS) 3.5.0-6, any content.
2. Upgrade it to `main` (`php tools/upgrade.php upgrade`).
3. In the database, list the columns of `edit_tasks`.
   - Expected: no `status` column, as on a fresh `main` install.
   - Observed: `status | smallint | default 1 | not null` is still
     there; on a fresh install of the same checkout it is absent.

## Cause

`lib/pkp/classes/migration/upgrade/v3_6_0/I11702_ExtendTasks.php`,
`up()`: `$table->removeColumn('status')`. `Blueprint::removeColumn()`
removes a column the same Blueprint was about to add; it issues no
`ALTER TABLE … DROP COLUMN`. The install migration
(`SubmissionsMigration`) creates `edit_tasks` without `status`, so the
two paths part here. `down()` has the same mistake for `date_started`,
`date_closed` and `title`.

## Proposed fix

In `I11702_ExtendTasks::up()` use `$table->dropColumn('status')`, and in
`down()` `$table->dropColumn(['date_started', 'date_closed', 'title'])`.
Sites already upgraded on a `main` or `ore` build keep the column; a
3.6 step that drops it when it exists (`Schema::hasColumn('edit_tasks',
'status')`) tidies them. Small: one migration, no data to move (the
column is never read).
