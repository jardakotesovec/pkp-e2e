## Summary

An editor who creates a new version of a published article or a posted
preprint expects the Activity Log to add "A new version was created."
It now also adds "Revision "article.pdf" was uploaded for file 46."
under the editor's own name, one such line per galley file. Nobody
uploaded anything: the new version received a copy of the galley's file.

Nothing is lost and the new version is right. But the submission's
history now says that this editor uploaded a revised file on that day,
and nothing on screen tells a reader that the line means a copy. The
lines cannot be removed.

A press has always logged its publication formats' files this way when
a version is created; a journal and a preprint server do so since
2026-10-27.

## Impact

- **Lost**: a correct history. The Activity Log credits the editor with
  an upload they never made, and each new galley file's own history
  starts with an upload entry. Nobody is told.
- **Who**: every editor or manager who presses "Create New Version" on
  a published article or posted preprint that has a galley with a file,
  every time, one line per galley file.
- **Way round**: none on screen, and none needed to get the work done.
  The wrong lines stay in the log and pile up with every version.

Low: nothing is lost and the version is created as it should be; only
the history misattributes an upload. It would be medium if anything
acted on these lines (a notice or an email); nothing does at the
production stage.

## Steps to reproduce

Preconditions: PKP's default dataset, OJS `main` (and OPS `main`, OJS
and OPS `stable-3_5_0`). Submission 17, "Antimicrobial, heavy metal
resistance and plasmid profile of coliforms isolated from nosocomial
infections in a hospital in Isfahan, Iran", is published with one
galley, "PDF". (OPS: submission 2, "The Facets Of Job Satisfaction: A
Nine-Nation Comparative Study Of Construct Equivalence".)

1. Sign in as `dbarnes` and open submission 17 from the editorial
   dashboard (`/index.php/publicknowledge/en/dashboard/editorial`).
2. Press the header's "Activity Log": the "Activity Log & Notes" window
   opens on "History". Note the lines, then close it.
3. Press "Create New Version": on `main` it is in the side menu; keep
   the preselected stage and "Minor Revision" and press "Confirm". On
   3.5 it is a button on the published version's "Title & Abstract"
   page (OPS: "Galleys"); press "Yes".
4. Press "Activity Log" again.

**Expected**: one new line for the version, as until 2026-10-27 (with
the "Submission metadata updated" line the press always adds):

```
2026-10-28 | Daniel Barnes | A new version was created.
2026-10-28 | Daniel Barnes | Submission metadata updated
```

**Observed**: a third line, an upload of the copied galley file, whose
"Settings" toggle reveals a "Download" link to the copy:

```
2026-10-28 | Daniel Barnes | Revision "article.pdf" was uploaded for file 46.
2026-10-28 | Daniel Barnes | A new version was created.
2026-10-28 | Daniel Barnes | Submission metadata updated
```

OPS reads `Revision "The Facets Of Job Satisfaction: A Nine-Nation
Comparative Study Of Construct Equivalence.pdf" was uploaded for file
20.` The same on `stable-3_5_0`, OJS and OPS. The server log shows
nothing. Control: the log of step 2 already lists the galley's real
upload, "Revision "article.pdf" was uploaded for file 40.", dated the
day the dataset was built; file 46 of step 4 is the version's copy of
that same file.

## Cause

`pkp/pkp-lib#13637` gives each new version its own copy of a galley's
file, so that a change to one version's file never reaches another.
OJS's `APP\publication\Repository::version()`
(`classes/publication/Repository.php`, lines 177-205 on `main`) clones
the galley's submission file onto the new galley and calls
`Repo::submissionFile()->add()` on it (line 189), then once per
dependent file (line 202). OPS's `version()` does the same (lines 149
and 162). Before the change the new galley kept the old submission file
id, and no file was added.

`PKP\submissionFile\Repository::add()` (lib/pkp
`classes/submissionFile/Repository.php`, lines 267-306) is the method
an upload ends in. After the insert it always writes two event-log
rows: `submission.event.fileUploaded` on the new file and
`submission.event.fileRevised` ("Revision "{$name}" was uploaded for
file {$submissionFileId}.") on the submission, both under the signed-in
user. It has no way to say that the file is a system copy, although its
sibling `edit()` takes `bool $log = true` for the same purpose.

Reach:

- OJS and OPS galleys with a file: two rows per galley file, and two
  more per dependent file (an HTML galley's images; code). Walked with
  one PDF galley on both apps and lines.
- OMP: `version()` has copied every publication format's files through
  `add()` since 3.3 (`pkp/pkp-lib#6057`), so a press has always logged
  the same lines (walked on `main` with one "PDF" format). Not a
  regression there, but the same fault.
- lib/pkp `versionSubmissionFile()`, which `version()` calls for an
  uploaded JATS XML file, copies it through `add()` too and logs the
  same way on all three apps since 3.5 (code).
- `copy()`, which copies a file to another stage, also logs through
  `add()`, but that copy is an editor's own act, so the line fits.
- Stored data: every version created since the change carries the two
  rows per copied file. They are only history; nothing reads them back.

## Proposed fix

Give `add()` the same `bool $log = true` flag `edit()` already has,
and have the copies that versioning makes pass `false`:

```php
    public function add(SubmissionFile $submissionFile, bool $log = true): int
    {
        …
        Hook::call('SubmissionFile::add', [$submissionFile]);

        // A copy made by the system (a new version's files) is no upload: log nothing
        if (!$log) {
            return $submissionFileId;
        }
        …
```

The three apps' `submissionFile\Repository::add()` overrides take the
flag and pass it to `parent::add()` (PHP refuses an override that drops
a parameter of its parent). Their `version()` methods pass `false` for
the galley (format) copy and each dependent copy, and lib/pkp's
`versionSubmissionFile()` does the same for the JATS copy. The hook
still fires, and OJS's and OPS's overrides still link the galley to its
new file. The version keeps its "A new version was created." line,
which already records the act. The diffs, against each app root with
the lib/pkp part under `lib/pkp/`:
[fix.diff](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13637/fix.diff)
(OPS),
[fix-ojs.diff](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13637/fix-ojs.diff),
[fix-omp.diff](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13637/fix-omp.diff).

Tried on OPS `main`: the Steps add only "A new version was created."
and "Submission metadata updated", and the new galley still points at a
submission file of its own on the same file. In the same trial a galley
file uploaded through the upload wizard still logged its upload.
`fix-ojs.diff` and `fix-omp.diff` apply cleanly to their apps' `main`
and were not run; `fix.diff` and `fix-ojs.diff` apply to `stable-3_5_0`
with offsets.

**Alternatives**:

- Insert the copies with the DAO (`$this->dao->insert()`) in
  `version()`. That skips the `SubmissionFile::add` hook (no bundled
  code listens, but third-party plugins may) and OJS's and OPS's galley
  link, which would then have to be repeated in each app.
- Log one honest line per copy ("A copy of … was made for the new
  version"). It needs a new locale key in every language, and "A new
  version was created." already says it.

**What goes with it**: the pkp-lib change and the three apps' overrides
must land together, or the apps whose override is not updated stop
with a fatal error. No data repair: the rows already written are only
history. Backport: the same change applies to `stable-3_5_0` as it
stands. Test: a unit test that versions a publication with a galley
file and counts the event-log rows, or a bullet in U49 scenario 4's
Activity Log read that no "uploaded" line is added.

Medium: one line of logic, but it touches pkp-lib and all three apps,
which must land together.
