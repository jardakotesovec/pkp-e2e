## Summary

The PRs add DataCite export and deposit for public peer reviews. A
review's DataCite record validates against DataCite's schema. An
anonymous or double-anonymous reviewer shows only as "unknown". An open
reviewer shows only their name, a verified ORCID and an affiliation. The
Crossref review record gets the shared title. Nothing that worked
before broke: the suites are green with one intended test change.

Five things in the new DataCite path go wrong:

1. With DataCite's "Testing" box ticked, which is the setup the issue's
   own test steps use, a deposit never sends the reviews. Their DOIs
   stay "Submitted" for good.
2. With "DOI Versioning" on, a review of version 1 is registered as
   reviewing the current version, under that version's title. Under
   DataCite it is never deposited at all.
3. A work with no English title crashes the review's deposit job. A
   journal whose primary language is not English cannot export review
   records. Crossref review records for such works get an empty title.
4. The review's landing URL is registered with DataCite with `&amp;`
   in it, so the link carries no usable review id.
5. A review record never carries its "Updated" date.

## Finding 1 — With DataCite "Testing" on, a deposit never sends the work's reviews

- **Severity** medium
- **Effort** small
- **Kind** intention gap
- **Affects**
  - main: OJS (walked)

### Impact

- **Lost**: every review deposit in DataCite test mode. The review DOIs
  stay "Submitted", and nothing on screen says why.
- **Who**: journals and testers that check DataCite with test
  credentials before going live, including anyone who follows the
  issue's own "Steps to test".
- **Way round**: none in test mode. Production deposits are not affected.

Medium: it blocks the feature's own test procedure, and a journal that
tries it first concludes peer-review DOIs don't work.

### Steps to reproduce

Preconditions: an OJS journal with DOIs on for "Articles" and "Peer
Review", DataCite chosen and configured with "Testing" ticked and a
"Test DOI Prefix". A published work has a completed, public review that
the editor confirmed and that has a DOI.

1. DOIs page: tick the work and choose "Deposit DOIs". Confirm.
2. Let the queued jobs run.
3. The article's DOI is sent to DataCite's test service and reads
   "Submitted". The review's DOI also reads "Submitted", and no deposit
   is ever made for it.

With "Testing" unticked, step 3 sends the review right after the
article and both read "Registered".

### Cause

`DepositSubmission::handle()` (`lib/pkp/jobs/doi/DepositSubmission.php`)
now dispatches a `DepositPeerReview` only when the article DOI's status
is `Doi::STATUS_REGISTERED`. The older code checked that the deposit
returned no errors. In test mode
`DataciteExportPlugin::depositXML()` never stores "Registered" (`if
(!$this->isTestMode($context))`), so the DOI stays `STATUS_SUBMITTED`
after a successful test deposit and the gate stays shut.

### Proposed fix

Accept "Submitted" beside "Registered" in the gate. An error leaves
`STATUS_ERROR`, so a failed deposit still sends no review. Part of
`checks/sync/pkp-lib-13119/fix-pkp-lib.diff`:

```php
if ($doiId && in_array(Repo::doi()->get($doiId)?->getStatus(), [Doi::STATUS_REGISTERED, Doi::STATUS_SUBMITTED])) {
```

Tried: in test mode the four reviews are sent to `mds.test.datacite.org`
right after the article. A refused article deposit ("Error") still
queues no review.

## Finding 2 — With "DOI Versioning" on, a review of an earlier version is registered as reviewing the current one

- **Severity** medium
- **Effort** small
- **Kind** intention gap
- **Affects**
  - main: OJS (walked)

### Impact

- **Lost**: correct metadata at DataCite. The review's record names the
  current version's title and says it `Reviews` the current version's
  DOI. Its landing URL points at version 1. Under DataCite with
  versioning, version 1's review is never deposited at all, because
  DataCite is given only the current version (U45 OJS8) and the review
  waits for version 1's DOI to read "Registered".
- **Who**: DataCite journals with "DOI Versioning" on whose works have
  more than one published version.
- **Way round**: none.

Medium: registered metadata is public and slow to correct, and those
reviews go unregistered.

### Steps to reproduce

Preconditions: DataCite chosen, "DOI Versioning" "Yes", DOIs on for
"Articles" and "Peer Review". A work was reviewed in round 1 on version
1 (a public, completed, editor-confirmed review with a DOI) and
published. Version 2 was then created and published.

1. DOIs page: "Deposit DOIs" for the work. Let the jobs run.
2. Only version 2 is sent. Version 1's DOI and the review's DOI stay
   "Submitted", and no review deposit is queued.
3. Build the review's record (as "Export DOIs" does): its title is
   `Review: "<version 2's title>" (Round 1, Review 1)` and its
   `relatedIdentifier relationType="Reviews"` is version 2's DOI.

Crossref's record for the same review names version 1's title and
`isReviewOf` version 1's DOI.

### Cause

`DataciteXmlFilter::process()` takes `$publication =
$article->getCurrentPublication()` for every object. For a review, the
title, the publication year and the `Reviews` relation all come from it.
`_getObjectUrl()`, `getExportableDOIsPeerReviewIds()` and Crossref's
`PeerReviewCrossrefXmlFilter` use the review round's publication
instead.

### Proposed fix

For a review, take the round's publication. Part of
`checks/sync/pkp-lib-13119/fix-ojs.diff`:

```php
if ($reviewAssignment) {
    $reviewRound = DAORegistry::getDAO('ReviewRoundDAO')->getById($reviewAssignment->getReviewRoundId());
    $publication = $reviewRound ? Repo::publication()->get($reviewRound->getPublicationId()) : $publication;
}
```

Tried together with Finding 1's gate: the record names version 1's title
and `Reviews` version 1's DOI. The review is now deposited, because
version 1's DOI reads "Submitted" after "Deposit DOIs". Whether the team
would rather send version 1 itself is the older question in U45 OJS8.

## Finding 3 — A work with no English title crashes the review deposit job; non-English journals can't export review records

- **Severity** medium
- **Effort** small
- **Kind** intention gap
- **Crash** server
- **Affects**
  - main: OJS (walked)

### Impact

- **Lost**: the review's deposit, and its export on a journal whose
  primary language is not English. The job fails with "Call to a member
  function getPrimaryLocale() on null", is retried, then lands in
  Failed Jobs. The review DOI stays "Submitted". On a fr_CA-primary
  journal, building the review record throws "DataCite export: titles
  are required but none were found." For Crossref, such a work's review
  record goes out with an empty `<title/>` (before these PRs it went
  out with the placeholder `##plugins.importexport.crossref.reviewTitle##`).
- **Who**: every journal publishing works titled in a language whose
  locale file lacks the new `submission.doi.review.title` key, which
  is every language but English until translations arrive, and any
  language the translators never cover.
- **Way round**: add an English title to the work.

Medium: a server error in a background job, on a common journal setup.

### Steps to reproduce

Preconditions: DataCite chosen, DOIs on for "Articles" and "Peer
Review". A work submitted in French with a French title only has a
public, completed, editor-confirmed review with a DOI, and is published.

1. DOIs page: "Deposit DOIs" for the work. Let the jobs run (`php
   lib/pkp/tools/jobs.php run`, or the job runner).
2. The article is registered. The review's `DepositPeerReview` job fails
   with `Error: Call to a member function getPrimaryLocale() on null`
   (`DataciteXmlFilter.php:711`), and the review's DOI stays
   "Submitted".

On a journal whose primary language is French, "Export DOIs" for the
same work fails while it builds the review record.

### Cause

`ReviewAssignment\Repository::getReviewTitle()` translates with
`Locale::getBundle($locale)->translateSingular()`, which returns `null`
for a locale that lacks the key. `DataciteXmlFilter::createTitlesNode()`
then falls back to `Application::get()->getRequest()->getContext()`,
which is `null` in a queued job or on the command line. In a request on
a French-primary journal the fallback asks for French again, gets
`null` again, and the filter throws. Crossref's filter passes the
`null` to `htmlspecialchars()`.

### Proposed fix

Fall back to English in `getReviewTitle()`, and take the context from
the deployment in DataCite's fallback (`fix-pkp-lib.diff` and
`fix-ojs.diff`):

```php
return Locale::getBundle($locale)->translateSingular('submission.doi.review.title', $params)
    ?? Locale::getBundle(LocaleInterface::DEFAULT_LOCALE)->translateSingular('submission.doi.review.title', $params);
```

```php
$this->getDeployment()->getContext()->getPrimaryLocale()
```

Tried: the job deposits the review titled `Review: "Succession des
cuvettes de marée …" (Round 1, Review 1)`. The French-primary
journal's record builds and validates. Crossref writes the same
title. The comment above `getReviewTitle()`, which promises `null` for
a missing translation, would need updating. If the team would rather
keep that promise, the English fallback can sit in both filters
instead.

## Finding 4 — The review's landing URL is registered with DataCite as `&amp;reviewId=`

- **Severity** low
- **Effort** small
- **Kind** intention gap
- **Affects**
  - main: OJS (walked)

### Impact

- **Lost**: the review id in the link the DOI resolves to. The link
  opens the right version's page, but the review id arrives as the
  parameter `amp;reviewId`.
- **Who**: every DataCite-registered review DOI.
- **Way round**: none. Today it shows nothing different, because no
  page displays the peer-review record yet (U13 footnote p). Once one
  does, every registered link would miss its review, and a DOI's
  registered URL has to be updated at DataCite to change.

Low: no visible effect today.

### Steps to reproduce

1. As in Finding 1 with "Testing" off: "Deposit DOIs" for a work with a
   review, and let the jobs run.
2. The review's `POST /doi` to DataCite carries
   `url=…/article/view/<id>/version/<pub>?tab=peer-review-record&amp;reviewId=<n>`.

### Cause

`DataciteExportPlugin::_getObjectUrl()` passes `$escape = true` to
`Dispatcher::url()` for the review URL, the only one of its URLs with
two query parameters. DataCite's `/doi` body is plain text, not XML, so
the `&amp;` is never decoded. Crossref is not affected: its URL sits in
XML, where `&amp;` decodes to `&`.

### Proposed fix

Pass `false` for `$escape` in the review case (`fix-ojs.diff`). Tried:
the URL is sent with a plain `&`.

## Finding 5 — A review record never carries its "Updated" date

- **Severity** low
- **Effort** small
- **Kind** intention gap
- **Affects**
  - main: OJS (walked)

### Impact

- **Lost**: the `Updated` date in every review's DataCite record. A
  review whose last-modified date is empty would instead get
  `Updated=1970-01-01`.
- **Who**: every DataCite-registered review.
- **Way round**: none.

Low: an optional date.

### Steps to reproduce

1. Build a review's DataCite record ("Export DOIs", or the deposit).
2. `<dates>` holds `Submitted`, `Accepted` and `Issued`, and no
   `Updated`, although the review has a last-modified date.

### Cause

`DataciteXmlFilter::createDatesNode()`, review case: `if
(!$lastModified) { $dates[DATACITE_DATE_UPDATED] = $lastModified; }`.
The condition is inverted.

### Proposed fix

`if ($lastModified)` (`fix-ojs.diff`). Tried: `Updated` is written, and
every record still validates against kernel-4.
