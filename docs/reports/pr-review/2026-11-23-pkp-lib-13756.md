**The core defect holds on `main`.** `PKPContextService::edit()`
(`lib/pkp/classes/services/PKPContextService.php:691-696`) writes
`array_merge($context->_data, $params)`, and `SchemaDAO::updateObject()`
(`lib/pkp/classes/db/SchemaDAO.php:144-210`) upserts every setting of
that copy. `shared/playwright/checks/sync/pkp-lib-13756/race.sh` on OJS
`main` `7e37e2dfd9` (pkp-lib `b18c557ff2`), PKP's test journal from the
Cypress setup, `php -S` with 4 workers; the Forms tick took 0.7 s, Add
Language 0.3 s, all answers 200:

| Add Language sent | `supportedFormLocales` | `supportedAddedSubmissionLocales` |
|---|---|---|
| after the tick ends | `["en","fr_CA"]` | `["en","fr_CA"]` |
| 0.1 s, 0.3 s after | `["en","fr_CA"]` | `["en"]` (lost) |
| 0.5 s after | `["en"]` (lost) | `["en","fr_CA"]` |
| 0.6 s, 0.7 s after | `["en","fr_CA"]` | `["en","fr_CA"]` |

With one `php -S` worker (pkp's CI, `pkp-github-actions`
`run-http-server.sh`, and the campaign's Cypress runner) the requests
queue and nothing is lost, so the Cypress flake shows only on a
multi-process server such as the Docker image's Apache.

The same stale write runs inside one request:
`LanguageGridHandler::saveLanguageSetting()` calls
`restoreLocaleDefaults()` and then `edit()` with the context it loaded
first, so a Forms tick writes the texts it just restored back to their
old values. That is why a typed French text survives an untick and
re-tick of Forms (U57 note i). A core fix that writes only `$params`
would make that tick overwrite typed texts with the defaults, which
the issue does not mention.
