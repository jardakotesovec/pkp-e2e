## 1. With ORCID off, a person who has an ORCID iD can never change contributor type (medium)

**Steps** (OJS, a fresh install)

1. A journal with ORCID enabled; a submission's contributor "Ida
   Offorcid", Person, carries a verified ORCID iD (as one verified
   while ORCID was on, or imported with `<orcid>`).
2. Settings › Users & Roles › ORCID: "Enable ORCID functionality"
   off.
3. Workflow › Publication › Contributors › Ida Offorcid › "Edit":
   choose "Organization or group", fill "Organization Name", "Save".
   Expected: saved, or a way to remove the iD. Observed: "Please
   correct one error." with "This contributor has an ORCID iD. Remove
   the ORCID iD before changing the contributor type." under
   Contributor Type. The panel has no ORCID iD field (it exists only
   while ORCID is on), and `POST orcid/deleteForAuthor/{id}` answers
   403 "You cannot perform this operation with ORCID functionality
   disabled." The API's `PUT …/contributors/{id}` with
   `contributorType: ORGANIZATION` is refused the same way.

The only way round on screen is to delete the contributor and add it
again, or to switch ORCID back on (which needs client credentials).

**Cause** `classes/author/Repository.php:162`: the check refuses the
type change whenever the author has an ORCID iD. `OrcidController.php`
`validateRequest()` refuses `deleteForAuthor` while ORCID is off, and
`ContributorForm.php` adds the ORCID field only while ORCID is on.

**Fix** One of:
- (a) While ORCID is off, clear the ORCID data on the type change
  instead of refusing it. Nothing can be deposited while ORCID is off.
- (b) Let `deleteForAuthor` run while ORCID is off. The issue's own
  reasoning is that deleting an iD "should always be possible". The
  form then needs a way to reach it.

Tried: refusing only while ORCID is enabled
(`&& OrcidManager::isEnabled($context)`,
[trial-fix.diff](../../../shared/playwright/checks/sync/pkp-lib-13624/trial-fix.diff)).
The switch then saves with ORCID off and is still refused with ORCID
on. But the iD stays stored on the organization, and the article page
prints any stored iD (`templates/frontend/objects/article_details.tpl:139`),
so (a) or (b) is the better fix. The gating would also create
organizations that carry an iD, which nothing else can create
once the PR is merged (item 2, settled: no such data exists before 3.6).
