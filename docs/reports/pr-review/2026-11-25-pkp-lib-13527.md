## 1. `common.help` is added, but nothing uses it any more (low)

**Steps** (OJS, OMP or OPS, `main` or 3.5)

1. `grep -rn "common\.help['\"]"` over the app with its `lib/pkp`, `lib/ui-library`
   and plugins (locale files left out).
   Expected: a use for the new key. Observed: none. The dashboard header's help
   link already reads "Help" at the tip (the walk's step help).

**Cause** ui-library `src/components/TopNavActions/TopNavActions.vue:11` uses
`t('help.help')` since ui-library#1046 (`main`, pkp-lib#12717) and #1050
(3.5, pkp-lib#12719). No template, PHP class, Vue or JS file of pkp-lib,
ui-library, OJS, OMP or OPS uses `common.help` on either branch, so the new
`locale/en/common.po` entry only adds a string for translators.

**Fix** Drop `common.help` from `locale/en/common.po` in #13861 and #13862.

## 2. OPS uses `notification.type.formatNeedsApprovedSubmission` too, and it stays undefined there (low)

**Steps** (OPS, `main` or 3.5)

1. `grep -rn formatNeedsApprovedSubmission classes locale/en` in OPS.
   Expected: a definition beside the use, as #6108/#6109 give OJS.
   Observed: `classes/notification/managerDelegate/ApproveSubmissionNotificationManager.php:41`
   and no `msgid`.

**Cause** OPS's `ApproveSubmissionNotificationManager::getNotificationMessage()`
has the same match arm as OJS's. In OJS and OPS the notification is stored (the
shared `PKPApproveSubmissionNotificationManager::updateNotification()` creates
type `0x100001D` for every unpublished submission: the walk found the row), but
nothing shows it: the apps' `getMgrDelegate()` routes only `APPROVE_SUBMISSION`
(and OJS `VISIT_CATALOG`) to the delegate, and `WorkflowNotificationDisplay.vue`
asks for it only in OMP. `notification/fetchNotification` asked for that type in
OJS renders an empty message at the tip and at the PR alike. So the OJS key is
never read, and OPS's reference is just as dead.

**Fix** Either add the key to OPS's `locale/en/locale.po` (PRs on `main` and
3.5), or, leaning to this one, drop the `FORMAT_NEEDS_APPROVED_SUBMISSION` line
from `getNotificationMessage()` in OJS's and OPS's
`ApproveSubmissionNotificationManager` instead of ojs#6108/#6109: no string for
translators that no reader sees, as with `notification.type.configurePaymentMethod`.
Not tried.

## 3. Question: `user.authorization.userRequired`, or the existing `user.authorization.loginRequired`?

`Locale::translate()` falls back to no other language: a key missing from a
locale shows as `##key##` there. The new `user.authorization.userRequired`
("You must be logged in to access this operation.") exists in `en` only, so the
signed-out Profile alert stays `##user.authorization.userRequired##` in the 70
other locales until Weblate fills them. `user.authorization.loginRequired`
("Login required.", the default message of `PKPSiteAccessPolicy`) is translated in 55 of
71 pkp-lib locales. Pointing `UserRequiredPolicy`'s default `$message` at it
(`classes/security/authorization/UserRequiredPolicy.php:32`) would give a
translated sentence at once and no new string, as the reuse in the second
commit does for `orcid.verify.denied` (37 locales) and `common.options` (55).
