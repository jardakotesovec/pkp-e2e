## Summary

Most of what the PRs set out to do works. On both lines and all three
apps, an upgrade from 3.3 or 3.4 with `fr_FR` (renamed to `fr`) now
creates every French default in French. Run on its own against a
database already upgraded at the base, `I13778_RepairRenamedLocaleDefaults`
produces the same default email templates, row for row, as the fixed
upgrade. It keeps a journal's own help texts and changes nothing on a
second run.

One broken shape is missed. The repair recognises a help text or the
checklist introduction as broken only when it equals another locale's
default text, usually English. That is what the issue reports. A site
whose `config.inc.php` still says `locale = en_US`, as every 3.3 and
3.4 config did and as PKP's own 3.3 CI dataset does, got no English
text. On such a site the 3.5 upgrade could not fall back to a valid
locale, so it stored the raw key: `##default.submission.step.beforeYouBegin##`
and the five other help texts, and
`<p>##submission.submit.submissionChecklistDescription##</p>` at the
head of the checklist. The repair leaves those as they are. The email
templates on the same site are repaired.

## Impact

- **Lost**: nothing is lost, but the submission wizard shows French
  authors raw keys where its six help texts should be, and the
  checklist opens with one.
- **Who**: OJS, OMP and OPS sites upgraded to 3.5.0-0…6 from 3.3
  (help texts and checklist) while their config still named `en_US`
  (or another pre-3.5 code), with one of the 11 renamed locales
  (`fr_FR`, `pt_PT`, `zh_CN`, `ja_JP`, `nb`, `bs`, the `sr`, `uz` and
  `be` variants) among a context's languages.
- **Way round**: the editor rewrites the six texts and the checklist
  sentence by hand under Settings → Workflow → Submission in that
  language. "Reload defaults" is no way round (the issue explains why).

Low: a raw translation key, and the task gets done. What would raise
it: many sites keeping `locale = en_US` through the upgrade, so that
the repair misses most of the sites it is written for.

## Steps to reproduce

1. Take PKP's 3.3 OJS dataset (`stable-3_3_0`, its `config.inc.php`
   with `[i18n] locale = en_US`) with every `fr_CA` replaced by `fr_FR`.
2. Upgrade it with `stable-3_5_0` at the PR base (`php tools/upgrade.php upgrade`).
3. Run `I13778_RepairRenamedLocaleDefaults` from the PR head on that
   database, as the 3.5.0.0–3.5.0.99 upgrade block will when the
   release is bumped (`repair-driver.php` in Evidence).
4. As admin, Settings → Workflow → Submission, switch the form to
   French: each help text reads `##default.submission.step.…##`, and
   the checklist begins "##submission.submit.submissionChecklistDescription##".

**Expected**: the French default texts, as the same steps give for a
site whose config says `locale = en` (the English texts are replaced).

## Cause

`I13778_RepairRenamedLocaleDefaults::isDefaultOfOtherLocale()` matches
a stored help text only against `__($localeKey, [], $otherLocale)` for
the installed locales, `en` and the config's default locale. The
checklist branch only checks the prefix `'<p>' . $otherDescription . '</p>'`
built the same way. With `locale = en_US`, `Locale::setLocale('fr_FR')`
in the 3.4 migrations "restored" the default locale, which is invalid
in 3.5 too, and with no handler in place `__()` returned
`##<key>##`. Neither check can match that, since `__()` for any valid
locale returns a translation.

## Proposed fix

Treat the bare key marker as one more broken state, in both checks.
Tried on both lines and all three apps (Evidence): the marker texts
become the French defaults, the English-shaped ones are repaired as
before, the journal's own texts stay, and a second run changes nothing.
