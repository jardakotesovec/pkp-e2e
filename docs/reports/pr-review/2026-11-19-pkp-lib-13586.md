## 1. A delete filtered on a setting removes the settings and keeps the row (low)

The reviewer's comment on the PR, confirmed.

**Steps** (OJS, a fresh install)

1. Two announcements titled "X" and "Y";
   `Announcement::query()->where('title', 'X')->delete()`.
   Expected: 1 returned, "X" gone. Observed: 0 returned, the "X" row
   still in `announcements` with no title. At the base the row and its
   settings went (the settings by the foreign key's cascade).

**Cause** `classes/core/SettingsBuilder.php:179`: `parent::delete()`
re-runs the query, whose `where('title', …)` is a subquery on
`announcement_settings`, after line 173 has deleted those rows.

**Fix** Delete the main rows by the ids `getTargetModelIds()` resolved,
in the same chunks, and return their count, as the reviewer suggested.
Tried, in the trial fix below: the row and its settings go, 1 returned.

## 2. `select()` of primary columns adds the primary key: `groupBy()` fails, `distinct()` returns every row (low)

**Steps** (OJS, a fresh install, PostgreSQL)

1. Three announcements of type A, one of type B;
   `Announcement::query()->select('type_id')->distinct()->get()`.
   Expected: two models. Observed: four, one per announcement. At the
   base: two (with an "Undefined property: stdClass::$announcement_id"
   warning).
2. `Announcement::query()->select('type_id')->groupBy('type_id')->get()`.
   Expected: two models. Observed: `QueryException` "column
   announcements.announcement_id must appear in the GROUP BY clause".
   At the base: two (with the warning). MySQL with `ONLY_FULL_GROUP_BY`
   fails the same way.

**Cause** `classes/core/SettingsBuilder.php:384`: the primary key is
pushed into the main-table select whenever it is missing, though it is
only needed to attach settings, and here no setting is selected.

**Fix** Add the key only when a setting column is selected, and when
none is, return the rows after `filterRow()` without reading the
settings table (which also removes the warning without the key). Tried:
two models in both cases, no warning.

## 3. With a join, the selected columns lose their table name and the ids are read with an unqualified key (low)

**Steps** (OJS, a fresh install, PostgreSQL)

1. `Announcement::query()->join('announcement_types', 'announcement_types.type_id', '=', 'announcements.type_id')->select(['announcements.announcement_id', 'announcements.type_id'])->get()`.
   Expected: the announcement. Observed: `QueryException` "column
   reference "type_id" is ambiguous". At the base: the announcement.
   With `'title'` added to the select it fails the same (at the base it
   failed on `title`).
2. `Announcement::query()->join('announcement_settings as s', 's.announcement_id', '=', 'announcements.announcement_id')->where('s.setting_value', 'X')->delete()`.
   Expected: "X" deleted. Observed: `QueryException` "column reference
   "announcement_id" is ambiguous". At the base: deleted. The query-path
   `update()` with a setting value reads the ids the same way.

**Cause** `classes/core/SettingsBuilder.php:380` and `:387` put the
stripped names (`type_id`) back as the main query's columns;
`:310` plucks `getPrimaryKeyName()` rather than the qualified key.

**Fix** Keep the primary columns as given, push
`$this->model->getQualifiedKeyName()`, and pluck the qualified key in
`getTargetModelIds()`. Tried: both cases return the announcement, and
the delete removes it.
