## 1. With the ORCID plugin on, nobody can register (high)

**Steps** (OJS or OPS 3.4, PKP's dataset, the ORCID Profile plugin enabled)

1. Signed out, open Register, fill the form (no ORCID), Register.
   Expected: the account is made. Observed: HTTP 500, a blank page, no
   account. The same with an ORCID iD filled in by the ORCID button.

**Cause** `plugins/generic/orcidProfile/OrcidProfilePlugin.php:954`:
`new \FormValidatorORCID(…)`. The global name is only a `class_alias`
made at the end of `lib/pkp/classes/form/validation/FormValidatorORCID.php`,
so it exists only once that file has been loaded under its namespaced
name; nothing has loaded it during registration, and the autoloader does
not know the global name. The log:
`PHP Fatal error: Uncaught Error: Class "FormValidatorORCID" not found`.

**Fix** `new \PKP\form\validation\FormValidatorORCID(…)` (or a `use`).
Tried with fix 2: accounts register on OJS and OPS with no iD, with
`https://orcid.org/0000-0002-1825-0097`, with `…-1694-233X` and with
the sandbox iD; a value that is not an ORCID URI is refused with "The
ORCID value is not a valid ORCID URI. Please reconnect your ORCID and
try again."

## 2. Every real ORCID iD is refused, in every app (critical)

**Steps** (OJS, OMP or OPS 3.4, PKP's dataset, plugin off)

1. As `dbarnes`, Edit Profile › Public, ORCID iD
   `https://orcid.org/0000-0002-1825-0097`, Save.
   Expected: saved. Observed: "The ORCID iD you specified is invalid.
   Please include the full URI (e.g.
   "https://orcid.org/0000-0002-1825-0097")." The same for
   `https://orcid.org/0000-0002-1694-233X`.
2. Save a contributor with that iD (the contributor form's request,
   `PUT …/contributors/<id>` with `orcid`).
   Expected: 200. Observed: 400, the same message; also for the sandbox
   iD.
3. With the plugin on, an account that already has an iD opens Profile ›
   Public and presses Save without changing anything.
   Expected: saved. Observed: the same error. The plugin hides the field
   and sends the stored iD back, so the tab cannot be saved at all
   (biography, homepage). The contributor form keeps a stored iD in its
   ORCID field and sends it with the other fields, so a contributor who
   has one is refused the same way (by code; the form itself not driven).

**Cause** `lib/pkp/classes/validation/ValidatorFactory.php:111`: the
pattern ends in `z/`, a literal "z", where `\z/` was meant (the 3.3 PR,
pkp/pkp-lib#13851, has `\z`), so only a value ending in "z" passes. The
rule backs `FormValidatorORCID` and the `orcid` validation of
`schemas/author.json` and `schemas/user.json`. The branch's
`ValidatorORCIDTest` asserts that this example iD is valid. pkp's own
checks are red on pkp/ojs#6105 (4 jobs; the tip is green) and
pkp/ops#1523 (5; the tip has 2); their logs were not readable while
the runs were in progress.

**Fix** `(\d{3}[0-9X])\z/`. Tried: all four steps pass on OJS, OMP and
OPS, the sandbox iD included.

## 3. The ORCID link on Profile › Public goes nowhere (low)

**Steps** (OJS or OPS 3.4, plugin on, an account with a stored iD)

1. Edit Profile › Public.
   Expected: the iD links to `https://orcid.org/…`. Observed: the
   link's address is empty (it reloads the profile page):
   `<a href="" https:\="" \="" orcid.org\="" 0000-0002-1825-0097""="" target="_blank">`.

**Cause** `templates/orcidProfile.tpl:28` and `:30`:
`href="{$orcid|json_encode}"` writes the value with its own double
quotes (and `\/` for every slash) inside the attribute's quotes.
`json_encode` is the right escape in a script, not in an HTML attribute.

**Fix** `href="{$orcid|escape}"` in both lines. Tried: the link is
`https://orcid.org/0000-0002-1825-0097` again on OJS and OPS.
