## Summary

pkp/pkp-lib#13795 removes the repair tool from `main`, because only
sites upgraded with 3.5.0-5 or earlier need it. Such a site can still
upgrade to 3.6 without having run it. Step 2 of the issue then tells it
to download the `stable-3_5_0` copy, and that copy runs on a 3.6
install without complaint. There it reads a 3.6 organization
contributor's own ROR ID as the old ROR plugin's, lists the
organization as `repair`, and `--commit` gives it an affiliation that
is the organization itself. This is finding 1 of
`docs/reports/2026-11-13-pkp-lib-13788.md`, reached now through the 3.5
copy.

## Impact

- **Lost**: a correct public record for each organization contributor
  with a ROR ID, if the administrator does not spot the line in the CSV.
- **Who**: sites that upgrade to 3.6 from 3.5.0-5 or earlier before they
  run the tool. No 3.6 release exists yet.
- **Way round**: run the tool before upgrading to 3.6, or exclude those
  authors with `--exclude`.

Low: no site can reach it until 3.6 is released (a latent defect). It
becomes medium, finding 1's level, from the 3.6 release on.

## Steps to reproduce

1. On OJS `main` (3.6.0.0, PKP's default test dataset), add an
   "Organization or group" contributor with a ROR ID, e.g. NSERC
   (`https://ror.org/01h531d29`), as in finding 1 of
   `docs/reports/2026-11-13-pkp-lib-13788.md`.
2. Download `tools/repairRorAffiliations.php` from `stable-3_5_0` (here
   the PR head `a3da55ce64`) into `lib/pkp/tools/`, as the issue's step 2
   says.
3. From the OJS root, run `php lib/pkp/tools/repairRorAffiliations.php`,
   then again with `--commit`.

**Expected**: the tool says it is for 3.5 and stops, or leaves the
organization alone.

**Observed**: "Checked 1 authors … To repair: 1". The organization's
line reads `repair` to `[{"ror":"https://ror.org/01h531d29","name":{}}]`,
and `--commit` writes it.

## Cause

The 3.5 tool decides whether it runs only from the tables it finds
(`author_affiliations` and `rors`, `execute()`), and 3.6 has both. It
reads every `author_settings` `rorId` as the old plugin's, but on `main`
the ORGANIZATION contributor keeps its own ROR in that setting.

## Proposed fix

Make the 3.5 tool refuse to run on anything that is not 3.5 (in
pkp/pkp-lib#13794), and add a line to the issue: "Run it before you
upgrade to 3.6".

```diff
+use APP\core\Application;
 use Illuminate\Support\Collection;
 …
     public function execute(): void
     {
+        // the tool knows 3.5's author data only: 3.6 stores an organization contributor's own ROR in author_settings 'rorId'
+        $version = Application::get()->getCurrentVersion();
+        if ($version->getMajor() !== 3 || $version->getMinor() !== 5) {
+            fwrite(STDERR, 'This tool is for 3.5 installations; this one is ' . $version->getVersionString() . ".\n");
+            exit(1);
+        }
```

Tried with
[`guard.diff`](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13794/guard.diff):
on OJS `main` it prints "This tool is for 3.5 installations; this one
is 3.6.0.0." and stops. On OJS `stable-3_5_0` it runs as before.

**Alternatives**:
- Keep a 3.6 copy on `main` with finding 1's fix (it skips
  ORGANIZATION contributors; `../pkp-lib-13788/fix.diff`), for sites that
  upgrade before they repair.
- Leave the tool unguarded and only add the sentence to the issue.

**What goes with it**: a 3.6 site that has not repaired before
upgrading has no tool, and the issue should say so.

Small: a few lines in one file, plus a sentence in the issue.
