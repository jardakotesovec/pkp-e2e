## Summary

With "Thema Subjects" turned on for a press, the Subjects field of a
book's "Metadata" (and of the submission wizard's "For the Editors"
step) offers Thema categories as the user types, but only when the typed
text appears in a category's description. Typing a Thema code, the way
metadata staff usually work, offers nothing from Thema. Typing "FJH"
lists only "FJH" itself, the free-text option. The suggestions API
answers the same request with "Historical adventure fiction" (FJH)
first, and the PR's search sorts an exact code match first precisely so
that "typing a code offers it". The browser then drops every category
whose description does not contain the typed text.

When free text is allowed, pressing Enter keeps "FJH" as a free-text
subject. Its chip reads like a code, but the ONIX export leaves it out
without a word, because only categories picked from Thema are exported.
When Thema is required, the code finds nothing at all, and Enter does
nothing.

## Impact

- **Lost**: finding a category by its code. In "allow free text" mode,
  a code typed and kept becomes a free-text subject that is missing from
  the ONIX export, with nothing on screen to say so.
- **Who**: press editors and authors on OMP 3.5 presses that turn on
  Thema Subjects, once these PRs ship.
- **Way round**: on screen. Type words from the category's description
  ("adventure" lists FJ, FJH, FJM, FJW and others) and pick it from the
  list.

Medium: the task can be done, but a common way of doing it fails, and in
one mode the failure is silent in the export. It would be higher if no
description search worked.

## Steps to reproduce

Preconditions: OMP at `stable-3_5_0` with pkp/omp#2456 checked out (its
`lib/pkp` at pkp/pkp-lib#13301), JS built, PKP's 3.5 test dataset
loaded.

1. As `admin`, Settings › Workflow › Metadata: tick "Enable subject
   metadata", then under "Thema Subjects" tick "Enable Thema subject
   categories" and choose "Allow free-text subjects alongside Thema
   subject categories.". Save.
2. As `dbarnes`, open book 4 ("How Canadians Communicate") › Publication
   › "Metadata".
3. Click into "Subjects" and type `FJH`.

**Expected**: the list offers the Thema category "Historical adventure
fiction" (FJH), as `GET /api/v1/vocabs?vocab=submissionSubject&term=FJH&locale=en`
returns it first.

**Observed**: the list holds one item, "FJH", the free-text option.
Pressing Enter adds a chip "FJH", and after "Save" the subject is stored
as `{"name": "FJH"}`, with no `source` or `identifier`. Typing
`adventure` in the same field lists "Historical adventure fiction" with
FJH under it, and picking that stores `{"name": "Historical adventure
fiction", "identifier": "FJH", "source": "thema"}`.

With "Only allow Thema subject categories." chosen in step 1, typing
`FJH` lists nothing.

## Cause

The OMP `VocabController::getMany()` that the PR adds appends
`Thema::search($term)` results. `search()` matches the term against the
code and the description, and puts an exact code match first, then code
prefixes. ui-library's `FieldControlledVocab.vue` (3.5 and `main` alike,
unchanged since pkp/pkp-lib#1550) filters what the API returns once more
in the browser:

```js
this.suggestions = this.allSuggestions.filter(
	(suggestion) =>
		!this.inputValue ||
		(this.inputValue !== suggestion.value.name &&
			suggestion.value.name.match(regex)),
);
```

It tests only `value.name`, the description, so every entry matched by
its code alone is dropped. The PR set has no ui-library change, so the
code search never reaches the screen.

## Proposed fix

Let the browser filter match the entry's code too (ui-library,
`FieldControlledVocab.vue`, `setSuggestions()`):

```diff
 					(this.inputValue !== suggestion.value.name &&
-						suggestion.value.name.match(regex)),
+						(suggestion.value.name.match(regex) ||
+							suggestion.value.identifier?.match(regex))),
```

Tried at the PR heads with OMP's JS rebuilt (Evidence): typing `FJH`
then lists "Historical adventure fiction" (FJH), VFJH and YFJH below the
free-text "FJH" option, and picking FJH stores the coded entry. In
"allow free text" mode the free-text option stays first, so Enter alone
still keeps the text; the team may want the coded match first. The diff is
kept at
`shared/playwright/checks/sync/pkp-lib-9906/fix-ui-library.diff`. The
same filter serves the other controlled-vocabulary fields (keywords,
disciplines), whose entries carry an `identifier` only when one was
stored. An alternative is to skip the browser filter for entries the
server has already matched by `term`.
