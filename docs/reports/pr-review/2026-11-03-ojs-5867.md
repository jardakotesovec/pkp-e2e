## Summary

`pkp/ojs#5867` makes a DataCite journal's file carry every translation
of a work's title, subjects and descriptions, each marked with its
language (`xml:lang`), as `pkp/pkp-lib#9170` asks. Built on PKP's
dataset with French translations added, the article's, issue's and
supplementary file's records carry both languages correctly marked and
pass DataCite's kernel-4 schema. Three points of the issue are not met
yet. All three are among the points bozana raised on the issue
(2026-11-03), and the walk reproduces each one:

1. **Empty translations are sent.** The issue says a translation that
   is empty, including after its HTML is turned into text, is not
   exported. At the head, an abstract saved as `<p></p>` gives an empty
   `<description xml:lang="fr-CA">`. A translation in a language the
   journal no longer offers (`de`) that holds `""` gives an empty
   description or subject. An abstract of `<p>&nbsp;</p>` gives a
   description holding only a no-break space.
2. **An issue's alternative title can carry the wrong language.** An
   issue titled only in French ("Numéro spécial", English empty) goes
   out as `<title xml:lang="en" titleType="AlternativeTitle">Numéro
   spécial</title>`.
3. **An issue's table of contents is marked with the journal's primary
   language.** Each entry is that article's own primary title. An
   article titled only in French is listed in a description marked
   `xml:lang="en"`.

The fix in Proposed fix, tried at the head, clears all three. Every
record still passes the schema.

The PR also fixes a crash outside this review. On a DataCite journal,
a supplementary file with a subject cannot be exported at the base
(`TypeError: Cannot access offset of type string on string`). The same
happens on `stable-3_5_0` (3.5.0-4 and later), which this PR does not
reach (see Evidence).

## Impact

- **Lost**: nothing a reader needs. DataCite and the indexes behind it
  get empty abstracts or subjects tagged with a language. An
  alternative title or a table of contents can also be marked with a
  language its text is not in.
- **Who**: multilingual journals that register DOIs with DataCite,
  once the PR is merged.
- **Way round**: none needed for the deposit itself: every file passes
  the schema and deposits. Clearing a stray translation only helps
  where the editor can reach that language.

Low: a wrong value in machine-read metadata that the deposit accepts,
on an unmerged PR.

## Steps to reproduce

The test installs cannot download "Export DOIs" files (the schema fetch
goes through a dead proxy; U45 Rule 29), so the file is built on the
server with the plugin's own export filter:

1. Load PKP's OJS dataset (`npm run fleet-prep -- --feature sync-9170
   --apps ojs --dataset --reset`). The journal offers English and
   French (Canada), and articles 1 and 17 are published in issue 1.
2. Check OJS out at `pkp/ojs#5867` (`57eb645396`).
3. Run `shared/playwright/checks/sync/pkp-lib-9170/xml-lang.php` with
   `PKP_CONFIG_FILE` set to the fleet's config, pointing at a local copy
   of DataCite's kernel-4 schema. It adds the translations in memory,
   or in a transaction it rolls back. Its scenarios are:
   - C: article 1 with an English abstract, a French `<p></p>` and a
     Spanish `<p>&nbsp;</p>`.
   - D: an empty German title, abstract and keyword list.
   - G: issue 1 titled only in French, and article 17 titled only in
     French.
   - H: galley 1's file made a supplementary file with a German subject
     `""`.
4. Read scenario C's descriptions: `fr-CA|Abstract|(empty)` and
   `es|Abstract|` followed by a no-break space. Expected: the English
   abstract alone.
5. Read scenario D: `de|Abstract|(empty)`. Scenario H: `de|-|(empty)`
   among the subjects.
6. Read scenario G's titles: `en|AlternativeTitle|Numéro spécial`.
   Expected `fr-CA`. Its table of contents is
   `en|TableOfContents|Un article seulement en français …`.

## Cause

`plugins/generic/datacite/filter/DataciteXmlFilter.php` at the head:

- The new loops take every value `getTranslationsByPrecedence()`
  returns. That function drops empty values only for the languages in
  the precedence list, which holds the journal's form languages. Any
  other language is passed on as it is. No value is checked once
  `PKPString::html2text()` has turned it into text, so `<p></p>` passes
  as non-empty. Before the PR only `getPrimaryTranslation()`'s first
  non-empty value was used, so this never showed.
- `createTitlesNode()` takes the issue's title from
  `getPrimaryTranslation()`, which falls back to any language that has
  one. It then sets `xml:lang` from `$objectLocalePrecedence[0]`, not
  from the language it picked.
- `createDescriptionsNode()` files the table of contents under
  `$objectLocalePrecedence[0]`. `getIssueToc()` builds each entry from
  that article's own primary title, so no single language fits the
  whole table.

## Proposed fix

`shared/playwright/checks/sync/pkp-lib-9170/fix-ojs.diff`, against the
PR head (tried there, reverted):

- A helper `isBlank()` treats a value as empty when, after
  `html2text()`, it has nothing but whitespace or no-break spaces. The
  subject loops and the description loop skip such values, and the
  `<descriptions>` element is left out when nothing remains.
- The issue's alternative title takes its text and its language from
  the same entry of `getTranslationsByPrecedence()`.
- The table of contents is filed under no language and written without
  `xml:lang`, as bozana suggested. Marking each entry is not possible:
  one `<description>` holds the whole table.

With the fix, scenarios C, D and H carry no empty element. G's
alternative title reads `fr-CA` and its table of contents has no
`xml:lang`. A, B, E and F are unchanged, and all eight files pass the
schema. A test for points 1–3 in `DataciteXmlFilterTest.php` (bozana's
point 4) was not written here.
