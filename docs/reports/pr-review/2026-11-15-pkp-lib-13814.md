hands the merged account's comments and reports to the kept account,
and they stay on the article's page and on the Comments page.

One thing is still broken. An administrator who deletes a submission
with `php tools/deleteSubmissions.php <id>` gets a fatal error. The
publication is deleted, but the submission row stays behind without

## Finding 3 — `tools/deleteSubmissions.php` fails with `Call to a member function getData() on null` and leaves the submission without its publication

- **Severity** medium
- **Effort** small
- **Kind** regression
- **Crash** server
- **Affects** main: OJS, OPS at the PR heads; round 1 only for articles carrying a comment, round 2 for every article

### Impact

- **Lost**: the submission keeps its row without any publication (a web
  delete that failed this way left such a submission on the dashboard
  in round 1), and the tool stops at the first submission.
- **Who**: administrators who delete submissions from the command line,
  on any OJS or OPS site. OMP ships no such tool.
- **Way round**: delete the submission from the web, as an editor.

Medium: an administrator's task fails every time, with a way round on
screen. What would raise it: other context-less callers, such as an
import that fails and cleans up after itself (code only, below).

### Steps to reproduce

1. Take any submission's id, published or not, with or without
   comments.
2. On the server: `php tools/deleteSubmissions.php <id>`.
3. The tool exits 255 with
   `PHP Fatal error:  Uncaught Error: Call to a member function getData() on null in lib/pkp/classes/userComment/Repository.php:41`.
   The `submissions` row is still there, and its `publications` rows
   are gone.

**Expected**: as at the base, exit 0 and the submission deleted.

### Cause

Round 2's `PKP\publication\DAO::deleteById()` calls
`Repo::userComment()->deleteNotifications(...)` on every publication
delete. `Repo::userComment()` builds a `PKP\userComment\Repository`,
whose constructor reads `$request->getContext()->getData('itemsPerPage')`.
A command-line request has no context, so the constructor throws. By
then `parent::deleteById()` has already deleted the publication, so
`Repo::submission()->delete()` never reaches the submission row.

Round 1 built the repository only when the publication had comments,
so the CLI failed only for commented articles.

The reach:

- `tools/deleteSubmissions.php` (OJS, OPS): driven.
- `PKPImportExportDeployment::removeImportedObjects()`, which deletes the
  submissions of a failed native XML import, from `tools/importExport.php`
  too: code only, unverified.
- Deleting a journal from site administration is not affected. OJS's
  `afterDeleteContext` deletes the submissions after the journal row is
  gone, and the publications have already cascaded with it (driven).

### Proposed fix

Call the static method without building the repository:

```diff
-        Repo::userComment()->deleteNotifications($associatedCommentsId, $reportIds);
+        \PKP\userComment\Repository::deleteNotifications($associatedCommentsId, $reportIds);
```

(or `use PKP\userComment\Repository as UserCommentRepository;` and
`UserCommentRepository::deleteNotifications(...)`). `deleteNotifications()`
is already `public static` and reads nothing from the instance. Tried
at the round-2 head: the CLI deletes a submission with or without a
comment (exit 0, nothing left), and every web path gives round 2's
results.

- **Alternatives**: restoring round 1's guard only narrows the failure
  back to commented articles.
- **What goes with it**: the controller's calls may stay as they are,
  since a web request to the comments API always has a context.

Small: one line, already tried.

## Finding 1 (fixed in round 2) — Deleting a comment, a report or a commented article answers `Class "PKP\userComment\Application" not found`

- **Severity** high
- **Effort** small
- **Kind** regression
- **Crash** server
- **Affects** main: OJS at the PR heads; OMP and OPS with the PR in `lib/pkp` (comments made through the API)

### Impact

- **Lost**: the deleted article keeps a submission with no
  publication. It stays on the dashboard, and the tasks about deleted
  comments and reports stay in every moderator's panel.
- **Who**: every journal with public comments on. Every moderator who
  deletes a comment or report, every writer who deletes their own
  comment, and every editor who deletes an article that has comments.
- **Way round**: none on screen. "Hide Comment" keeps a comment off the
  article but does not delete it.

High: a secondary task, deleting in comment moderation, fails for
everyone who uses it, with no way round. Deleting an article with
comments then leaves a broken submission behind.

### Steps to reproduce

1. With public comments on, as a reader, comment on a published
   article; as another reader, report the comment.
2. As the Journal Manager, Settings › Website › Comments ("Comments"
   page): on the comment's row press "Delete Comment" and "Delete".
   The request `DELETE api/v1/comments/{id}` answers 500:
   `{"error":"Class \"PKP\\userComment\\Application\" not found"}`.
   The page shows an error, not "The comment has been deleted
   successfully." The comment is gone after a reload, and the tasks
   about it and its report are still in the Tasks panel.
3. The same with a report's "Delete Report"
   (`DELETE api/v1/comments/{id}/reports/{reportId}`), and with the
   writer's own "Delete Comment" on the article's page.
4. Unpublish an article with a comment and delete the submission
   (`DELETE api/v1/submissions/{id}`): 500 with the same error. The
   submission is still listed on the dashboard and
   `GET api/v1/submissions/{id}` answers 200, but its publication row
   is gone.

**Expected**: as at the base, 200 and the success notice; the
comment, the report or the whole submission deleted, with their tasks.

### Cause

The PR moves the notification clean-up into a new
`PKP\userComment\Repository::deleteNotifications()`
(`classes/userComment/Repository.php:119–132`), which reads
`Application::ASSOC_TYPE_COMMENT` and
`Application::ASSOC_TYPE_COMMENT_REPORT`. The file imports
`PKP\core\PKPApplication` but not `Application`. In the namespace
`PKP\userComment` the bare name resolves to
`PKP\userComment\Application`, which does not exist.

Each caller runs it after its rows are deleted, so the error comes
after the deletion and before the clean-up and the response:

- `UserCommentController::delete()`, `deleteReport()` and
  `deleteReports()` (the comment or report is already deleted);
- `PKP\publication\DAO::deleteById()`, only when the publication has
  comments. The publication row is already deleted, so
  `Repo::submission()->delete()` never reaches the submission row.

The context deletion is not affected. By the time its publications are
deleted, the comments are already gone with the context (the
`context_id` foreign key cascades), so `deleteById()` finds none and
skips the call.

### Proposed fix

Import the class, as the controller does:

```diff
 namespace PKP\userComment;

+use APP\core\Application;
 use APP\core\Request;
```

(or use `PKPApplication::`, already imported). With that line added at
the PR head, the drive below gives back the base's results for every
delete path: 200, the rows deleted, the comment's and the report's
tasks cleared, the submission deleted.

- **What goes with it**: none of the PR's code paths had a test. U14's
  scenarios S3, S4, S5, S10 and S15 (deleting comments and reports)
  go red at the PR head and green with the line added; S12 (deleting
  an article) then reds only on the intended change.

Small: one line, already tried.

## Finding 2 (fixed in round 2) — A deleted article's report tasks stay in the moderators' panels

- **Severity** low
- **Effort** small
- **Kind** intention gap
- **Affects** main: OJS at the PR heads, once Finding 1 is fixed

### Impact

- **Lost**: nothing. Each moderator keeps a blank task about a report
  that no longer exists.
- **Who**: moderators of a journal that deletes an article whose
  comments were reported.
- **Way round**: each moderator deletes the task by hand.

Low: a dead row in a panel. It is the report half of what the PR's
second commit ("Cleanup orphaned public comments related notifications
after a publication is deleted") sets out to clear.

### Steps to reproduce

1. With Finding 1's line added: a published article with a comment
   that another reader reported. The Journal Manager's Tasks panel has
   the two tasks: "A comment has been submitted…" and "A report was
   submitted for a comment…".
2. Unpublish the article and delete the submission.
3. The comment's task is gone from the panel. The report's task stays,
   blank.

**Expected**: both tasks deleted, as when the comment itself is
deleted.

### Cause

`PKP\publication\DAO::deleteById()` (`classes/publication/DAO.php:294–308`)
collects the comment ids before `parent::deleteById()`, but it collects
the report ids after it:

```php
$associatedComments = UserComment::withPublicationIds([$publicationId])->pluck('user_comment_id')->all();
$affectedRows = parent::deleteById($publicationId);
// …
if ($associatedComments) {
    $reportIds = UserCommentReport::withCommentIds($associatedComments)->pluck('user_comment_report_id')->all();
    Repo::userComment()->deleteNotifications($associatedComments, $reportIds);
}
```

Deleting the publication row cascades to `user_comments` and from there
to `user_comment_reports`. By the time the second query runs, the
reports are gone, `$reportIds` is empty, and `deleteNotifications()`
skips the report notifications.

### Proposed fix

Collect both before the delete:

```diff
         $associatedComments = UserComment::withPublicationIds([$publicationId])->pluck('user_comment_id')->all();
+        $reportIds = $associatedComments
+            ? UserCommentReport::withCommentIds($associatedComments)->pluck('user_comment_report_id')->all()
+            : [];
         $affectedRows = parent::deleteById($publicationId);
@@
         if ($associatedComments) {
-            $reportIds = UserCommentReport::withCommentIds($associatedComments)->pluck('user_comment_report_id')->all();
             Repo::userComment()->deleteNotifications($associatedComments, $reportIds);
         }
```

Not tried; the cause is the order the drive shows (comment tasks 0,
report tasks 2 after the delete).

- **What goes with it**: the same applies to the comments of a deleted
  account (`PKP\user\Repository::delete()`, the cascade from
  `users`), which U14 A10 records and the PR does not touch.

Small: two lines moved.
