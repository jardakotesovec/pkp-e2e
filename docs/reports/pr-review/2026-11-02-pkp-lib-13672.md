## Summary

**Round 2 (2026-11-02): fixed.** `pkp/omp#2540` and `pkp/ops#1475` were
force-pushed to `403f1c7f20` and `7ef057dff9`. Each one's tree differs from
round 1 only in the `upgrade.xml` line, which now names
`PKP\migration\upgrade\v3_6_0\I13530_…`: this report's proposed fix.
`lib/pkp` is still `fcc464cfc8`, and pkp-lib and OJS are unchanged. At the
new heads PKP's 3.5 datasets upgrade to 3.6.0.0 on OMP and OPS, and
`review_round_author_responses` loses `doi_id`, its index and its
foreign key, as on OJS. Nothing is open. The cleanup notes below stand
as optional.

Round 1:

The PR set removes the author-response DOI kind, as the issue asks.
pkp-lib drops the code, the `doi_id` column from the fresh install, and
adds the upgrade migration
`PKP\migration\upgrade\v3_6_0\I13530_RemoveDoiIdFromReviewRoundAuthorResponses`.
OJS's `upgrade.xml` names that class correctly. OMP's and OPS's name it
`APP\migration\upgrade\v3_6_0\I13530_…`, a class that exists in neither
app. Upgrading a press or a preprint server from 3.5 therefore stops at
that step with `PHP Fatal error: Uncaught Error: Class
"APP\migration\upgrade\v3_6_0\I13530_RemoveDoiIdFromReviewRoundAuthorResponses"
not found`, after every earlier 3.6 migration has run.

At the PR bases (the `main` tips) the same 3.5 datasets upgrade to
3.6.0.0 on OMP and OPS. With `APP` changed to `PKP` in the two
`upgrade.xml` lines, both upgrade at the heads and the column, its index
and its foreign key are gone, as on OJS.

The rest of the set does what the issue asks, as far as the walks
reach. On OJS at the head:

- PKP's 3.5 dataset upgrades to 3.6.0.0, leaving
  `review_round_author_responses` without `doi_id`, its index or its
  foreign key.
- On the default dataset, a journal whose settings carry the
  `authorResponse` kind no longer mints DOIs for author responses.
  This was pkp-e2e#965, spec U45 OJS9, which retires at the merge step
  (see Evidence).

Cleanup the PRs leave behind (low; nothing a user meets):

- OJS `schemas/context.json` still lists `authorResponse` in
  `enabledDoiTypes` (`in:publication,representation,issue,peerReview,authorResponse`),
  so `PUT api/v1/contexts/{id}` still accepts and stores the kind. Once
  stored, nothing reads it any more.
- OJS `classes/submission/Collector.php` `addHasDoisFilterToQuery()`
  still left-joins `review_round_author_responses as current_rrar`,
  which nothing uses now.
- OJS `DoiSetupSettingsForm.php` keeps a commented-out
  `authorResponseCustomSuffixMessage` field, the twin of the commented
  option the PR removed.
- pkp-lib `Repository::getReviewAuthorResponses()` (publication) has no
  caller left in pkp-lib, OJS, OMP or OPS.
- ui-library `DoiListPanelOJS.vue` still builds author-response rows
  (`enabledDoiTypes.includes('authorResponse')`, the
  `_dois/authorResponses/{id}` route this set removes, the
  `submission.reviewRound.authorResponse.identified` key). There is no
  ui-library PR.

## Impact

- **Lost**: the upgrade to 3.6. It stops with a fatal error part-way
  through the 3.6 migrations and leaves the database between versions.
- **Who**: every OMP and OPS install that upgrades from 3.5 (or any
  earlier version) once these PRs merge. Fresh installs are not affected.
- **Way round**: none in the app; an administrator would have to edit
  `dbscripts/xml/upgrade.xml`.

High: an upgrade fails for every press and preprint server, with no way
round. This is caught before merge.

## Steps to reproduce

1. OMP at `pkp/omp#2540` (`fffb9cf7eb`, `lib/pkp` at `pkp/pkp-lib#13672`
   `fcc464cfc8`); load PKP's `stable-3_5_0` test dataset (pkp/datasets,
   `omp/stable-3_5_0/pgsql`, schema 3.5.0.6).
2. `php tools/upgrade.php upgrade`.
3. The run logs
   `[migration: APP\migration\upgrade\v3_6_0\I13530_RemoveDoiIdFromReviewRoundAuthorResponses]`,
   then `PHP Fatal error: Uncaught Error: Class "APP\migration\upgrade\v3_6_0\I13530_RemoveDoiIdFromReviewRoundAuthorResponses" not found in lib/pkp/classes/install/Installer.php:434`
   and exits 255.
4. The same on OPS at `pkp/ops#1475` (`0b7e068572`).

Expected: "Successfully upgraded to version 3.6.0.0", as at the bases
(omp `853bf3b05`, ops `fd893a8c92`, `lib/pkp` `442148e14e`) and as on
OJS at `pkp/ojs#6013`.

## Cause

The migration class lives in pkp-lib, namespace
`PKP\migration\upgrade\v3_6_0`
(`classes/migration/upgrade/v3_6_0/I13530_RemoveDoiIdFromReviewRoundAuthorResponses.php`).
OJS's `upgrade.xml` names it with `PKP\`. OMP's (`dbscripts/xml/upgrade.xml:237`)
and OPS's (`:226`) name it with `APP\`, and neither app has a class of
that name. `Installer::executeAction()` instantiates the named class and
fails.

## Proposed fix

In `pkp/omp#2540` and `pkp/ops#1475`, `dbscripts/xml/upgrade.xml`:

```diff
-		<migration class="APP\migration\upgrade\v3_6_0\I13530_RemoveDoiIdFromReviewRoundAuthorResponses"/>
+		<migration class="PKP\migration\upgrade\v3_6_0\I13530_RemoveDoiIdFromReviewRoundAuthorResponses"/>
```

Tried at the heads on both apps: the 3.5 dataset upgrades to 3.6.0.0
and `review_round_author_responses` loses `doi_id`, as on OJS.

The cleanup above is optional. For the OJS schema, drop `authorResponse`
from the `enabledDoiTypes` rule in `schemas/context.json`. For the
others, delete the join, the method, the commented block and the
ui-library branch.
