## 1. OPS still ships the old Crossref plugin on `main` and 3.5 (medium)

crossref-ops#82 and #81 are merged in the plugin, but no OPS PR moves
`plugins/generic/crossref`, so a preprint server's deposit run by the
job tool still loses Crossref's message.

**Steps** (OPS, PKP's 3.5 dataset, `job_runner = Off`, kept check
`shared/playwright/checks/sync/pkp-lib-13860/cli-deposit-dataset.js`)

1. DOIs on, Crossref enabled and chosen; "Deposit DOIs" on a posted
   preprint; `php lib/pkp/tools/jobs.php work --stop-when-empty`.
   Expected: "Error" with Crossref's message under "View Error".
   Observed: "Error" and no `crossrefplugin_failedMsg` (OPS 3.5 tip
   `7b58c0b4f8`, crossref `e72c479`; `main` `a80a5decc1`, crossref
   `0bcf460`, as in round 1).

**Cause** OPS's pointers: `main` at `0bcf460`, 3.5 at `e72c479`, both
before the merges (`f4bd0f177d`, `8738fc17ca`).

**Fix** An OPS PR per branch moving `plugins/generic/crossref` to the
merged tip (3.5 also `lib/pkp` to pkp-lib#13886), as ojs#6124 and
ops#1528 do. The merged tips' code is the round-1 heads', walked fixed.

On 3.4 a connection error is not caught by either plugin (the job
fails and the DOI stays "Submitted"); only an answer with a response
writes the message, so the 3.4 runs stub the agency's answer: the
deposit job runs in a command-line tool's process (plugins registered
with no context, as `jobs.php` does) with the Guzzle client 3.4 hands
out under `PKPContainer::setRunningUnitTests()`. pkp-lib#13886 is
`main`'s `1967e76f38`; #13885 is the same fix in 3.4's own parser
(`in_array('--force', $parameters)`, 3.4 has no `hasFlagSet()`).
`--force` was read only. OMP gets the `jobs.php` fix with its next
`lib/pkp` update on 3.4 and 3.5 (no OMP PR; its 3.5 suite ran with
#13886 on CI).
