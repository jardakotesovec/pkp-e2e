## Summary

The tool works out again which ROR organizations the faulty 3.5.0
upgrade gave each author. It matches the author's old affiliation
against the organization names in today's copy of the ROR registry,
not the copy the upgrade used. When ROR has renamed an organization
since the upgrade, the old affiliation no longer matches it. The
wrong ROR the upgrade put on the author stays, and the tool writes no
line for that author and counts them nowhere.

Seen at the PR head: an author whose pre-3.5 affiliation was "Former
Name", with no ROR ID from the old plugin, and who holds the ROR the
upgrade matched by that name (the record is now called "University
Mental Health Research Institute"), gets no line in the CSV.

## Impact

- **Lost**: the repair, for these authors. The name-derived ROR, which
  the issue names as the main harm, stays on the author and on the
  article page, and goes out with every DOI deposit.
- **Who**: sites upgraded with 3.5.0-5 or earlier, for each author
  whose affiliation matched exactly one ROR name at the upgrade, had no
  ROR ID from the old plugin, and whose organization has since changed
  its ROR display name or a label in that language. The registry
  changes every month, and these sites upgraded between June 2025 and
  November 2026.
- **Way round**: none from the tool. The administrator would have to
  look for affected authors with SQL.

Medium: the result is silently wrong for a few authors, in a state that
comes about rarely. It would be high if renames turned out to be common
in the registry over a year.

## Steps to reproduce

On an OJS 3.5 install upgraded by 3.5.0-5 or earlier, with the ROR registry downloaded (the default test dataset holds a complete copy):

1. Pick an author. Give them the pre-3.5 state: an `author_settings`
   `affiliation` "Former Name" (`en`), no `rorId`. Give them what the
   upgrade left: one `author_affiliations` row with `ror` =
   `https://ror.org/02d439m40` and no name. The registry copy names
   that record "University Mental Health Research Institute", so it no
   longer matches "Former Name".
2. From the OJS root, run `php lib/pkp/tools/repairRorAffiliations.php`.

**Expected**: the author is listed, as `review` at least, because their
ROR was derived from a name and the tool can no longer tell which one.

**Observed**: no line for the author. The counts include the author in
"Checked" only.

## Cause

`classify()` (pkp-lib `a3da55ce64`, `tools/repairRorAffiliations.php`)
rebuilds the upgrade's matches from `$nameMatches`, which is computed
from today's `ror_settings` names. The cache keeps only `ror_display`
and `label` names (`UpdateRorRegistryDataset`), so a renamed record's
old name is gone. With no match, `$matchedRors` is empty, and the
stored `[R]` equals neither a buggy shape nor the repaired names-only
shape. In the `else` branch, `$stillGuessed` (from `$matchedRors`) is
empty, and `$plugInRorMissing` is false because there is no plugin ROR,
so `continue` drops the author. The PR's comment ("or a ROR name changed
since the upgrade's registry") covers this case only for authors who
have a plugin ROR.

## Proposed fix

In the `else` branch, also list any stored ROR that the legacy data does
not account for (neither a name match today nor the plugin ROR):

```diff
                 $plugInRorMissing = $rorIsKnown && !in_array($plugInRor, $currentRors, true);
-                if (empty($stillGuessed) && !$plugInRorMissing) {
+                // a ROR the legacy data no longer explains: matched by a name ROR has changed since the upgrade, or chosen later
+                $unexplained = array_diff(array_filter($currentRors), $matchedRors, [$plugInRor]);
+                if (empty($stillGuessed) && !$plugInRorMissing && empty($unexplained)) {
                     continue;
                 }
                 $action = 'review';
                 $reasons = array_filter([
                     !empty($stillGuessed) ? 'name-derived ROR still present' : null,
                     $plugInRorMissing ? 'ROR plugin ROR missing' : null,
+                    !empty($unexplained) ? 'ROR not found from the legacy data' : null,
                 ]);
```

Tried on `stable-3_5_0` at the PR head with
[`fix.diff`](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13794/fix.diff):
the author is listed as `review`, "ROR not found from the legacy data".
The four other cases of the check give the same lines as before.

**Alternatives**:
- Keep the tool as it is and add a sentence to the issue saying that
  authors whose ROR organization was renamed since the upgrade are not
  found.

**What goes with it**:
- A `review` line changes nothing. The cost is noise: an author an
  editor gave a ROR by hand after the upgrade is listed too, and the CSV
  shows the legacy name beside the ROR, so the administrator can tell
  quickly.
- Test: the kept check
  [`new-shapes.js`](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13794/new-shapes.js)
  (`renamed`).

Small: a few lines in `classify()`.
