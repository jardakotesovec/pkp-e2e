## Summary

Round 2 fixes most of round 1. Each exported reference now shows its
number ("2. Beta, B. …"), so "[2]" and "[4]" match the list, and a
citation edited in "Selected Element" › "In-text citation" › "Update"
becomes `custom` and keeps its text ("(2023)" stays "(2023)").

Two ways of writing a citation still lose its text in the export, because
the export decides by the citation's mode rather than by its text:

- **Dropping a reference onto a year already in the text.** An editor
  types "Smith (2021) found yams." and drops Beta onto "(2021)". The
  editor turns that bracketed text into a citation that keeps "(2021)",
  in mode `generated`. The galley reads "Smith (2) found yams."
  This is the editor's own way of linking an author–year text, so it
  is the path most likely used for years. Not every generated citation
  reads `[id]`.
- **Dropping a reference onto an edited citation.** The editor merges the
  reference into the citation and rewrites its text to the reference ids
  ("(2023)" becomes "(54; 51)"), but the mode stays `custom`. The export
  leaves custom text alone, so the galley publishes the database ids
  "(54; 51)" beside "(Reference 4; Reference 1)". Round 1 exported this
  as "(4; 1)". This break is new in round 2.

## Impact

- **Lost**: the year written in the text, replaced in the HTML and PDF
  galleys by a list number with no warning; and, after a merge, the
  published citation shows internal database ids.
- **Who**: every OJS journal that links author–year citations by dropping
  references onto them, or adds a reference to a citation it edited.
  Readers of the galleys meet it.
- **Way round**: insert the citation away from the year and type the year
  in "Selected Element", or delete and re-insert an edited citation
  before adding a reference to it.

Medium: a published text is silently wrong on an ordinary editing path.
There is a way round once the editor knows about it, which keeps it
from high.

## Steps to reproduce

Preconditions: PKP's default dataset, OJS `main`, with the three PRs'
heads checked out and built.

1. Sign in as `dbarnes` and open submission 15, "Yam diseases and its
   management in Nigeria" (Production).
2. Under the version, open "References" and add four references:
   "Alpha, A. (2020). First reference.", "Beta, B. (2021). Second
   reference.", "Gamma, G. (2022). Third reference.", "Delta, D. (2023).
   Fourth reference.".
3. Open "Body Text" and type "Smith (2021) found yams.". From the side
   panel's "References", drag "Beta, B. …" onto "(2021)". The text stays
   "(2021)", now a citation.
4. Press Enter and type "Jones found more.". Drag "Delta, D. …" to its
   end; the citation reads "[n]". Click it, open "Selected Element", set
   "In-text citation" to "(2023)" and press "Update".
5. Press "Save", then "Export" › "Export to HTML", and open the "HTML"
   galley.
6. Back in "Body Text", drag "Alpha, A. …" onto the "(2023)" citation.
   "Save", "Export to HTML" again, and open the galley.

**Expected**: "Smith (2021) found yams." and "Jones found more.(2023)"
(step 5). After step 6: "Jones found more.(4; 1)", the list numbers of
Delta and Alpha.

**Observed** (the drive's run `r2`, reference ids 51–54):

```
step 5: Smith (2) found yams.
        Jones found more.(2023)
        2. Beta, B. (2021). Second reference.
        4. Delta, D. (2023). Fourth reference.
step 6: Jones found more.(54; 51) (Reference 4; Reference 1)
```

In the editor, step 3's citation is `generated` and reads "(2021)". Step
6's reads "(54; 51)" and is still `custom`.

## Cause

`src/components/BodyTextEditor/bodyTextReferenceExport.js`,
`exportBodyTextReferences()`, renumbers a citation unless it has
`data-citation-mode="custom"`, and `customCitationTextCommand.js` sets
`custom` only when "Selected Element"'s "Update" changes the text. The
check assumes that a `generated` citation reads `[id]` and a `custom`
one never does. `@sciflow/editor-core` breaks that assumption both ways
(`features/citation/index.js`):

- A drop onto text calls `getDropTargetRange()`, which takes the
  bracketed span or the word under the pointer. `runInsertCitation()`
  then makes a citation with that text (`text: replacementRange.text`)
  and `citationMode: 'generated'`.
- A drop onto a citation calls `mergeCitationWithId()`, which rewrites
  the text with `citationContentWithIds()` ("(54; 51)") and keeps the
  node's attributes, `custom` included.

## Proposed fix

Decide by the text, not the mode. Rewrite a marker only when its digits
are the citation's own reference ids, as the editor writes them ("[54]",
"(54; 51)", "[54, 51]"), whatever the mode. Pass the ids to
`updateNumericCitationMarker()` and return when `marker.match(/\d+/g)`
differs from them (for a range, compare its two ends with the first and
last id). A typed or dropped-on year never equals the ids, and a merged
custom citation's ids do. With this check the export no longer needs
the mode, so `customCitationTextCommand.js` (which patches SciFlow's
`commands` getter with a Proxy) can stay for SciFlow's own use of
`custom` or be dropped.

The diff is `shared/playwright/checks/sync/ui-library-1053/fix2.diff`
(relative to the OJS root, one file, 16 lines). Tried 2026-11-11 at the
round-2 heads with `bin/try-fix.js`:

- `year.js` (run `fix2`): "Smith (2021) found yams.", "(2023)" kept,
  and the merged citation exported as "(4; 1)".
- `cite.js` (run `cite-fix2`): "[2]", "[4]", "[2, 4]" and "(2021)",
  numbered "2. Beta …" and "4. Delta …", the PDF with 5 links, the
  deleted-reference refusal (U48 A27) unchanged.

A unit test of `exportBodyTextReferences()` would cover all three: a
`generated` citation "(2021)", a `custom` citation "(34; 12)" citing 34
and 12, and a `custom` "(2021)".

Small: one file in ui-library, plus a unit test.

Still as in round 1, outside this finding: A27 (a citation to a deleted
reference stops every export) and A28 ("[2, 4] (Reference 2; Reference
4)") wait for the team's answer. The JATS `<body>` still repeats the
cited references after "Export to HTML" (low; the jatsTemplate's to
decide).
