# The Users XML import fix refuses dates it used to accept, and reports roles that are already in place

Intention gap. OJS and OMP at the PR heads, before the merge: pkp/pkp-lib#13414
at `ddfcf362ca` (on pkp-lib `main` `8b79730431`), pkp/ojs#5872 at
`c8a24a81a9` (submodule-only), omp `8994baaf1` with lib/pkp at the PR head;
issue pkp/pkp-lib#13412. Introduced by the PR (compared with `main`
`8b79730431`). stable-3_5_0: not driven (pkp/pkp-lib#13413 is the same
change for that branch). Tracked in the import & export spec (U63 A19, A20,
A21) and the companion's ci-triage row. Temporary: delete once acted on.

## Summary

The PR fixes both problems of #13412: an empty role date no longer fails
the import, and a role with a future start date is added once however often
the file is imported. It also checks role dates and periods more strictly,
and three kinds of file that imported quietly on `main` now come back with an
error line:

1. A date written in another common way, such as `2024-01-05T09:30:00`,
   `2024-1-5` or `2024-01-05 09:30`, is refused as "not a valid date".
   The role is dropped, although these imported with the right date
   before. The issue only asks to refuse a date that cannot be parsed.
2. A file that gives a role with no dates is reported as an "overlapping
   period" when the user already holds that role with an end date still to
   come. The issue says an existing row covering today counts as already
   imported.
3. The app's own export cannot be imported back into the same journal when
   an older role (from before start dates were stored) has been ended. The
   export writes the end date alone, and the import refuses it as "start
   date is not before its end date".

## Finding 1 — Dates in other spellings are refused and the role is dropped

### Impact

Managers who import users from a file made by another tool (a spreadsheet
export, a script) that writes dates as ISO 8601 with a `T`, without leading
zeros, or without seconds. Each such role is left out with the line "…
has not been imported because its start or end date is not a valid date
(YYYY-MM-DD or YYYY-MM-DD HH:MM:SS).". The users themselves are created
without it. The line does say what to do, so the manager can fix the file
and import it again. On OJS's command-line import (`tools/importExport.php`)
nothing is printed at all, and the roles are simply missing. Minor: the
refusal is reported on the screen, but it drops data that imported
correctly before.

### Steps to reproduce

Preconditions:
- A fresh OJS install with a journal and its Journal Manager.
- A users file with three new users, each given "Section editor" with one
  of these start dates:
  `<date_start>2024-01-05T09:30:00</date_start>`,
  `<date_start>2024-1-5</date_start>`,
  `<date_start>2024-01-05 09:30</date_start>`.

1. As the Journal Manager open Tools › "Import/Export" › "Users XML Plugin".
2. On "Import Users", upload the file and press "Import Users".
3. Open Settings › Users & Roles › "Users".

**Expected** (as on `main`): "The import completed successfully. …". Each
user holds "Section editor" from 2024-01-05 (09:30, 00:00 and 09:30).

**Observed**: "Import/Export errors:" with three lines "The role "Section
editor" of the user "…" has not been imported because its start or end date
is not a valid date (YYYY-MM-DD or YYYY-MM-DD HH:MM:SS).". The three
accounts exist, but none of them holds the role. On a press the same happens
with "Series editor".

### Cause

`UserXmlPKPUserFilter::getRoleDate()` accepts only a text that
`DateTime::createFromFormat('!Y-m-d H:i:s' | '!Y-m-d')` formats back to
exactly the same text. Before, the text went straight into
`UserUserGroup::create()`, whose `datetime` cast parses it with Eloquent's
`asDateTime()` (`Y-m-d` with one- or two-digit month and day, else
`Carbon::parse()`). That cast accepted all three spellings. The command-line
path (`PKPUserImportExportPlugin::executeCLI('import')`) never prints
`$filter->getErrors()`. This predates the PR, but the PR adds three more
reasons that it drops without a word.

### Proposed fix

A proposal, for the team to decide:
- Keep the strict check only to reject roll-overs such as 2027-02-30. For
  anything else, fall back to `Carbon::parse()` in a `try`, and count the
  date invalid only when that throws.
- Or keep the two formats and state them in `pkp-users.xsd` (a pattern on
  `date_start`/`date_end`), so a file is refused before anything is
  imported rather than role by role.
- Separately, have the command-line import print the filter's errors.

## Finding 2 — A file with no dates is reported as overlapping a role that ends later

### Impact

Managers who import a user list without role dates (a hand-made file, or one
from before 3.5) for users who already hold the role with an end date still
to come, such as an editor appointed until the end of 2027. The Results tab
reads "Import/Export errors: The role "Section editor" of the user "…" has
not been imported because the user already holds this role in an
overlapping period.". Nothing is changed, and nothing needed to be. The
success sentence is gone, and the manager is told something went wrong when
it did not. Minor: a misleading message, no data lost.

### Steps to reproduce

Preconditions:
- A fresh OJS install with a journal and its Journal Manager.
- File 1: a new user given "Section editor" with
  `<date_start>2020-01-01 00:00:00</date_start>` and
  `<date_end>2027-12-31 00:00:00</date_end>`.
- File 2: the same user given "Section editor" with no `<date_start>` and
  no `<date_end>`.

1. Tools › "Import/Export" › "Users XML Plugin" › "Import Users": import
   file 1. It reads "The import completed successfully. …".
2. Import file 2.

**Expected** (as on `main`, and as the issue states: "If the file gives no
start date, an existing row covering today counts as already imported"):
"The import completed successfully. …", with the user holding the one role
from 2020-01-01 to 2027-12-31.

**Observed**: "Import/Export errors: The role "Section editor" of the user
"…" has not been imported because the user already holds this role in an
overlapping period.". The one role is unchanged. Control: when the existing
role has no end date, file 2 imports silently.

### Cause

When the file gives no start date, `$alreadyImported` requires
`$existing->dateEnd === null || ($dateEnd !== null && $existing->dateEnd >=
$dateEnd)`. An existing row that covers today but has an end date fails that
test when the file gives no end date either.

### Proposed fix

A proposal: when the file gives no end date, count any overlapping row that
has started by today as already imported. The overlap query already ensures
it has not ended. That is, `$dateEnd === null || $existing->dateEnd === null
|| $existing->dateEnd->toDateTimeString() >= $dateEnd` in the no-start
branch.

## Finding 3 — The app's own export of an ended older role is refused when imported back

### Impact

Sites upgraded from 3.4 or earlier, whose older roles have no start date. A
manager ends such a role, exports the users (the export writes
`<date_end>` and no `<date_start>`), and imports the file back into the
same journal, for example to test a round trip or to restore after a
mistake. The Results tab reads "The role "Section editor" of the user "…"
has not been imported because its start date is not before its end date. A
missing start date means the day of the import.". Nothing is changed. Into
another journal, that past term of the role is not carried over. The issue
rules "a past end date with no start date" an error, and this is the one
place the application writes that shape itself. Minor: a misleading line on
a same-journal round trip, and a lost past term on a move between journals.

### Steps to reproduce

Preconditions (a person reaches them on a site upgraded from 3.4; on a
fresh install one database update stands in for the upgrade):
- A journal where a user holds "Section editor" with no start date and an
  end date in the past. On a fresh install: import the user with the role,
  then set that row's `date_start` to NULL and `date_end` to `2026-01-01
  00:00:00` in `user_user_groups`.
- The same user also holds a current role (the "Export Users" list shows
  only users with a current role), such as "Reader".

1. Tools › "Import/Export" › "Users XML Plugin" › "Export Users": tick the
   user and press "Export Users". The file's "Section editor" entry reads
   `<date_end>2026-01-01 00:00:00</date_end>` with no `<date_start>`.
2. "Import Users": import that file into the same journal.

**Expected** (as on `main`): the ended role recognised as already there, and
no line about it. The other lines of the Results tab (the password notice
for existing accounts) are unchanged by the PR.

**Observed**: in addition, "The role "Section editor" of the user "…" has
not been imported because its start date is not before its end date. A
missing start date means the day of the import.". The rows are unchanged.
Control: a legacy role with neither date round-trips with no line.

### Cause

`$dateStart ??= Core::getCurrentDate()` runs before the period check, so an
entry with only a past `<date_end>` fails `$dateStart >= $dateEnd` and is
skipped before the existing rows are looked at.
`PKPUserUserXmlFilter::addUserUserGroups()` writes `<date_start>` only
`if ($userUserGroup->dateStart)`, and `I9462_UserUserGroupsStartEndDate`
added the column as nullable with no backfill.

### Proposed fix

A proposal:
- Before the period check, look for an existing row of the same group with
  `date_start` NULL and the file's `date_end`. When there is one, skip the
  entry silently as already imported.
- Or have the export write `date_start` for such a row (which date to write
  is the team's call).
