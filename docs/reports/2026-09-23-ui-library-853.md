# A review closed quickly after "Read Review" still shows as unread in the Reviewers table and on the dashboard

Regression. OJS at `802202cb3e` with lib/ui-library at `cab09538`, the
head of pkp/ui-library#853 (open, for issue pkp/pkp-lib#13359, driven
2026-09-23 before its merge); not present at the tip's lib/ui-library
`2034439a`. OMP and OPS: not yet (their lib/ui-library pointers,
`977e460c` and `5d138aa9`, predate the change); the same code reaches
them with their next submodule update. stable-3_5_0: does not carry the
change. Tracked in spec U27 register A32 and the companion row
`optimize-table-reloads` in `docs/tracking/ci-triage.md`. Temporary:
delete once acted on.

## Summary

Opening a submitted review ("Read Review" in the workflow's Reviewers
table, or "View unread recommendation" on the dashboard) marks it as
read. With the change, the table behind the window picks that up only if
the mark has already reached the server when the window closes. An
editor who closes the window sooner still sees "Review Submitted" in the
Reviewers table, and still sees "View unread recommendation" on the
dashboard, until the page is reloaded. Before the change the table always
caught up once the mark was saved.

## Impact

It affects editors who open a completed review and close it again
quickly: to check which reviewer it was, or after opening the wrong row.
On a quick server the window has to close within a fraction of a second.
On a slow server or connection that grows to a second or more. The
review is marked as read on the server, so nothing is lost and a page
reload shows the right state. Until then the table tells the editor that
a review they have already seen is new, which can send them back to
reread it or keep a dashboard indicator looking unread. Minor: the stored
state is right and a reload corrects the display, but the wrong label is
exactly what the "unread" marker exists to prevent.

## Steps to reproduce

Preconditions:

- A fresh OJS install with its default languages.
- A submission in review, with one reviewer who has submitted a review
  with a recommendation (the Reviewers row reads "Review Submitted").
- A Journal Manager or editor assigned to the submission.
- In the browser's developer tools, Network › throttling set to
  "Slow 4G" or "3G". This only stretches the mark-as-read request, so
  a person has time to close the window before it answers. On a quick
  local install the window has to close within a fraction of a second.

1. As the editor, open the submission's workflow in the review stage.
   The reviewer's row reads "Review Submitted".
2. Press the row's "Read Review". The "Review Details: {title}" window
   opens.
3. As soon as the review text shows, press "Cancel".
4. Look at the reviewer's row.
5. Reload the page and look at the row again.

For the dashboard: on "Active submissions", open the submission row's
"Review completed on {date}" indicator. Press "View unread
recommendation", then "Cancel" as in step 3, and open the indicator
again.

**Expected** (as before the change, and as the issue asks: something
changed in the window, so the table reloads): after step 3 the row reads
"Review Viewed". On the dashboard the popover offers "View
recommendation".

**Observed:** after step 3 the row still reads "Review Submitted", and
nothing reloads. After step 5 it reads "Review Viewed". On the dashboard
the list reloads when the window closes but still shows "View unread
recommendation"; after a page reload it shows "View recommendation".

Control: with the same steps at the tip's lib/ui-library, the row reads
"Review Viewed" right after "Cancel". The dashboard popover offers "View
recommendation".

## Cause

`useReviewDetails.js` used to reload the opener after the mark-as-read
answered (`loadReviewAssignment().then(async () => { if (await
markViewedIfNew()) onDataChangedFn(); })`). The PR removes that
(`loadReviewAssignment().then(markViewedIfNew)`) and relies on the
modal's new `dataChanged` flag instead. `useFetch` sets that flag through
`modalStore.markModalDataChanged()` only after the POST
`…/reviewAssignments/{id}/consider` has answered.
`closeSideModalById()` reads the flag at the moment of closing. A POST
that answers after the close flags a modal that is already closed, so
the workflow's Reviewers table, whose `onClose` is now
`triggerDataChange`, does not reload. The dashboard passes an
unconditional `refetchCallback`, so it does reload at the close. That
reload can go out before the POST (in the failing trace, the list GET at
+0 ms and the POST at +18 ms), and it reads the review as unread.

## Proposed fix

A proposal; the team decides.

- Smallest: in `useReviewDetails.js`, when `markViewedIfNew()` answers
  after the window has closed, call the opener's reload as the removed
  `onDataChangedFn` did. The workflow and the dashboard both catch up.
- In `useReviewDetails.js`, mark the modal changed when the mark-as-read
  is sent rather than when it answers, and have the close wait for that
  request before calling `onClose`. One reload, after the mark, and no
  stale list on the dashboard either.
- General: `useFetch` marks the modal changed when a write is sent, and
  `closeSideModalById()` waits for the modal's writes in flight before
  `onClose`. This covers every write that can outlive its window, at the
  cost of a slower close while a write is pending.
