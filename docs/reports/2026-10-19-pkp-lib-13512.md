## Summary

`pkp/pkp-lib#13512` makes the apps check that an uploaded picture
really is a picture before storing it. In three places it refuses
the file after part of the save has already been written:

1. A manager replaces a highlight's picture with one the check
   refuses. The save shows "There was an error uploading this image.",
   but the old picture is already deleted. The home page's slideshow
   then shows that highlight as an empty grey band, without its
   picture, title, text or button, until the manager uploads a new
   picture.
2. A category's picture is stored as a file with no extension
   (`8-category` instead of `8-category.png`). It still shows
   everywhere, so nothing is lost on screen.
3. A program that creates a new version through the REST API with a
   cover image the check refuses gets an error, but the version is
   created anyway, without the cover. No screen sends a cover with
   that request.
4. A program that saves one uploaded cover picture under two
   languages gets a server error, and a copy of the picture is left
   in the journal's public folder. Sent with a new version, the
   version is created anyway. No screen sends one picture twice.
   (Added 2026-10-21.)

A question for the team closes the report: the check also refuses a
real picture whose name has the wrong extension, such as a PNG named
`cover.jpg`. Until this change, that file was accepted.

## Finding 1 — A refused replacement picture deletes the highlight's old picture and blanks its slide

- **Severity** medium
- **Effort** small
- **Kind** regression
- **Affects**
  - main: OJS, OMP, OPS
  - 3.5: OJS, OMP, OPS
  - 3.4: none (code; the change is not on `stable-3_4_0`)
  - 3.3: none (code; no Highlights)

### Impact

- **Lost**: the highlight's picture, deleted from the server, and its
  slide on the home page, which becomes an empty grey band without
  its title, text or button. The error message
  says only that the upload failed, not that the old picture is gone.
- **Who**: a journal, press or server manager editing a highlight on
  Settings › Website › "Setup" › "Highlights", with a file the check
  refuses: a picture whose name's extension does not match its
  contents (a PNG named `.jpg`), or a file that is not a picture.
- **Way round**: upload a picture the check accepts; it replaces the
  broken one. Nothing tells the manager that this is needed.

Medium: the refusal is shown, but it silently removes a picture that
readers see on the home page, and only a narrow input reaches it. It
would be high if mismatched names turned out to be common among
uploaded pictures.

### Steps to reproduce

Preconditions:
- The default dataset, OJS `main` (also OMP and OPS, and
  `stable-3_5_0`). The journal has no highlights.
- Three files: `photo.png` (any PNG picture), `photo2.png` (another
  PNG picture) and `photo.jpg` (a copy of `photo2.png` renamed to
  `.jpg`; its contents stay PNG).

1. Sign in as `rvaca` on the journal's login page
   (`/index.php/publicknowledge/login`).
2. Open Settings › Website › "Setup" › "Highlights" and press "Add
   Highlight".
3. Fill in "Title" "Spring issue", "Description" "Read the spring
   issue.", "URL" `https://example.org/` and "Button Label" "Read".
   Under "Image" press "Upload File", choose `photo.png`, and press
   "Save". The panel closes, and the journal's home page shows the
   picture in its slideshow (the control).
4. On the "Spring issue" row press "Edit". Under "Image" press
   "Remove", then "Upload File", choose `photo.jpg`, and press "Save".
5. Close the panel, reload the page, and press "Edit" on the row
   again.
6. Open the journal's home page (`/index.php/publicknowledge`).

**Expected**: either the new picture is stored and shown, as it was
until 2026-10-16, or it is refused and the highlight keeps
`photo.png`.

**Observed**:
- Step 4: the save answers 400 and the panel stays open, with "There
  was an error uploading this image." under the picture, twice:

  ```
  PUT /index.php/publicknowledge/api/v1/highlights/1   400
  {"image":"There was an error uploading this image."}
  ```

  By then `1.png`, the old picture, is gone from the journal's
  `public/journals/1/highlights/` folder, which is empty, and the
  highlight's stored image is `{"temporaryFileId":2}`.
- Step 5: the "Image" box is empty, with only "Upload File".
- Step 6: the slideshow's slide for "Spring issue" is an empty grey
  band: no picture (`<img src="…/public/journals/1/highlights/?">`), and
  neither its title, its text nor its button shows. The server
  logs, for each view of the page:

  ```
  PHP Deprecated:  strtotime(): Passing null to parameter #1 ($datetime) of type string is deprecated in lib/pkp/classes/highlight/Highlight.php on line 81
  ```

OMP and OPS show the same (`…/presses/1/highlights/?`,
`…/contexts/1/highlights/?`). Replacing the picture with `photo2.png`
under its own name works: it is stored and shown.

### Cause

`PKP\highlight\Repository::edit()` (lib/pkp
`classes/highlight/Repository.php`) writes in this order:

```php
$this->dao->update($newHighlight);            // line 189: the request's image, {"temporaryFileId": N}
…
if ((!$image || $hasNewImage) && $highlight->getImage()) {
    $this->deleteImage($highlight);           // line 195: the old picture's file
}
if ($hasNewImage) {
    $this->handleImageUpload($newHighlight);  // stores the file and the image's real record
}
```

`07bc43fe67` adds the type check inside `handleImageUpload()`, after
both writes:

```php
if (!$temporaryFileManager->isValidImage($temporaryFile)) {          // lines 273-274
    throw new StoreTemporaryFileException($temporaryFile, $filePath, $user, $highlight);
}
```

The same commit removes `Repo::highlight()->delete($highlight)` from
`HighlightsController::edit()`'s `catch`. Before, that line deleted the
whole highlight whenever storing failed; it had no refusal of a real
picture to answer. So a refusal now leaves the highlight saved with
the request's `{"temporaryFileId": N}` and no file.
`Highlight::getImageUrl()` builds the address from the missing
`uploadName` and `dateUploaded`, hence `…/highlights/?`. The rule that
breaks: a refusal comes before anything is written. The same
`validate()` already applies that rule to a missing temporary file
(`ValidatorFactory::temporaryFilesExist()`).

Reach:
- Adding a highlight with a refused picture: clean.
  `HighlightsController::add()` deletes the new highlight in its
  `catch` (code).
- The site's highlights (Administration › Site Settings): the same
  code, but no site highlight can be saved today (U11 A5) (code).
- Announcements: `Announcement::save()` follows the same order: it
  saves, then `deleteImage()`, then `handleImageUpload()`, which
  refuses. Checked through the REST API on the three apps: an
  announcement's picture replaced by `photo.jpg` answers 400, the
  announcement keeps `{"temporaryFileId": N}` as its image, and the
  old file stays on disk, now referenced by nothing. This is not a
  regression. Announcements have refused such files since 2023, and
  until `07bc43fe67` that refusal deleted the whole announcement (the
  removed line carried the comment "TODO do we really need to delete
  an announcement if the image upload fails?").
- A publication's cover (OJS issue entry, OMP catalog entry, OPS
  preprint entry): clean. `Publication\Repository::edit()` moves the
  files before it writes, and a refused cover leaves the earlier one
  stored (walked through the REST API).

### Proposed fix

A proposal, tried (below); the team decides. Refuse the picture in
`validate()`, before any write, with the rule the store applies. A new
`ValidatorFactory::temporaryFilesAreImages()` sits beside
`temporaryFilesExist()` and follows its shape. A temporary file that
`getImageExtension()` does not know, or that `isValidImage()` refuses,
becomes the field error `api.400.errorUploadingImage`, the message the
manager sees today. `PKP\highlight\Repository::validate()` and
`PKP\announcement\Repository::validate()` call it for `image`. The
check in `handleImageUpload()` stays as the store's own guard. This
follows `PKP\category\Repository::validate()`, which refuses a
category picture of the wrong type in the same way before anything is
saved.

```php
// classes/highlight/Repository.php, validate(), after temporaryFilesExist()
ValidatorFactory::temporaryFilesAreImages($validator, ['image'], [], $props, $allowedLocales, $user?->getId());
```

The diff, with findings 2 and 3, is
[fix-followup.diff](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13512/fix-followup.diff),
for pkp-lib, applied at the app root.

Tried on OJS, OMP and OPS `main`, on the default dataset loaded fresh.
Step 4 answers 400 with `{"image":["There was an error uploading this
image."]}`, the message shows under the picture as before, and
`photo.png` stays: on disk, in the reopened panel and in the
slideshow. Neighbour checks in the same trial: replacing the picture
with `photo2.png` stores and shows it, and an announcement edited with
`photo.jpg` answers 400 and keeps its picture.

**Alternatives**:
- Reorder `edit()`: check and store the new picture before deleting
  the old one. This fixes the highlight but not announcements, and the
  error would still come from the store, not from the form's checks.
- Restore the deletion in the controller's `catch`. That loses the
  whole highlight, which is worse than losing its picture.

**What goes with it**:
- REST API: a refused picture answers 400 with the field error in the
  validation shape (`{"image":["There was an error uploading this
  image."]}`, an array), where it now answers a bare string. The
  panel shows the message under the picture either way (tried).
- Data repair: none by code. A highlight broken since 2026-10-16 (on
  3.5 since 2026-10-14) shows a broken slide until a picture is
  uploaded again; its stored image has a `temporaryFileId` and no
  `uploadName`.
- Backport: every hunk but the category one applies to
  `stable-3_5_0` as written (`patch --dry-run`).
- Tests: a unit test for `temporaryFilesAreImages()`, and an e2e guard
  in spec U11 (a refused replacement keeps the earlier picture).

Small: a validation helper in one class and a call in each repository,
following an existing pattern, with a unit test.

## Finding 2 — A category's picture is stored without its file extension

- **Severity** low
- **Effort** small
- **Kind** regression
- **Affects**
  - main: OJS, OMP, OPS
  - 3.5: none (code; categories are saved by the older `CategoryForm`, which names the file itself)
  - 3.4: none (code; the same)
  - 3.3: none (code; the same)

### Impact

- **Lost**: nothing on screen. The picture shows in the "Edit
  Category" window, and the category page shows its thumbnail. The
  full-size file has no extension, so a reader who saves it gets a
  file named `8-category`.
- **Who**: every journal, press or server manager who adds a picture
  to a category on `main`.
- **Way round**: none needed.

Low: a wrong file name that nothing on screen relies on today.

### Steps to reproduce

Preconditions: the default dataset, OJS `main` (also OMP and OPS);
`photo.png`, any PNG picture.

1. Sign in as `rvaca` on the journal's login page.
2. Open Settings › Journal › "Categories" (Settings › Press, Settings
   › Server) and press "Add Category".
3. Fill in "Name" "Maps" and "Path" `maps`. Under "Cover Image" press
   "Upload File", choose `photo.png`, and press "Save".
4. Look at the journal's public folder, or open the category's
   full-size picture,
   `/index.php/publicknowledge/catalog/fullSize?type=category&id=8`
   (OPS: `preprints/fullSize`).

**Expected**: the picture stored as `8-category.png`, as until
2026-10-16.

**Observed**: `public/journals/1/` holds `8-category` and
`8-category-thumbnail.png`. The category's stored image reads
`"uploadName":"8-category"`. The full-size address answers 200 with
`Content-Type: image/png` and `Content-Disposition: inline;
filename="8-category"`. The "Edit Category" window's preview
(`…/public/journals/1/8-category?…`) and the category page's
thumbnail show the picture.

### Cause

`CategoryCategoryController::saveCategory()` (lib/pkp
`api/v1/categories/CategoryCategoryController.php`, line 200) stores
the picture with `moveTemporaryFile($context, $temporaryFile,
$filenameBase, $user)`, without `$isImage`. `07bc43fe67` split
`PKPContextService::moveTemporaryFile()` into two branches. The
non-image branch now takes its extension from `getDocumentExtension()`
alone:

```php
} else {
    $extension ??= $publicFileManager->getDocumentExtension($temporaryFile->getFileType());   // false for image/png
}
$fileName .= $extension;
```

Before, a type `getDocumentExtension()` did not know fell back to
`getImageExtension()` (`if (!$extension || $isImage)`), so a PNG got
`.png`. Between `07bc43fe67` and `042726ebf6` the same save answered
500, because the controller still passed a user id where the method
now takes a `User`. `042726ebf6` fixed the argument and exposed this.

Reach: the category picture is the only caller of
`moveTemporaryFile()` without `$isImage` or `$extension`, in the three
apps (code). The thumbnail is named by the controller's own
`generateThumbnail()` and keeps `.png`. OMP's own
`catalog/fullSize?type=category` reads from another folder and is not
affected by this change.

### Proposed fix

Pass the picture's extension, as the thumbnail and the style sheet
(`extension: '.css'`) already do:

```diff
-            $fileName = app()->get('context')->moveTemporaryFile($context, $temporaryFile, $filenameBase, $user);
+            $fileName = app()->get('context')->moveTemporaryFile($context, $temporaryFile, $filenameBase, $user, extension: $temporaryFileManager->getImageExtension($temporaryFile->getFileType()));
```

`PKP\category\Repository::validate()` has already checked that the
file is a JPEG, PNG or GIF picture, so this stores exactly what was
stored before the change, and adds no new refusal.

Tried on OJS, OMP and OPS `main`: the picture is stored as
`8-category.png`, the "Edit Category" preview and the category page's
thumbnail show it, and the full-size address names
`filename="8-category.png"`. Neighbour check: a PNG named `photo.jpg`
is still accepted and stored as `9-category.png`, as before the
change, so the fix adds no refusal.

**Alternatives**:
- `isImage: true`. This also applies the name check (see the
  question). A PNG named `.jpg` would then throw from the store, after
  the controller has already deleted the old picture, and the
  controller does not catch it, so the save would answer 500. If the
  team wants the name check on categories, it belongs in
  `PKP\category\Repository::validate()`, with this line kept.
- Restore the image fallback in `moveTemporaryFile()`'s non-image
  branch. That restores the old behaviour for every caller, but it
  hides the missing flag at the one caller that has it wrong.

**What goes with it**: categories saved on `main` since 2026-10-16
keep their extensionless file. It still shows, so a repair is
optional; saving the picture again stores it with its extension. No
backport is needed. Test: the e2e guard in spec U16 (the stored name
ends in the picture's extension).

Small: one argument at one caller.

## Finding 3 — Creating a version through the REST API with a refused cover answers 400 but creates the version

- **Severity** low
- **Effort** small
- **Kind** regression
- **Affects**
  - main: OJS, OMP, OPS
  - 3.5: OJS, OMP, OPS
  - 3.4: none (code; the change is not on `stable-3_4_0`)
  - 3.3: none (code; the change is not on `stable-3_3_0`)

### Impact

- **Lost**: nothing is lost. A version is added that the request was
  told had failed, without its cover image. The version is created
  without the `Publication::add` hook, and without the submission's
  status and current version being updated afterwards.
- **Who**: programs that create versions through the REST API with a
  cover image. No screen sends a cover with this request: "Create New
  Version" calls `POST …/publications/{id}/version`, which takes no
  cover. The editor sees the extra version in the workflow's
  "Publication" menu.
- **Way round**: delete the extra version. A program that retries
  after the 400 adds one more version on each try.

Low: only the REST API reaches it, and nothing is lost. A client that
retries would make it worse.

### Steps to reproduce

Preconditions: the default dataset, OJS `main` (also OMP and OPS, and
`stable-3_5_0`). Submission 4, "Computer Skill Requirements for New
and Existing Teachers: Implications for Policy and Practice", has one
version. (OMP: submission 3, "The Political Economy of Workplace
Injury in Canada"; OPS: submission 1, "The influence of lactation on
the quantity and quality of cashmere production".)

1. Sign in as `rvaca` and open any page of the journal's settings,
   for example Settings › Website.
2. In the browser's console, send the request a program would send:
   upload a text file as a temporary file, then create a new version
   with that file as its cover. The body is built from a `GET` of the
   current version (OMP: `const id = 3` and `seriesId` for
   `sectionId`; OPS: `const id = 1` and `versionStage: 'AO'`; 3.5:
   `version: current.version + 1` and no `versionStage`,
   `versionMajor` or `versionMinor`). `version: 2` is there because
   the schema still lists `version` as required on `main`:

   ```js
   const id = 4;
   const api = pkp.context.apiBaseUrl;
   const headers = {'X-Csrf-Token': pkp.currentUser.csrfToken};
   const get = async (route) => (await fetch(api + route, {headers})).json();
   const versions = async () => (await get(`submissions/${id}`)).publications.length;
   const before = await versions();
   const current = await get(`submissions/${id}/publications/${(await get(`submissions/${id}`)).currentPublicationId}`);
   const form = new FormData();
   form.append('file', new File(['plain text, not an image\n'], 'notes.txt', {type: 'text/plain'}));
   const temporaryFile = await (await fetch(api + 'temporaryFiles', {method: 'POST', headers, body: form})).json();
   const response = await fetch(`${api}submissions/${id}/publications`, {
       method: 'POST',
       headers: {...headers, 'Content-Type': 'application/json'},
       body: JSON.stringify({
           version: 2,
           versionStage: 'VoR',
           versionMajor: 2,
           versionMinor: 0,
           sectionId: current.sectionId,
           title: current.title,
           abstract: current.abstract,
           coverImage: {en: {temporaryFileId: temporaryFile.id, altText: ''}},
       }),
   });
   console.log(response.status, await response.json());
   console.log('versions before:', before, 'after:', await versions());
   ```

3. Open submission 4's workflow and its "Publication" menu.

**Expected**: either 200 and one new version without a cover, as
until 2026-10-16, or 400 and no new version.

**Observed**: 400, and the version is created anyway:

```
400 {"coverImage":["There was an error uploading this image."]}
versions before: 1 after: 2
```

The "Publication" menu lists "Version of Record 2.0" under the
original "Unassigned version" (OPS: "Author's Original 2.0"). OMP and
OPS show the same; on OPS the new version's stored cover is the
request's `{"temporaryFileId":…}`, with no file behind it. The same
request with a PNG cover named `cover.png`, or with no cover, answers
200 and adds one version.

### Cause

`PKP\publication\Repository::add()` (lib/pkp
`classes/publication/Repository.php`) inserts the publication first
(`$this->dao->insert($publication)`, line 357), then stores its cover
through `_saveFileParam()`. `07bc43fe67` turned that method's quiet
`return null` for a temporary file that is not a picture into a
`throw new StoreTemporaryFileException(…)` (line 1148), and passes
`$isImage` on to `moveTemporaryFile()`, which throws for a picture the
name check refuses (`PKPContextService.php` lines 830-832).
`PKPSubmissionController::addPublication()` catches the exception and
answers 400, but nothing removes the inserted row. The rest of
`add()` (the `Publication::add` hook,
`Repo::submission()->updateStatus()`,
`updateCurrentPublication()`) never runs for it.

Reach: `addPublication()` is the only caller that passes a new cover
to `add()`. `Repo::submission()->add()` creates a submission's first
version without one (code). Editing a version
(`PUT …/publications/{id}`) moves the files before it writes, so a
refused cover leaves the version as it was (walked).

### Proposed fix

The same check as finding 1, in `Publication\Repository::validate()`,
beside the existing `temporaryFilesExist()` call for `coverImage`:

```php
ValidatorFactory::temporaryFilesAreImages($validator, ['coverImage'], ['coverImage'], $props, $allowedLocales, $user?->getId());
```

A refused cover then answers 400 from validation before anything is
inserted, for adding and for editing alike. It is in
[fix-followup.diff](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13512/fix-followup.diff).

Tried on OJS, OMP and OPS `main`: the snippet answers 400 with
`{"coverImage":{"en":["There was an error uploading this image."]}}`
and the versions stay at 1. Neighbour checks in the same trial: the
same request with `cover.png` adds a version with its cover, and with
no cover adds a version; editing a version's cover with `cover.jpg`
still answers 400 and keeps the earlier cover.

**Alternatives**: delete the inserted publication in
`addPublication()`'s `catch`, as `HighlightsController::add()` does
with `getDataObjectId()`. That is three lines, but the version would
still be inserted and removed, and the hooks that watch publications
would see a delete without an add.

**What goes with it**: the 400 body nests the message under the
locale (`{"coverImage":{"en":[…]}}`), as the existing "file not found"
error already does. No data repair is needed beyond deleting
versions added this way. Backport: the hunk applies to `stable-3_5_0` as written. Test: a
unit test with a text file as `coverImage`.

Small: one call to the helper finding 1 adds.

## Finding 4 — One uploaded cover picture named under two languages answers a server error and leaves a stray copy

- **Severity** low
- **Effort** small
- **Kind** regression
- **Affects**
  - main: OJS, OMP, OPS
  - 3.5: OJS, OMP, OPS (walked on OJS; OMP and OPS by the 2026-10-21 claim check)
  - ore: none (code; `07bc43fe67` is not on `ore`)
  - 3.4: none (code; the change is not on `stable-3_4_0`)
  - 3.3: none (code; the change is not on `stable-3_3_0`)

Added 2026-10-21, from the housekeeping session's U49 claim check
(spec U49 [A15](https://github.com/jardakotesovec/pkp-e2e/blob/main/docs/specs/U49-publish-schedule-and-versions.md#a15)).

### Impact

- **Lost**: nothing that was stored. Edited this way, a version keeps
  the cover it had. Created this way, a new version is added anyway,
  as in finding 3, and the request is reported as failed.
- **Who**: programs that save a cover image through the REST API and
  reuse one uploaded picture for two languages. No screen sends one
  picture under two languages: the "Cover Image" field uploads a file
  per language.
- **Way round**: upload the picture once per language. A copy is left
  in the journal's public folder that nothing points to; it can be
  deleted by hand.

Low: only the REST API reaches it, and nothing stored is lost.

### Steps to reproduce

Preconditions: the default dataset, OJS `main` (also OMP and OPS, and
`stable-3_5_0`). The journal has English and French; submission 5,
"Genetic transformation of forest trees", has an unpublished version
(publication 6) with no cover. (OMP: submission 4, publication 4; OPS:
submission 1, publication 1.)

1. Sign in as `rvaca` and open any page of the journal's settings,
   for example Settings › Website.
2. In the browser's console, upload one PNG as a temporary file and
   save it as the version's cover in both languages:

   ```js
   const api = pkp.context.apiBaseUrl;
   const headers = {'X-Csrf-Token': pkp.currentUser.csrfToken};
   const canvas = Object.assign(document.createElement('canvas'), {width: 400, height: 400});
   const png = await new Promise((resolve) => canvas.toBlob(resolve, 'image/png'));
   const form = new FormData();
   form.append('file', new File([png], 'cover.png', {type: 'image/png'}));
   const temporaryFile = await (await fetch(api + 'temporaryFiles', {method: 'POST', headers, body: form})).json();
   ```

3. Read the version back (`await (await fetch(api +
   'submissions/5/publications/6', {headers})).json()`, its
   `coverImage`) and list the journal's public folder
   (`public/journals/1/`).

**Expected**: either 200 with the picture stored for both languages,
or 400 naming the problem, and no file left behind.

**Observed**: 500. The version has no cover, as before, and
`submission_5_6_coverImage_en.png` is in the journal's public folder
with nothing pointing to it. The server log shows a PHP error raised
while building `StoreTemporaryFileException`. Sent as `POST
…/submissions/5/publications` (a new version, finding 3's request
with this cover), the answer is also 500, and the version is created.
Until 2026-10-16 (3.5: 2026-10-14) the same `PUT` answered 200 and
stored the English cover, dropping the French one without a word.

### Cause

`Publication\Repository::edit()` and `add()` call `_saveFileParam()`
once per language. `validate()` checks each language's
`temporaryFileId` (`ValidatorFactory::temporaryFilesExist()`) before
either call, so one file named twice passes. The first language's
`moveTemporaryFile()` moves the file into the public folder and
deletes the temporary file. For the second language,
`getFile()` returns null, and `07bc43fe67` made that case
`throw new StoreTemporaryFileException($temporaryFile, …)`
(`classes/publication/Repository.php`, line 1148 at `042726ebf6`).
The constructor is typed `TemporaryFile`, so passing null raises a
PHP error, which the controllers' `catch (StoreTemporaryFileException)`
does not catch. Before the change, `_saveFileParam()` returned null for
a missing file.

### Proposed fix

Refuse a temporary file named under more than one language in
`ValidatorFactory::temporaryFilesExist()`, so the request answers 400
before anything is moved:

```php
$seenTemporaryFileIds = [];
foreach ($allowedLocales as $localeKey) {
    // … the existing checks …
    $temporaryFileId = (int) $props[$uploadProp][$localeKey]['temporaryFileId'];
    if (in_array($temporaryFileId, $seenTemporaryFileIds)
        || !$temporaryFileManager->getFile($temporaryFileId, $userId)) {
        $validator->errors()->add($uploadProp . '.' . $localeKey, __('common.noTemporaryFile'));
    }
    $seenTemporaryFileIds[] = $temporaryFileId;
}
```

It is in
[fix-one-file-two-languages.diff](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-13512/fix-one-file-two-languages.diff).
Tried on OPS `main` (lib/pkp `042726ebf6`): the `PUT` and the `POST`
answer 400 `{"coverImage":{"fr_CA":["The file you uploaded could not
be found. Please try to upload it again."]}}`, no file is left behind,
and the `POST` adds no version. The controls in the same trial (one
PNG under English only; two PNGs, one per language) still store their
covers.

**What goes with it**: the helper also guards the context's
multilingual pictures, which move one temporary file per language the
same way (not walked). The message is the existing "file not found"
one; a message of its own would need a new locale key. Not tried with
`fix-followup.diff` applied as well; the two touch different lines.

Small: four lines in one helper.

## Question — Is refusing a correctly-typed picture with a mismatched name intended?

The check the change adds, `FileManager::isValidImage()`, accepts a
file only when its name's extension matches its contents (`.jpeg`
counts as `.jpg`). It now guards the cover image, the context's and
the site's logos, favicon, homepage image and thumbnails, and
highlights. Announcements have had it since 2023. The facts:

- A real PNG uploaded as `cover.jpg` and saved as a version's cover
  through `PUT …/publications/{id}` answers 400 "There was an error
  uploading this image." on the three apps, `main` and 3.5, and the
  earlier cover stays. Until 2026-10-16 (3.5: 2026-10-14) it was
  stored, as a `.png` cover (`submission_4_23_coverImage_en.png` in
  the walk before the change). The same PNG named `cover.png` is
  stored. A highlight's `photo.jpg` (finding 1) is the same case.
- The issue asks that settings uploads "should be checked for type"
  so that a file of the wrong type ("Expected Result: The file should
  be rejected.") never reaches the public folder. A PNG named `.jpg`
  is a picture of the right kind. The server stores it under the
  extension its contents give (`.png`), whatever its name.
- `pkp/pkp-lib#12744` (open) reports the same name check refusing
  `.jpeg` announcement pictures. The new check accepts `.jpeg`, but
  still refuses `.jpe`, `.jfif` and a name with no extension (code).

The campaign's reading is that this strictness is intended, a cheap
guard against disguised files. If it is, the message could say what
to do ("The file's name does not match its type. Rename it to .png
and upload it again."), since "There was an error uploading this
image." does not tell the manager what went wrong. If it is not
intended, `isValidImage()` can drop the name comparison and keep the
`getimagesize()` and content-type checks. The fix above follows
either answer.
