## Finding 1: the site-level Comments page address answers a server error

Open `/index.php/index/management/settings/userComments` (the site, not
a journal), signed out or as the Site Administrator. The answer is `500`
with an empty page, and the server log reads:

```
PHP Fatal error:  Uncaught Error: Call to a member function getData() on null in …/lib/pkp/pages/management/ManagementHandler.php:108
```

Before the PR a visitor signed out was sent to Login and the Site
Administrator to "No journal was found that matched your request.".

**Cause.** The new gate in `ManagementHandler::authorize()` reads the
journal's setting before the policies run, and there is no journal at
site level
([ManagementHandler.php at the head](https://github.com/pkp/pkp-lib/blob/9be1c9efb09c20cd38c87506610a8a014958f699/pages/management/ManagementHandler.php#L107-L110)).

## Finding 2: with comments off, one more path segment opens the page

With "Enable Public Comments" unticked, `…/management/settings/userComments`
and `…/userComments/` land on "Access denied.", but
`…/management/settings/userComments/x` (any extra segment) opens the
Comments page. Its requests are then refused like the rest of the
comments API, so nothing is listed or changed. Expected the same refusal.

**Cause.** The gate compares the request's arguments with exactly
`['userComments']`, while `settings()` routes on the first argument alone
(same lines).

**Proposed fix for both** (tried:
[page-gate-fix.diff](https://github.com/jardakotesovec/pkp-e2e/blob/i13539-main/shared/playwright/checks/sync/pkp-lib-13550/page-gate-fix.diff)):

```php
$context = $request->getContext();
if (($requestedArgs[0] ?? null) === 'userComments' && $context && !$context->getData('enablePublicComments')) {
    return false;
}
```

With it the site-level address answers as before the PR, the three
journal addresses are refused with comments off, and the page opens with
them on (the moderator's report panel, walked).

## Notes

- **The refused report** (U14 A14, ui-library#1024). The "Error" window
  now names the failure ("The requested resource was not found."), so a
  reader is told. The "Report Comment" window still closes behind it and
  the typed reason is lost, while a refused new comment keeps its text in
  the box. The PR's own description says the window "would close on
  error"; that half is unchanged. Not a regression.
- **A refused comment request** (`422`, e.g. no text) now also writes an
  error line with the validation message to the server log; before the PR
  nothing was logged. The answer is the same.
- **Comments off** refuses every comments request (`401`), so a
  moderator's Tasks entry about a comment leads to "Access denied." and a
  writer cannot delete their own comment until the setting is on again
  (the latter by the code, not walked). The kept comments are listed again
  once it is.
- The suite's S1 in the three apps now asserts "Access denied." for the
  page by address with comments off (the companion); round 1's version
  asserted the error dialogs.
