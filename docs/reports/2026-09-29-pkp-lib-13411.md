# "Cancel" after a second pick does nothing, or takes away another window's upload, when someone else revised the same file meanwhile

Regression. OJS at ojs `9d9f116f38` with lib/pkp at the head of the open
pkp/pkp-lib#13411 (`7263f86190`, 2026-09-29, issue #13286), before its
merge; the same lib/pkp code reaches OMP and OPS. On `main` (lib/pkp
`fab29cfeca`) the same steps restore the other window's revision.
stable-3_5_0: does not carry the change. Tracked in the submission-files
spec (U36 A26). Temporary: delete once acted on.

## Summary

The change fixes "Cancel" after a second pick on step 1, but breaks it
when someone else revised the same file while the wizard was open. If the
other revision was completed, "Cancel" does nothing: the window stays
open, and the upload just cancelled becomes the file. If the other
window is the same person's and still on step 1, "Cancel" also removes
that window's upload, which nobody cancelled.

## Impact

Editors, assistants and authors who revise a file in the upload wizard
("Upload" on a file list, a galley's "Change File"), pick a file, pick
another, then change their mind, while a colleague or another tab of
their own revised the same file. When the colleague finished their
revision, the one being cancelled replaces it with no warning. A
colleague who notices can upload theirs again from the file's history.
Minor: it needs two people (or two tabs) revising one file at the same
moment and a second pick before the cancel.

## Steps to reproduce

Preconditions:
- A fresh install; a journal with two Editors, A and B, and an Author.
- A submission whose "Submission Files" list holds `article.pdf`,
  uploaded by the Author.

1. As Editor A, open the submission's workflow, "Submission Files",
   "Upload". On "1. Upload File", choose `article.pdf` under "If you are
   uploading a revision of an existing file, please indicate which
   file.", pick `rev-a.pdf` and wait for it to finish uploading. Leave
   the window open.
2. As Editor B, in another browser, open the same workflow, "Upload",
   choose the same file (now listed as `rev-a.pdf`) as the file being
   revised, pick `rev-b.pdf`, then "Continue", "Continue", "Complete".
3. Back in Editor A's window, still on step 1, pick another file,
   `rev-c.pdf`, and wait for it to finish.
4. Press "Cancel".
5. Reload the page and read "Submission Files".

**Expected** (as on `main`): the window closes and the list shows
`rev-b.pdf`, Editor B's completed revision.

**Observed**: the window stays open with no message; the request answers

```
POST …/api/file/manage-file-api/cancel-file-upload → {"status":false,"content":"","elementId":"0","events":[]}
```

A second "Cancel" closes the window without a request. After the reload
the list shows `rev-c.pdf`, the upload Editor A just cancelled. The same
happens when step 2 is done by Editor A in a second tab of the same
browser. When that second tab is left on step 1 instead of pressing
"Complete", Editor A's "Cancel" closes and the list shows `article.pdf`:
`rev-b.pdf` is deleted, and the second tab's own "Cancel" then does
nothing. A single pick followed by "Cancel", and a second pick with no
other window, restore `article.pdf` correctly.

## Cause

`PKPManageFileApiHandler::cancelFileUpload()` now walks the revisions
from the one below the cancelled file down to the posted `originalFile`
and refuses unless every revision on the way has a stash in the current
session (`FileUploadWizardHandler::getOriginalFileSessionKey($id,
$replacedFileId)`) and none past the first is `confirmed`. A revision
another window uploaded sits in that walk: another user's upload writes
its stash into that user's session (missing here, line 139), and the
same person's "Complete" in the other tab marks the stash below it
`confirmed` (`finishFileSubmission()`, refused at line 143). A stash
written by the same person's other tab still on step 1 is neither, so
the walk passes it and `$chain->take($originalPosition)` deletes that
tab's upload with the others (lines 172 and 175–179).

## Proposed fix

A proposal, smallest first:

- Stop the walk at the first revision that is not this window's own
  (its stash missing or `confirmed`) and restore the revision just above
  it with the stash written when this window replaced it. That gives
  `rev-b.pdf` back in the "Complete" cases. It does not cover the
  same-person tab still on step 1.
- Key the stash by the wizard run as well: a token the wizard receives
  with its first upload and posts back on cancel. The walk then takes
  back only the run's own uploads and stops at the first revision that
  another run uploaded. This also covers the second tab and the order
  still refused in `docs/reports/2026-09-27-pkp-lib-13288.md` Finding 2.
- The page script could show a refused cancel instead of leaving the
  window open silently.
