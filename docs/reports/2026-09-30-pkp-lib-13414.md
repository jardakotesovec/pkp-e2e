# A users import refuses fixed dates written with a weekday name or as an ISO week date, and drops the role

Severity: medium · Effort: small · Intention gap · OJS OMP

Introduced: pkp/pkp-lib#13414 for pkp/pkp-lib#13412, commit `ed27614ef0`
(2026-09-29, second round, not yet merged), by Bozana Bokan (bozana)

`e8bf16a02f` (submodule-only, on the ojs tip `7ce98ec09e`), omp
`3b0ecf794`, both with lib/pkp at `ed27614ef0` (on pkp-lib `main`
`3dc90c81a6`). stable-3_5_0: not driven (pkp/pkp-lib#13413). Tracked in the

## Summary

The second round of the Users XML import fix accepts the common date
spellings, as the first round's review asked. Some dates that are fixed
dates are still refused, though, and they imported correctly on `main`:
- a date with its weekday name, such as `Fri, 05 Jan 2024 09:30:00 +0000`
  (the form PHP's `date('r')` and email headers use),
  `Fri, 05 Jan 2024 09:30:00 GMT` (JavaScript's `toUTCString()`) or
  `Friday, January 5, 2024`;
- an ISO 8601 week date, such as `2024-W01-5`.

Each gets the line "… is not a valid date." and the user is imported
without that role. The issue says only a date that "cannot be read as a
fixed date" is refused.

## Impact

Managers who import users from a file written by another tool that dates
roles in one of these forms. Each such role is left out with a line on the
Results tab. The manager can rewrite the dates and import the file again,
since users already imported are matched and only their missing roles are
added. On OJS's command-line import nothing is printed and the roles are
simply missing, which predates this PR. Medium: a task fails for a narrow
input, with a way round on the screen. It would be high if a widely used
tool wrote users files in these forms, which this review did not find.

## Steps to reproduce

Preconditions:
- A fresh OJS install, a journal and its Journal Manager.
- A users file with four new users, each given "Section editor" with one of
  these start dates: `Fri, 05 Jan 2024 09:30:00 +0000`,
  `Fri, 05 Jan 2024 09:30:00 GMT`, `Friday, January 5, 2024`,
  `2024-W01-5`.

1. As the Journal Manager open Tools › "Import/Export" › "Users XML Plugin".
2. On "Import Users", upload the file and press "Import Users".
3. Open Settings › Users & Roles › "Users".

**Expected** (as on `main`): "The import completed successfully. …". Each
user holds "Section editor" from 2024-01-05.

**Observed**: "Import/Export errors:" with a line per user, such as "The
role "Section editor" of the user "…" has not been imported because "Fri, 05
Jan 2024 09:30:00 +0000" is not a valid date.". The accounts exist without
the role. On a press the same happens with "Series editor". Control: at the
same head, `2024-01-05T09:30:00`, `2024-1-5`, `2024-01-05 09:30` and
`5.1.2024` import with 2024-01-05, and `soon`, `tomorrow`, `2027-02-30` and
`0000-00-00 00:00:00` are refused as intended.

## Cause

`UserXmlPKPUserFilter::parseRoleDate()` refuses a value when
`date_parse()` reports `relative` data. `date_parse()` puts a weekday name
there (`relative.weekday`), even beside a full date, and does the same with
an ISO week date (`relative.day`). The same method already requires a year,
a month and a day, and that alone refuses what the issue names:
"tomorrow", "+1 day" and "next monday" have no year. Before, the text
reached `UserUserGroup`'s `datetime` cast, which parsed all four.

## Proposed fix

A proposal, for the team to decide. The recommended fix is to drop
`|| !empty($parsed['relative'])` from `parseRoleDate()`. Tried on the
checkout's PHP and vendor:
- the four dates above read as 2024-01-05, with 09:30 where the text gives
  a time;
- `tomorrow`, `next monday`, `+1 day`, `2027-02-30`, `0000-00-00 00:00:00`,
  `soon` and `09:30` are still refused;
- `2024-01-05 +1 day` would then import as 2024-01-06, which is a fixed
  date.

A Unix timestamp (`1704447000`) is refused at the head and was imported on
`main`. Accepting digits as a timestamp would also turn `2024` into a 1970
date, which `main` did, so leaving timestamps refused seems right. It only
needs saying if the team wants it documented. Effort: small (one condition,
one test line per form).
