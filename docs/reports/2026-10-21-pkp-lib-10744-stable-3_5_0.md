## Summary

On 3.5, a journal (or preprint server) that deposits to ORCID through
the Member API and runs its background jobs with the command-line
worker (`php lib/pkp/tools/jobs.php work`, the way PKP's
documentation describes for production sites), gets failed jobs whenever it publishes an item one of whose
contributors has verified their ORCID iD. The item's search-index job
(`UpdateSubmissionSearchJob`) and metadata job (`MetadataChangedJob`)
each fail three times with "Call to a member function
getLocalizedName() on null" and land in Administration › "Failed
Jobs". Later metadata edits on the item fail the same way.

The publication itself works, and the deposit sent when it is
published still goes out. What is lost is the ORCID re-deposit that
3.5 added to the search index, and, by the code, the indexing of the
item's galley files, which comes after the failing call.

## Impact

- **Lost**: the re-deposit to ORCID that 3.5 sends from the search
  index; by the code, the galley text in the search index (the title,
  abstract and keywords are indexed before the failure); and a clean
  "Failed Jobs" list: three failed jobs for every such publish or
  metadata save. "Try Again" fails the same way under the worker.
- **Who**: journals and preprint servers with ORCID on the Member API
  whose jobs run in the worker or the scheduler
  (`process_jobs_at_task_scheduler = On`), each time they publish or
  edit an item with a verified contributor. Every 3.5 release has it.
  Installs that run jobs inside web requests (`job_runner = On`) do
  not meet it from the journal's own pages (code).
- **Way round**: none on screen. Running the jobs inside web requests
  avoids the failure.

Medium: no published content is lost and the publish-time deposit goes
out, but for installs that run their jobs in the worker every such publish leaves failed
jobs behind and loses the re-deposit, and (by the code) full-text
search of the item's files.

## Steps to reproduce

Preconditions: a fresh OJS 3.5 install (OPS the same), PostgreSQL or
MySQL, with `job_runner = Off` in `config.inc.php` (jobs left to the
worker). One journal with one issue.

1. As the Journal Manager, Settings › Users & Roles › "ORCID": tick
   "Enable ORCID functionality", set "ORCID API" to "Member Sandbox",
   enter a sandbox "Client ID" and "Client Secret", Save.
2. Submit an article whose author verifies their ORCID iD through the
   email link (their contributor then shows a verified iD in
   "Contributors"). Move it to Production and add a PDF galley.
3. In Publication, "Schedule For Publication", assign it to the issue,
   "Publish" (OPS: "Post").
4. On the server, run the jobs: `php lib/pkp/tools/jobs.php work
   --stop-when-empty`.
5. As the Site Administrator, Administration › "Failed Jobs".

**Expected**: every job ends "Processed"; the list is empty.

**Observed**: the worker reports `MetadataChangedJob` and
`UpdateSubmissionSearchJob` as failed after three tries, and "Failed
Jobs" lists them with "Call to a member function getLocalizedName() on
null" in `plugins/generic/citationStyleLanguage/CitationStyleLanguagePlugin.php`
line 461. The same steps with an author who has not verified their iD
leave no failed job.

## Cause

`ArticleSearchIndex::submissionMetadataChanged()` (OJS
`classes/search/ArticleSearchIndex.php`, lines 81-83; OPS
`PreprintSearchIndex.php`, lines 80-83) ends, for a published item,
with `(new SendSubmissionToOrcid($publication, $context))->execute()`,
added by `pkp/pkp-lib#10744` to "increase opportunity" for deposits.
`execute()` builds the ORCID work, and `OrcidWork::getBibtexCitation()`
asks the citation plugin for a BibTeX citation with
`Application::get()->getRequest()`. Run by the worker, that request
has no journal: `CitationStyleLanguagePlugin::getCitation()` takes
`$context = $request->getContext()` (line 440) and calls
`$context->getLocalizedName()` on null (line 461). The `Error` is not
an `Exception`, so `getBibtexCitation()`'s `catch (\Exception)` lets it
through and the job fails. In `UpdateSubmissionSearchJob` the call
comes before `submissionFilesChanged()`, so the galley text is not
indexed (code). Inside a web request (the publish request's own
deposit through the `PublicationPublished` listener) the request has
the journal, so that deposit works.

## Proposed fix

Let `getCitation()` fall back to the submission's own journal, and
build the citation's address with that journal's path instead of the
request's:

```php
$context = $request->getContext() ?? Application::getContextDAO()->getById($submission->getData('contextId'));
// …
$citationData->URL = $request->getDispatcher()->url($request, PKPApplication::ROUTE_PAGE, $context->getPath(), …);
```

(the same change in the three `URL` lines). It is in
[fix-stable-3_5_0.diff](https://github.com/jardakotesovec/pkp-e2e/blob/main/shared/playwright/checks/sync/pkp-lib-10744/fix-stable-3_5_0.diff),
a change to the citationStyleLanguage plugin
(`pkp/citationStyleLanguage`, `stable-3_5_0`).

Tried on OJS 3.5 (the kept script, Evidence): the item's search and
metadata jobs are "Processed", none fails; the only failed job left is
the ORCID deposit itself, which fails on the test install's blocked
network ("Failed to connect to api.sandbox.orcid.org"); its work
carries the article's address under the journal's own path
(`…/index.php/<journal>/article/view/15`). Not tried on OPS (the same
plugin code).

**Alternatives**: catch `\Throwable` in `OrcidWork::getBibtexCitation()`.
That keeps the jobs from failing but sends every re-deposit without its
citation. Or drop the search index's ORCID call, as `main` did.

**What goes with it**: without the path, the citation's address would
read `…/index.php/index/article/view/…` in the worker; with it the
address is right in both places. `job_runner = On` runs the job inside
whatever request picks it up, which may belong to another journal on
the same install; the fallback does not cover that (the request's
journal wins), so passing the submission's journal first would be the
stricter variant. Test: a job test that runs `UpdateSubmissionSearchJob`
for a published item with a verified contributor and no request
context.

Small: four lines in one plugin method.
