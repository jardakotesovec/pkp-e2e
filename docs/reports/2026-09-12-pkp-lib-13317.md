# pkp/pkp-lib#13317 (issue #13274): a mid-wizard language change now asks registry-matched authors to retype their affiliation

Read on 2026-09-12 at the ojs PR head `75df364d49` with lib/pkp at the pkp-lib PR head `3f82add062`, before the merge, on the OJS fleet (a fresh install, PostgreSQL). Companion branch `13274`. **Not a regression against the issue's intention**: the PR does what the issue asks. It widens the reach of a wizard limitation that already existed for typed institution names, so the team's call is whether that limitation should be fixed alongside. Filed as U21 ❓ A13.

## The change and its intention

Issue #13274: the 3.5 upgrade mapped affiliation strings to registry (ROR) records by exact name and linked "York University" to both York Universities. The intention (comment 5524949158): affiliation text is kept verbatim as a name, a ROR comes only from the legacy plugin's `rorId`. The PR rewrites the upgrade migration accordingly and, at runtime, changes `Repo::affiliation()->migrateUserAffiliation()`, the routine that copies the submitting user's profile affiliation into their contributor record when a draft is created: the text is copied per locale as a typed name, never matched to the registry cache, and the submission locale is filled from the profile's default locale when the profile has no text there.

Verified as intended (kept scripts under `shared/playwright/checks/sync/pkp-lib-13317/` on branch `13274`): all 16 outcomes of the issue's migration table on PostgreSQL, and the runtime copy in en and fr_CA drafts.

## Finding: after "Change" to another language, the copied affiliation and given name stay in the first language

**Steps on a fresh install (OJS):**

1. As a Journal Manager, under Settings › Website › Setup › Languages, enable English and French (Canada) for the UI, Forms and Submissions.
2. Register an Author whose profile "Affiliation" is a text that matches a registry record exactly, for example "Simon Fraser University" on a site whose ROR cache has been imported (on the fleet the cache is empty, so the check plants one record with that name through psql; see the script).
3. Signed in as that author, "Make a Submission" in English, tick the checklist, "Begin Submission".
4. Details step: press "Change" beside the language, choose "French (Canada)", "Save".
5. Contributors step: open your own row's "Edit", press "1 of 2 languages completed" under Affiliations.
6. Continue to "Review".

**Expected before the PR** (pkp-lib `b48c22ca06`, same planting): the draft's contributor carried the registry institution as a `ror` link with no name; a registry institution has no per-language name, the submit check skips it, and step 5 shows the institution, step 6 no contributor problem.

**Observed at the PR head:** the draft's contributor carries the text as `name.en` and no `ror`. Step 4's form sends `POST /index.php/{journal}/api/v1/submissions/{id}` with `X-Http-Method-Override: PUT`, answered 200; the submission's `locale` is now `fr_CA`, the affiliation and the given name still hold `{en}` only. Step 5's Affiliations table reads:

```
The primary language French (Canada) is required
1 of 2 languages completed
Type the institution name in French (Canada)
Selected  None
```

Step 6 shows "There are one or more problems that need to be fixed before you can submit. Please review the information below and make the requested changes." with, for an author whose profile given name exists in English only:

```
The given name is missing in French (Canada) for one or more of the contributors.
```

and, for an author whose given name exists in both languages (so only the affiliation is short):

```
The affiliation name is missing in French (Canada) for one or more affiliations for one or more of the contributors.
```

The author has to type the institution name (and the given name) in French before the draft can be submitted. This is what the PR's own Cypress change in pkp/ojs#5817 adds to the wizard test.

**Same steps without a registry record at the OJS tip `cea48a066b` (before the PR):** the same two messages. So for a typed institution name the limitation predates the PR; what the PR changes is who meets it: every author whose profile text happens to match a registry record, which is exactly the population the issue describes.

## Cause in the developer layer

- The wizard's "Change Submission Settings" form PUTs `submissions/{id}` (`PKPSubmissionController::edit()`), which saves the new `locale` and nothing else. Only the workflow's `changeLocale` route calls `copyMultilingualData()`, and the wizard does not use it.
- `migrateUserAffiliation()` fills the submission locale from the profile's default-locale text at draft creation only (the new fallback in `classes/affiliation/Repository.php`). Nothing re-runs it on a language change.
- `Repo::submission()->validateSubmit()` requires the affiliation name in the submission locale for non-registry affiliations (`submission.wizard.missingContributorAffiliationLanguage`) and the given name likewise; registry affiliations are skipped, which is why the old exact-match population never saw it.

## Options for the team

1. Carry the copied contributor fields into the new language when the wizard changes the submission language (call `copyMultilingualData()` from the wizard's path, or re-apply the creation-time fallback). The spec's lean.
2. Let the submit check accept the default-language name, as the creation-time fallback already does.
3. Accept as is: the wizard asks for the name in the new language, as it does for typed names today.
