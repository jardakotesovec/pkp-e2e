## Summary

The PRs for `pkp/pkp-lib#13593` add two columns for the new completion
step of an author's response to reviews, `date_completed` and
`date_reverted`. A fresh install gets them. An upgrade does not:

- **OJS.** Upgrading PKP's 3.5 test journal to 3.6 at the PR heads stops
  with `PHP Fatal error: Uncaught Error: Class
  "PKP\migration\upgrade\v3_6_0\I13593_I13593_AddDateCompletedAndDateRevertedToReviewRoundAuthorResponses"
  not found`, and the database is left half upgraded. `upgrade.xml`
  names the class with its issue prefix twice. The correct name would
  still not load, because the migration's file is named
  `I13593_AddDateCompletedToReviewRoundAuthorResponses.php` while its
  class is `…AddDateCompletedAndDateReverted…`.
- **OMP and OPS.** They have no PR, so their `upgrade.xml` has no line for
  the step. Their 3.5 test installs upgrade to 3.6 cleanly, but without
  the two columns. Both apps already run the earlier upgrade steps for
  this table (`I12048_ReviewRoundAuthorResponse`,
  `I12813_UpdateAuthorResponseAndSubmissionCommentTextType`).

Everything else the PRs add works as the issue asks (walked on the
default dataset; Evidence). That covers the single-response read, the
"completed" and "reverted" changes, who may make them, and the public
record listing a response only once it is public and completed.

## Impact

- **Lost**: the upgrade to 3.6, on every OJS site. On an upgraded press
  or server, any completion request would fail, because it writes the
  missing columns (code).
- **Who**: every OJS install upgrading to 3.6, and the OJS PR's own
  upgrade checks (`ojs-main … upgrade` jobs). Presses and servers
  upgraded from 3.5.
- **Way round**: none for the upgrade. After the fix, an install that is
  already on 3.6.0.0 needs the two columns added by hand, since the
  version does not change.

High: the upgrade path breaks for every journal. Effort is small: one
file rename, one corrected line, and two added lines.

## Steps to reproduce

Preconditions: PKP's default test dataset for `stable-3_5_0` (3.5.0.5),
loaded into OJS, OMP and OPS `main` with `lib/pkp` at the pkp-lib PR head
(OJS at the ojs PR head).

1. In each app, run `php tools/upgrade.php upgrade`.
2. OJS: the log lists `[migration:
   PKP\migration\upgrade\v3_6_0\I13593_I13593_AddDateCompletedAndDateRevertedToReviewRoundAuthorResponses]`,
   then the fatal error above, and the command exits 255.
3. OMP and OPS: "Successfully upgraded to version 3.6.0.0". Their
   `review_round_author_responses` has `response_id, review_round_id,
   user_id, created_at, updated_at, doi_id`, with no `date_completed` or
   `date_reverted`.

## Cause

- `ojs dbscripts/xml/upgrade.xml` (ojs#5985) names
  `I13593_I13593_AddDateCompletedAndDateRevertedToReviewRoundAuthorResponses`.
- `lib/pkp/classes/migration/upgrade/v3_6_0/I13593_AddDateCompletedToReviewRoundAuthorResponses.php`
  declares `class I13593_AddDateCompletedAndDateRevertedToReviewRoundAuthorResponses`.
  pkp-lib autoloads PSR-4 (`"PKP\\": "classes/"`), so a class loads only
  from a file of its own name. Its docblock already gives the right
  file name (`@file …/I13593_AddDateCompletedAndDateRevertedToReviewRoundAuthorResponses.php`).
- OMP and OPS have no PR, so nothing adds the step to their
  `upgrade.xml`.

## Proposed fix

Tried, in `shared/playwright/checks/sync/pkp-lib-13620/fix.diff`:

1. pkp-lib: rename the file to
   `I13593_AddDateCompletedAndDateRevertedToReviewRoundAuthorResponses.php`
   (and drop the doubled prefix in its `@class` line).
2. ojs#5985: name the class
   `PKP\migration\upgrade\v3_6_0\I13593_AddDateCompletedAndDateRevertedToReviewRoundAuthorResponses`.
3. OMP and OPS: the same `<migration>` line after
   `I12994_CompetingInterestsDeclared`, as pointer-bump PRs beside the
   pkp-lib one.

With the diff, the three 3.5 test installs upgrade to 3.6.0.0, and each
table gains `date_completed` and `date_reverted`. The same diff also
holds the fix for the PHP warning below. Tried on PostgreSQL only.

**Also seen (minor, same PR).** Each time a different editor marks a
response "completed" or "reverted", the server logs `PHP Warning: The
setting statusChangedByUserId doesn't have a defined type, using string
instead` (`SettingsBuilder.php:104`). The setting has no cast in
`AuthorResponse::$casts`. With `'statusChangedByUserId' => 'int'` added
there, as in `fix.diff`, the warning stops and the answer is unchanged
(walked).
