## Summary

The theme itself is opt-in, but the PRs that bring it also change shared
code every theme runs through. With them merged as they are, a journal
that stays on the Default theme is affected, and so are OMP and OPS:

1. OMP and OPS answer 500 on every page as soon as they receive the
   pkp-lib change.
2. The web installer fails on all three apps (this is why every Cypress
   job on ojs#5784 is red: the first test cannot install).
3. OJS's site-level home page (a site with several journals) answers 500
   on PostgreSQL.
4. Every "access denied" page shows the raw text key instead of its sentence.
5. The message pages (closed registration, awaiting verification,
   section closed, not allowed, …) lose their heading.
6. The login page prints whatever `loginMessage` the address carries, as HTML.
7. The editor's "Author Response to Reviews" window opens with the response empty.
8. Default theme, OJS: every article page shows a "JATS XML" button that links nowhere.
9. Default theme, OJS: the article sidebar's "Comments" box is empty and
   the comments lose their layout.
10. Default theme, OJS: the journal home page lists the categories whether
    or not the theme option asks for them.
11. Ticking "Eidos" under Plugins on a checkout where the theme was not
    built makes Website Settings answer 500, so it cannot be unticked.
12. Two shared templates are removed while OMP's payment plugins (and any
    third-party plugin or theme) still call them.

Of the 84 red Playwright tests on ojs#5784, 78 come from these
findings, 5 from two changes that look intended ("Questions for the
author" at the end) and one is already red on `main`. Seven one-line
changes (findings 2 to 5, 7 and 8) turn 47 of 64 red tests rerun locally
green; the other 17 are findings 9 and 10 (11 tests), those 5 and the
one known red.

## Finding 1 — OMP and OPS answer 500 on every page

- **Severity** critical · **Effort** medium (two more app PRs, or a fallback in pkp-lib) · **Crash** server
- **Affects** OMP, OPS (the moment their `lib/pkp` reaches pkp-lib#13260)

**Impact.** Every page of a press or a preprint server fails. Nothing in
the PR set updates OMP or OPS, so merging pkp-lib#13260 alone breaks both
at their next submodule update.

**Steps.** OMP or OPS at its tip, `lib/pkp` checked out at pkp-lib#13260's
head. Open any page, for example `/index.php/publicknowledge/en`.

**Observed**: HTTP 500, empty body. Server log:

```
PHP Fatal error:  Uncaught Error: Class "APP\view\MetadataBlocksRegistry" not found in lib/pkp/classes/template/PKPTemplateManager.php:195
```

**Cause.** `PKPTemplateManager::__construct()` now does
`new MetadataBlocksRegistry()` and `new HomepageBlocksRegistry()` from
`APP\view\…`. Only ojs#5784 adds those two classes.

**Proposed fix.** Add the two classes to OMP and OPS in PRs that merge
with pkp-lib#13260 (tried: two empty subclasses of
`\PKP\view\HomepageBlocksRegistry` and `\PKP\view\MetadataBlocksRegistry`
in each app; login, home, catalog and search pages answer 200 again). Or
let pkp-lib fall back to its own two classes when the app has none (the
two typed properties in `PKPTemplateManager` then take the `PKP\view`
types; not tried).

## Finding 2 — The web installer fails

- **Severity** high · **Effort** small · **Crash** server
- **Affects** OJS, OMP, OPS

**Impact.** A new install through the browser is impossible; the
command-line installer is the way round. Every Cypress job of ojs#5784
fails on its first test for this reason ("Installs the software":
`Expected to find element: input[name=adminUsername]`), and each later
test fails behind it.

**Steps.** A checkout at the PR heads with `installed = Off` in the
configuration file. Open `/index.php/index/install`.

**Observed**: a fatal error instead of the form
(`Smarty Compiler: … install.tpl … unknown tag 'translate'`). The first
error in the server log is the real one:

```
#13 lib/pkp/classes/site/SiteDAO.php(43)
#14 lib/pkp/classes/core/PKPRequest.php(549): PKP\site\SiteDAO->getSite()
#15 lib/pkp/classes/template/PKPTemplateManager.php(229): PKP\core\PKPRequest->getSite()
```

**Cause.** `PKPTemplateManager::initialize()` now assigns
`'site' => $request->getSite()` for every request. Before the install
there is no database to read the site from; the exception leaves the
template manager half set up and the installer's template then fails.

**Proposed fix.** `'site' => Application::isInstalled() ? $request->getSite() : null`,
as the rest of `initialize()` guards its reads (tried: the installer form
renders).

## Finding 3 — The site's home page answers 500 on PostgreSQL

- **Severity** high · **Effort** small · **Crash** server
- **Affects** OJS (any theme; a site with two or more journals and no journal redirect)

**Impact.** The page that lists the site's journals fails for every
visitor. About 27 of the red tests stop here (U59 and U60, the
site-level parts of U01, U02, U05, U07, U08, U10, U12, U20, U50, U57, U61).

**Steps.** OJS on PostgreSQL with two journals. Open `/index.php/index`.

**Observed**: HTTP 500.

```
SQLSTATE[22P02]: Invalid text representation: 7 ERROR:  invalid input syntax for type bigint: "*"
… where "s"."context_id" in (*) and "s"."status" in (3)
#12 classes/view/HomepageBlocksRegistry.php(132): PKP\submission\Collector->getCount()
#17 pages/index/IndexHandler.php(143): PKP\view\HomepageBlocksRegistry->load()
```

**Cause.** `IndexHandler::index()` now runs every registered homepage
block's loader, for every theme. Two loaders in OJS's
`HomepageBlocksRegistry` (the "search" block and the "recent issues"
block) pass the literal `'*'` as the context id on the site level. The
collectors' wildcard is `Application::SITE_CONTEXT_ID_ALL` (`-1`), so
`'*'` reaches the query.

**Proposed fix.** Use `Application::SITE_CONTEXT_ID_ALL` in both loaders,
as the "latest articles" loader beside them does (tried: the twelve
site-home tests rerun pass). Finding 10's fix would also keep these
queries from running for themes that show no blocks.

## Finding 4 — "Access denied" pages show the raw text key

- **Severity** low · **Effort** small
- **Affects** OJS, OMP, OPS (any theme)

**Impact.** A user sent to the refusal page reads
`user.authorization.roleBasedAccessDenied` instead of "The current role
does not have access to this operation." Every refusal goes through this
page, which is why about 30 tests are red.

**Steps.** PKP's default dataset. Sign in as `amwandenga` (an author) and
open `/index.php/publicknowledge/en/management/settings/website`.

**Expected**: "The current role does not have access to this operation."
**Observed**: breadcrumb "Home / Error", an empty heading (this page had
none before the change either) and the text
`user.authorization.roleBasedAccessDenied`.

**Cause.** `PKPUserHandler::authorizationDenied()` passes the locale key
from the address to `displaySystemMessage()`, which prints its `message`
as text; the old template translated it (`{translate key=$message}`).

**Proposed fix.** `message: __($authorizationMessage)` (tried).

## Finding 5 — Message pages have no heading

- **Severity** low · **Effort** small
- **Affects** OJS, OMP, OPS (themes that use the Smarty template; Eidos has its own)

**Impact.** The pages "Register" (registration closed), "Registration
awaiting verification", "Section Closed", "Not Allowed" and the payment
messages render an empty `<h1>` (seen: "Register" with registration
closed, U02 S5; the others by their tests, U02 S7, U21 S9 and S12, U52
S3). The browser tab's title comes from the same variable: the page an
invalid password-reset link leads to keeps its heading, and its tab
reads `##Reset Password## | Journal of Public Knowledge`.

**Steps.** Switch registration off for the journal and open its
registration page.

**Cause.** `displaySystemMessage()` assigns `title`;
`templates/frontend/pages/system-message.tpl` prints `{$pageTitle}`, and
`header.tpl` builds the tab title by translating `$pageTitle`, which is
no longer assigned (or, where a caller still assigns it, is now a
sentence, not a key).

**Proposed fix.** `{$title}` in the template (tried), and
`'pageTitleTranslated' => $title` among the variables
`displaySystemMessage()` assigns, which `header.tpl` uses as it is (not
tried).

## Finding 6 — The login page prints the address's `loginMessage` as HTML

- **Severity** medium · **Effort** small · **Security** unreleased
- **Affects** OJS, OMP, OPS (any theme)

**Impact.** Anyone can hand out a link to a journal's real login page
that shows their own sentence above the form, with a working link or an
image in it (scripts are stripped, links and images are kept). On `main`
and 3.5 the template translates the parameter as a text key
(`{translate key=$loginMessage}`), so no markup from the address reaches
the page. Links the application made before the change (carrying a key)
now show the key.

**Steps.** Open
`/index.php/publicknowledge/en/login?loginMessage=Your session has expired. <a href="https://example.org/">Sign in here</a> instead.`

**Observed**: the login page shows "Your session has expired. Sign in
here instead." with "Sign in here" linking to example.org. With
`?loginMessage=user.login.loginError` it shows `user.login.loginError`.

**Cause.** `Validation::redirectLogin()` now puts the translated sentence
into the address, and `userLogin.tpl` prints
`{$loginMessage|strip_unsafe_html}` where it had `{translate key=$loginMessage}`.

**Proposed fix.** Keep the key in the address and translate it in
`LoginHandler` behind the check `authorizationDenied()` already has
(`/^[a-zA-Z0-9.]+$/`), then print the result. Not tried.

## Finding 7 — The editor's "Author Response to Reviews" window is empty

- **Severity** medium (high if no other screen shows an editor the response) · **Effort** medium
- **Affects** OJS (the review stage, any theme; OMP and OPS have no such window)

**Impact.** An editor opening an author's response to the reviews sees an
empty text (U30 S8), and the window stays open after the editor's "Save"
(U30 S3).

**Steps.** A submission in review whose author has answered the reviews.
As the editor, open "Author Response to Reviews".

**Observed**: the window's text is empty.

**Cause.** `ReviewRoundAuthorResponseResource` now returns
`'response' => $response->getLocalizedData('authorResponse')` (a string).
The workflow's form reads `reviewRound.authorResponse.response` as the
field's value per language (ui-library
`ReviewRoundResponseManager/useAuthorResponseForm.js`).

**Proposed fix.** Leave `response` as it was and give the reader side its
own localized key, which ui-library's
`PkpOpenReviewAuthorResponseContent.vue` and Eidos's
`tab-peer-review.blade` (both now expect a string) then read. Tried:
with the line restored U30 S3 and S8 pass; the reader side with a new
key was not written.

## Finding 8 — Default theme: a "JATS XML" button on every article that links nowhere

- **Severity** low (a dead button, nothing lost; on every article page) · **Effort** small
- **Affects** OJS (Default theme and any theme using its `article_details.tpl`)

**Impact.** Every article page shows a "JATS XML" download button beside
"PDF", also when the journal does not publish JATS; it reloads the page.

**Steps.** PKP's default dataset. Open article 1, "The Signalling Theory
Dividends".

**Expected**: "PDF" alone. **Observed**: "PDF" and "JATS XML"
(`<a class="obj_galley_link xml" href="">`).

**Cause.** `ArticleHandler` now always assigns `jatsDownloadUrl` (an empty
string when JATS is not public); `article_details.tpl` tests
`{if isset($jatsDownloadUrl)}`.

**Proposed fix.** `{if $jatsDownloadUrl}` in the template (tried: U46 S3,
U48 S4 and S5 pass).

## Finding 9 — Default theme: the comments lose their sidebar box and their layout

- **Severity** medium · **Effort** medium
- **Affects** OJS with public comments on (Default theme)

**Impact.** The article sidebar's "Comments" box is a heading with nothing
under it (it held "All Comments (n)" and the sign-in prompt). The
comments part still loads and a comment can be written, but the
per-version headings with their counts are gone and the new markup has
no styling in the Default theme. Ten U14 tests are red.

**Steps.** PKP's default dataset; as `dbarnes` switch public comments on;
open article 1.

**Cause.** ui-library#972 deletes `PkpScrollToComments` and the other
comment sub-components and rebuilds `PkpComments`; `article_details.tpl`
still has `<pkp-scroll-to-comments>`, and ojs#5784 removes the matching
rules from the Default theme's `comments.less`.

**Proposed fix.** A decision for the author: keep the old components
registered for the Default theme, or update its template and styles to
the new ones in the same PR. Not tried.

## Finding 10 — Default theme: the home page lists the categories regardless of the theme option

- **Severity** medium · **Effort** medium
- **Affects** OJS (Default theme; every journal with categories)

**Impact.** A journal that did not choose "category listing" for its home
page now shows its categories at the top of it.

**Steps.** PKP's default dataset (the theme option holds the issue's table
of contents alone). Open the journal's home page.

**Expected**: no categories. **Observed**: "Applied Science" and "Social
Sciences" above "Current Issue".

**Cause.** `IndexHandler::index()` runs every homepage block's loader for
every theme. The "categories" loader assigns `categories`, the variable
the Default theme's template shows when it is set. The loaders also add
queries to every home page view whatever the theme (a count of the
published submissions, the recent issues, two file-genre lookups).

**Proposed fix.** Load only the blocks the active theme has selected (none
for a theme without the option), or keep block data out of the template
variables older themes read. Not tried.

## Finding 11 — "Eidos" ticked on an unbuilt checkout locks Website Settings

- **Severity** medium · **Effort** medium · **Crash** server
- **Affects** OJS, where `plugins/themes/eidos/dist/` is missing

**Impact.** Step 3 of the issue's own test steps on a plain checkout:
after ticking "Eidos" under Website Settings › Plugins, Website Settings
answers 500, and the Plugins tab where it would be unticked is on that
page. The
theme's `dist/` is ignored by git and nothing in the PRs builds it (no
workflow, no packaging step). `npm ci` in the theme folder refuses the
committed lock file ("Missing: @emnapi/core@1.11.3 from lock file",
npm 10.9); `npm install` and `npm run build` work, and the theme then
renders (home, article, login, search driven).

**Observed**:

```
PHP Fatal error:  Uncaught RuntimeException: Manifest file not found: plugins/themes/eidos/dist/.vite/manifest.json in plugins/themes/eidos/classes/ViteLoader.php:170
```

**Proposed fix.** Let the loader log and skip when the manifest is
missing; add the theme's build to the app's build, CI and release
packaging; regenerate the lock file. Not tried.

## Finding 12 — Two removed templates are still called

- **Severity** medium · **Effort** small
- **Affects** OMP (code); third-party plugins and themes (not surveyed)

**Impact.** pkp-lib#13260 deletes `frontend/pages/error.tpl` and renames
`frontend/pages/message.tpl`. OMP's Manual Fee and PayPal plugins still
display `frontend/pages/message.tpl` (four places), as may any plugin
outside the PR set, and a theme that overrides either file is no longer
used for these pages. Read in the code, not driven.

**Proposed fix.** Keep the two old files as they were beside the new one
(their callers assign text keys, which the old files translate and the
new one prints as text), marked deprecated; or update OMP's plugins in
the same PR set and announce the removal to plugin authors.
