## Summary

At the OMP PR head, on PHP 8.3 with OPcache, a PHP process that has served the press's catalog (or a
book page) answers every later request for a category page, and every later read of Statistics ›
Editorial Activity, with a server error. It stays that way until the PHP process is replaced. The
PR's own e2e check on omp#2372 is red for this reason (U16 "Categories" and U65 "Editorial
statistics", different scenarios in each run). One line of omp#2372 causes it, and a two-line preload
in pkp-lib removes it.

## Impact

- **Lost**: the public "category" pages of a press, the "Browse" block's category links, Statistics ›
  Editorial Activity and the monthly statistics email the same code builds.
- **Who**: readers and editors of every OMP press on PHP 8.3 with OPcache, which is PHP's default for
  web servers.
- **Way round**: none for a reader; restarting PHP helps until the catalog is opened again.

High: a public page of every press fails for every reader after an ordinary first visit, on a
supported PHP version, and reloading does not help. Seen on PHP 8.3.33 (the VM) and on the CI
runners; PHP 8.4 was not tried.

## Steps to reproduce

Preconditions: OMP at omp#2372's head with its submodules, PHP 8.3 with OPcache on, a press with one
category and one published book, served by one PHP process (`php -S 127.0.0.1:8000`).

1. Start the server.
2. Open the press's "Catalog" (`/index.php/publicknowledge/en/catalog`).
3. Open a category from it (`/index.php/publicknowledge/en/catalog/category/<path>`).

**Expected.** The category page (as on `main`, and as at the PR head when step 2 is left out: 200,
four times in a row).

**Observed.** HTTP 500 and an empty page, on this and every later request for a category page. The
server log:

```
PHP Fatal error:  During inheritance of PKP\publication\DAO, while autoloading
APP\publication\Publication: Uncaught Error: Class "PKP\publication\PKPPublication" not found in
classes/publication/Publication.php:28
```

`GET /api/v1/stats/editorial` answers 500 with the same fatal, so the Editorial Activity table shows
zeros.

## Cause

`APP\publication\Publication extends PKPPublication`, `PKPPublication::getDAO(): DAO`, and the DAO's
method signatures name `Publication` again: an old cycle. On `main`, OPcache declares OMP's
`Publication` with delayed early binding, which tolerates the cycle. omp#2372 adds
`use HasContextIdentityMetadata;` to the class (classes/publication/Publication.php line 30); a class
that uses a trait is declared at run time instead (`DECLARE_CLASS` instead of `DECLARE_CLASS_DELAYED`
in the OPcache dump), and that path refuses a parent that is still being linked. So a request whose
first publication class is `PKPPublication` (a `PKPPublication::STATUS_PUBLISHED` read in
`DatabaseEngine::buildQuery()` line 122 for the category page, in `PKPStatsEditorialQueryBuilder`
line 355 for the statistics) fails once an earlier request has left the classes in OPcache's
inheritance cache in the other order. OJS and OPS use the same kind of trait, but every request of
theirs that was tried loads the APP class first.

## Proposed fix

Link both class families through their APP class at the start of every request, in
`lib/pkp/includes/bootstrap.php` after the Composer autoloader (the fix proposed on 2026-09-30 for
the PHP 8.3 OPcache crash of the same cycle on `main`; pkp-lib 14a478bc53 does the same in single
handlers):

```php
class_exists(\APP\submission\Submission::class);
class_exists(\APP\publication\Publication::class);
```

- Tried on OMP at the PR head (`shared/playwright/checks/sync/pkp-lib-12915/fix.diff`): the steps
  above answer 200 throughout, and OMP's U16 and U65 spec files run green (12 passed) where three to
  five of their scenarios failed without it.
- It changes no behavior, API or hook. It belongs in pkp-lib#12915, since OMP needs it to merge
  omp#2372.
- Alternative, not tried: keep the resolvers off OMP's `Publication` class (in `PKPPublication` or a
  helper), so the class uses no trait.
- Guard: the e2e suites already cover it (OMP U16 S1, S6, S8; U65 S3 to S6).

## Further findings

Each was reproduced on a database reset the same day; none is a crash.

### 1. OJS: a major version with a new DOI keeps the issue's old identity (medium · small · intention gap)

- Steps: "DOI versioning" on; publish an issue with one article; rename the journal (name, initials,
  ISSNs, publisher); create a major version of the article and publish it.
- Expected (decisions, "Versioning" and "Article vs. issue stamps in DOI deposits"): the new version
  is "re-stamped from the current context", and its deposit carries the new identity.
- Observed: version 2.0, with its new DOI, returns `contextName` "Old Name Journal",
  `contextAbbreviation` "ONJ", the old print ISSN and "Old Publisher"; the Issue form lists "Journal
  Title: Old Name Journal" and the page has `citation_journal_title` "Old Name Journal". The same
  steps on an article without an issue give the new identity.
- Cause: OJS `Publication::stampContextIdentity()` returns early through
  `inheritContextIdentityFromIssue()` whenever the publication's issue is published and stamped,
  which is also true of a new major version in the same issue.
- Fix (not tried): inherit from the issue only for a first version (no earlier published version of the
  submission); a version whose stamp `Repository::version()` cleared takes the context's.

### 2. OJS, OMP: a field that was empty at publication follows the journal's current value (medium · medium · intention gap)

- Steps: a journal with a print ISSN only; publish an article; then give the journal a new name, a
  new print ISSN and an online ISSN.
- Expected (acceptance criteria: "Changing the journal name or ISSN after publication does not alter
  the stamped values"): the old article keeps its old title and its one old ISSN.
- Observed: OAI `oai_dc` has `Old Name Journal`, the old print ISSN `0378-5955` and the new online
  ISSN `2049-3630`; `DC.Source.ISSN` and `citation_issn` show `2049-3630` alone; Crossref
  `<full_title>Old Name Journal</full_title>` with `<issn media_type="electronic">2049-3630</issn>`;
  DOAJ and MARC likewise; DataCite sends the new EISSN and not the stamped print ISSN.
- The CLI tool has the same hole: `--online-issn=` previews "Online ISSN: (none) [given, cleared]"
  and reports "1 stamped", and the outputs still carry the journal's online ISSN; `--publisher=`
  likewise in OAI `dc:publisher` (OMP too).
- Cause: the per-field resolvers (`getData('onlineIssn') ?: $context->getData('onlineIssn')`, the
  same for the print ISSN, the publisher, the abbreviation and OMP's publisher code) cannot tell
  "stamped as empty" from "never stamped".
- Fix (not tried): let the resolvers fall back only when the object has no identity at all
  (`hasContextIdentity()` false); a stamped object returns its own value, empty included.

### 3. OMP: the Dublin Core meta tags keep the press's current name (low · small · intention gap)

- Steps: publish a book, rename the press, read the book page's source.
- Observed: `<meta name="DC.Source" content="New Name"/>` beside
  `<meta name="citation_publisher" content="Old Name"/>`.
- Cause: OMP's `plugins/generic/dublinCoreMeta/DublinCoreMetaPlugin.php` lines 149 and 309 still read
  `$press->getName(...)`; omp#2372 does not touch the file, while the decisions list "DC meta tags"
  among the moved paths and OJS's plugin was changed.

### 4. OMP: "How to Cite" takes the place of publication from the Masthead, no longer from the plugin (low · small · question)

- Steps: a press with Masthead "Geographical Location" Burnaby and the Citation Style Language
  plugin's "Publisher Location" Vancouver; publish a book; read the citation.
- Before: "Vancouver". Observed: "Burnaby: Old Name" for the stamped book (an unstamped one still
  reads "Vancouver").
- OMP stamps `publisherLocation` from the press `location` and the plugin now prefers the stamp. The
  decisions say only that OMP stamps `location`; if the switch is meant, a press that set the two
  differently sees its citations change at the upgrade, which the release notes should say.

### Seen in passing

- OPS: the checklist's own example `PUT {"publisher": "Hijacked Publisher"}` answers 200 and the
  value is dropped (a preprint has no `publisher` property), where the checklist expects 400; the
  four fields OPS does stamp answer 400.
- A PUT that names an identity field with a null value is refused with 400, and a GET returns those
  keys (null, `contextName` `{"en": ""}`) on a never stamped draft. A whole GET body sent back was
  already refused before the PR (403 on `status`), so no regression.
- ojs#5608 is one commit behind `pkp/ojs` `main` (`4408b94def` "Update submodules") and GitHub shows
  it as conflicting; it needs a rebase before the merge.
- The OPS pointer move of `plugins/generic/googleScholar` also brings googleScholar#38 (article
  numbers, pkp-lib#12609).

## What held

On OJS, OMP and OPS, unless an app is named: the stamp on publish (single article, issue publish,
scheduled, an article added to a stamped back issue), unpublish and republish, minor and major
versions with DOI versioning off, a major version outside an issue with it on; the read-only
"Identity" group on stamped publications only, with the forms still saving; the API's 400 on a
stamped field (OJS, OMP); the Native XML round trip against the XSD, and an import without identity
staying unstamped; the upgrade migration on PostgreSQL (published content only, nothing overwritten,
a second run adds nothing, the location only with the CSL plugin on); the CLI tool (usage, the
interactive-only refusal, every validation error, the preview, a second run reporting "unchanged",
stale DOIs); and after a rename the stamped values in the DC and Google Scholar tags, CSL, BibTeX and
RIS, PubMed, OAI DC and MARC, Crossref with a live `<registrant>`, JATS with a live `<journal-meta>`
and `prev-*` entries, ONIX and OMP's OAI DC, with the live values for content that has no stamp.

Not read: the DataCite issue export answers 500 on the test install (the failing line is the same on
`main`), and coins, medra, cnki, inspec and openAIRE are not installed, so their PRs were read as
diffs only (they use the same resolvers as finding 2).
