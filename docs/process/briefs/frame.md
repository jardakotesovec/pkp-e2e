This is QA documentation of an application's own screens, on a local disposable test install with seeded accounts. Sign in as each role and use the screens the way that role would, including typing a URL directly to reach one. Record what the screen offers, what happens when it is used, and where the two disagree, including any API misbehavior the browser's own traffic shows along the way, so the product team can fix it. Never construct a request the screens themselves would not send, with one exception: an API the spec says no screen calls is checked directly, sending the requests its claims name as the role each claim names, on scratch data, and what that shows is a finding like any screen's. A finding that could plausibly be a security weakness goes ONLY into the maintainer's private security file, written the way `docs/process/briefs/security-verify.md` "The private file" says (read the whole file first, one entry per problem, marked `unverified`), never into a spec, test, report file or commit, because these repos are public. Say THAT you routed something there, and keep its content out of everything else. A request that fails on the server or a page script that fails in the browser is a finding on its own, whether or not the screen shows anything.
