# The default test dataset

PKP's default test dataset (<https://github.com/pkp/datasets>) is the
install every PKP developer, test server and CI run starts from: one
context per app, in English and French, a roster of editors, reviewers
and authors, and a set of submissions in every stage. pkp's CI rebuilds
it from the apps' Cypress data tests, one dump per app, branch and
database (`<app>/<branch>/<dbms>/`: `database.sql`, `config.inc.php`,
`files/`, `public/`). The team has it; the campaign's own seed
(`publicknowledge` with the roster of `users.md`) they do not. So the
steps of an issue report (`REPORT.md`) start from this dataset, and a
walk that proves them runs on a **dataset fleet**, which holds exactly
what the team's installs hold (harness.md "Dataset fleets").

## Writing steps against it

- Name the dataset once, before the steps: "PKP's default test dataset
  for `main`" (or `stable-3_5_0`), as `npm run fetch-datasets` fetched
  it; the tables below say which pkp/datasets commit they were read from.
- Sign in by username: every user's password is the username twice
  (`dbarnes` / `dbarnesdbarnes`); the site administrator is `admin` /
  `admin`. Pick the user by role from the tables below: `dbarnes` is the
  editor (a manager-level group, so every submission is open to him;
  assigned to all of OJS's, a few of OMP's, none of OPS's), `rvaca` the
  manager, `dbuskins`, `sberardo`, `minoue` section editors (series
  editors, moderators), and each author account owns one submission.
  As on the campaign's fleets (seed-facts.md "Install defaults"), an
  editor or manager lands on the dashboard's "Assigned to me" (empty for
  `rvaca`; "Active submissions" lists every one), the one context leaves
  out the Site Settings tabs a second context brings ("Appearance",
  "Plugins", "Navigation" among them), and DOIs are on for the first kind
  with no prefix and no agency, so the DOIs "Setup" form refuses a save
  until a prefix is set (U09, U19, U45, U54, U57, U63 issue walks).
- Name a submission by its ID and title ("open submission 7,
  'Developing efficacy beliefs in the classroom'"), and the context by its
  path, `publicknowledge` in all three apps. "(2 versions)" in the tables
  may mean an unpublished latest version beside the published one (OJS
  submission 1's 1.1), and the workflow opens on the latest: a step on the
  published version picks it in the Publication menu ("All Versions" on
  3.5) (U13, U19, U44 issue walks).
- Name screens and buttons, not the fleet's addresses: the team's install
  runs on its own host and port. A path after `index.php/` is fine
  (`/index.php/publicknowledge/en/dashboard/editorial`).
- A step that changes the data (a decision, an assignment, a new user)
  changes it for the next walk too: steps start from a freshly loaded
  dataset, and a walk resets its fleet first (harness.md "Dataset
  fleets").
- A form with fields in two languages shows the English ones alone; the
  French fields appear once the button reading "French" above the form
  is pressed (`.pkpFormLocales__locale`), so a step names that press and
  the button as the screen words it, "French", not "Français" (U10 issue
  walk).
- Mail: every dataset user's address is `<username>@mailinator.com`
  (`pkpadmin@mailinator.com` for `admin`), the same in all three apps, so
  a mailbox read on a slot's Mailpit is scoped by recipient and time, not
  by app. The dataset's own config runs the job runner and the scheduled
  tasks on web requests (`job_runner = On`, `task_runner = On`), as a
  team install does and unlike the campaign fleets, so mail a job sends
  goes out without `drainJobs()`.
- Submission IDs and names come from the Cypress data build, whose order
  has been stable; the dump is regenerated, so a report names the date of
  the commit its walk loaded (`fleet.json` records it).

The tables are generated from the dumps, never written by hand:
`npm run dataset-facts -- --write` (after `npm run fetch-datasets --
--update`) rewrites the part between the markers. "Editors" are the
managers and section editors assigned to the submission, "Author
accounts" the authors with an account on it, "Other participants" the
assistants, each with the role it was assigned in (a stage's windows
offer only the roles that stage has, so a Copyeditor is not offered at
Production); a press's series carry their path; reviewer states
are the assignment's (`not responded` means not yet accepted or declined).
The dataset's titles hold no tags or entities: "Hansen & Pinto: Reason
Reclaimed" is stored with a bare "&", so a walk about a title's HTML
saves its own from a "Title" box.
